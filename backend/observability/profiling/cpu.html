可观测性与性能分析：CPU 分析深度指南 ​

1. 核心概念 ​

1.1 什么是可观测性？ ​

可观测性不仅仅是监控。它是指通过系统外部输出（如指标、日志、链路），来理解系统内部状态并探究未知问题的能力。

  • 监控：基于已知故障模式，设置告警。（已知的未知）
  • 可观测性：当出现未知问题时，有能力提出新问题并找到根源。（未知的未知）

1.2 CPU 相关的基础指标 ​

  • 利用率：CPU 忙于执行任务的时间百分比。
    • 用户态利用率：执行应用程序代码的时间。
    • 内核态利用率：执行操作系统内核代码的时间（如系统调用、中断处理）。
    • I/O 等待时间：CPU 空闲，但等待 I/O（通常是磁盘或网络）完成的时间。高 I/O 等待通常意味着瓶颈在 I/O，而非 CPU。
    • 空闲时间：CPU 完全空闲的时间。
  • 负载平均值：系统在特定时间间隔内（1分钟、5分钟、15分钟）的平均可运行线程数和不可中断睡眠线程数。它反映了系统的“繁忙”程度，而不仅仅是 CPU 利用率。
  • 上下文切换：CPU 从一个进程（或线程）切换到另一个的过程。频繁的上下文切换会带来开销。
  • 中断：硬件或软件发出请求，要求 CPU 暂停当前工作去处理紧急事件。
  • 时钟速度与核心数：物理硬件的基准能力。

3. 关键工具集 ​

根据上图的分析路径，我们需要使用不同的工具来获取数据。

3.1 宏观状态工具（第一眼诊断） ​

这些工具用于快速获取系统的整体健康状况。

  • top / htop

    • 功能：实时显示进程和系统资源使用情况。
    • 关键指标：
      • %Cpu(s) 行：us（用户）, sy（系统）, wa（I/O等待）, id（空闲）。
      • LOAD AVERAGE： 1, 5, 15分钟平均负载。
    • 用法：运行 top，按 1 查看每个 CPU 核心的详情。

  • vmstat

    • 功能：报告关于进程、内存、分页、块 I/O、陷阱和 CPU 活动的信息。
    • 关键指标：
      • r：可运行进程数。
      • cs：上下文切换次数。
      • us, sy, id, wa：同 top。
    • 用法：vmstat 1（每秒输出一次）。

  • mpstat

    • 功能：报告每个 CPU 核心的统计数据。
    • 用法：mpstat -P ALL 1。用于检查 CPU 使用率是否均衡，或者是否有单个核心被打满。

3.2 深入分析工具（寻找根因） ​

当宏观工具指出方向后，使用这些工具进行深度剖析。

  • pidstat

    • 功能：用于监控单个任务的资源使用情况。
    • 用法：
      • pidstat -u 1：查看所有进程的 CPU 使用。
      • pidstat -t -p <PID> 1：查看指定进程及其所有线程的 CPU 使用。
      • pidstat -w -p <PID> 1：查看指定进程的上下文切换情况（自愿/非自愿）。

  • perf

    • 功能：Linux 上最强大的性能剖析工具。它可以进行 CPU 性能计数、跟踪点分析、调用栈采样等。
    • 核心用法：
      1. 采样分析：perf record -F 99 -a -g -- sleep 30 （对全系统 -a 进行 99Hz 采样，持续30秒，并记录调用栈 -g）。
      2. 报告分析：perf report 或 perf report -n --stdio。查看热点函数和调用图。
      3. 统计进程：perf top 实时查看消耗 CPU 最多的函数。
    • 解读火焰图：
      • 使用 perf script 输出数据，然后用 FlameGraph 脚本生成火焰图。
      • 如何阅读：X轴显示堆栈深度，Y轴显示调用栈。每个矩形代表一个函数，宽度代表它在采样中出现的频率（即耗时）。寻找最宽的函数“平顶”就是热点。

  • eBPF/BCC 工具集

    • 功能：下一代动态追踪工具，可以在内核中安全地运行小程序，以极低的开销提供强大的观测能力。
    • 关键工具：
      • cpuunclaimed：检查 CPU 利用率是否均衡，是否有“空闲”的 CPU 周期因为调度问题而未被使用。
      • runqlat：测量任务在运行队列中等待被调度的时间。如果等待时间很长，说明 CPU 饱和。
      • offcputime：追踪进程在 Off-CPU（即不在运行）状态的时间，并生成火焰图。专门用于分析阻塞和等待问题。
      • execsnoop：追踪短命的进程。这些进程在 top 中很难捕捉，但可能会引起频繁的 CPU 峰值。

5. 高级技巧与注意事项 ​

  1. 理解 CPU 拓扑：了解物理 CPU、核心、超线程。使用 lscpu 查看。
  2. 性能剖析的开销：perf 和 eBPF 工具通常开销很低（<5%），但在生产环境仍需谨慎。perf 采样频率不宜过高。
  3. 符号表：为了 perf 和 eBPF 工具能显示函数名而不是内存地址，需要确保应用程序和系统库都带有调试符号（-g 编译）。对于生产环境，可以单独安装 -dbgsym 包或使用 perf inject。
  4. 容器环境：在容器内，视野受限。通常需要在宿主机上使用 perf 或 eBPF 工具，并通过 -p 指定容器内进程在宿主机上的 PID 来进行分析。
  5. 火焰图是朋友：
    • On-CPU 火焰图：回答“CPU 时间花在哪里了？”
    • Off-CPU 火焰图：回答“进程在等待什么？”
    • 差分火焰图：比较两个性能剖面，快速找到回归点。

6. 总结 ​

CPU 性能分析是一个系统性工程：

  1. 从不加区分的测量开始：使用 top, vmstat 获取宏观状态。
  2. 提出假设：是高用户态？高系统态？还是高 I/O 等待？
  3. 使用专项工具验证：
    • On-CPU 问题 -> perf (火焰图)
    • Off-CPU 问题 -> offcputime (Off-CPU 火焰图)
    • 调度/切换问题 -> pidstat -w, runqlat
    • 短时进程问题 -> execsnoop
  4. 定位到代码行：通过工具输出的调用栈和火焰图，定位到消耗资源的具体函数和代码逻辑。
  5. 优化并重复测试：修复问题后，重复上述流程以验证优化效果。

这份笔记涵盖了从理论到实践的核心知识。熟练掌握这些概念和工具，将使你能够系统地分析和解决绝大多数 CPU 相关的性能瓶颈。

XXL-JOB 完整学习文档 ​

一、概述 ​

1. 什么是 XXL-JOB？ ​

XXL-JOB 是一个分布式任务调度平台，其核心设计目标是开发迅速、学习简单、轻量级、易扩展。现已开放源代码并接入多家公司线上产品线，开箱即用。

简单来说，当我们的系统从单体架构升级到分布式、微服务架构后，原本单机上的定时任务（如 Linux Cron、Spring @Scheduled）会面临任务重复执行、无法统一管理、无法动态配置等问题。XXL-JOB 就是为了解决这些问题而生的。

2. 为什么选择 XXL-JOB？ ​

传统方案的痛点XXL-JOB 的解决方案
Linux Cron / @Scheduled：只能单机执行，无法分布式支持执行器集群部署，任务分布式执行
任务无法统一管理、无法动态配置提供 Web 可视化界面，页面修改 Cron 表达式无需重启
Quartz：功能强但配置复杂，运维难度大轻量级、开箱即用，学习成本低
无法水平扩展支持任务分片广播，动态扩容

XXL-JOB 基于 “中心化配置、分布式执行” 的设计理念，采用调度中心与执行器分离的核心架构。

二、核心架构 ​

1. 设计思想 ​

XXL-JOB 的核心设计思想是将“调度”与“任务”解耦：

  • 调度行为抽象成“调度中心”公共平台，调度中心自身不承担业务逻辑，只负责发起调度请求。
  • 任务逻辑抽象成分散的 JobHandler，交由“执行器”统一管理。

这样，调度和任务两部分相互解耦，提高了系统的稳定性和可扩展性。

2. 系统组成 ​

┌─────────────────────────────────────────────────────┐
│              调度中心（Admin）                      │
│  • Web 管理界面（任务配置、Cron编辑、日志查看）     │
│  • 发起调度指令（RPC 调用执行器）                  │
│  • 支持集群部署，通过 DB 锁保证单点调度             │
└─────────────────────────────────────────────────────┘
                        ↓ RPC 调用
┌─────────────────────────────────────────────────────┐
│              执行器（Executor）                     │
│  • 部署在业务服务器上                              │
│  • 接收调度指令，执行实际任务逻辑                   │
│  • 启动时自动注册到调度中心                        │
│  • 每个执行器有唯一的 appname                      │
└─────────────────────────────────────────────────────┘

调度中心（Admin） ：

  • 负责管理调度信息，按照调度配置发出调度请求
  • 支持可视化、动态管理调度信息（新建、更新、删除任务）
  • 支持监控调度结果和执行日志
  • 支持执行器故障转移（Failover）

执行器（Executor） ：

  • 负责接收调度请求并执行任务逻辑
  • 专注于任务的执行操作，开发和维护更加简单高效
  • 接收调度中心的执行请求、终止请求和日志请求

三、核心概念详解 ​

1. 调度中心 vs 执行器 ​

关键理解：调度中心只是“发号施令”，真正干活的是执行器。可以把调度中心理解为指挥官，执行器是士兵。

2. 运行模式：BEAN 模式 vs GLUE 模式 ​

对比维度BEAN 模式GLUE 模式
代码位置代码写在执行器项目中，打包部署代码写在调度中心网页文本框里
修改方式修改后需重新编译、打包、重启执行器在线修改，即时生效，无需重启
适用场景常规业务开发（95% 场景用这个）临时跑数、热修复、快速验证
支持语言Java（Spring Bean）Java_Groovy、Shell、Python、PHP、NodeJs

BEAN 模式代码示例：

java
@Component
public class SampleXxlJob {
    
    @XxlJob("demoJobHandler")
    public void demoJobHandler() {
        XxlJobHelper.log("XXL-JOB, Hello World.");
        // 业务逻辑...
    }
}

执行器启动时，会通过 @XxlJob 注解识别 Spring 容器中的“Bean模式任务”，以注解的 value 属性为 key 管理起来。

3. JobHandler ​

JobHandler 就是任务方法上 @XxlJob 注解中填写的名称。调度中心配置任务时填的 JobHandler，就是要找这个门牌号，找到了就执行里面的代码。

4. 执行器注册 ​

执行器注册主要有两种方式：

  1. 自动注册（推荐）：执行器启动时自动将 AppName 和机器地址注册到调度中心
  2. 手动录入：在调度中心手动录入执行器名称和机器地址

调度中心通过检查 xxl_job_registry 表中是否存在90秒内未更新的注册信息来判断执行器是否在线。

四、调度数据库表结构 ​

XXL-JOB 需要数据库来存储任务信息和执行器信息，核心表包括：

表名用途
xxl_job_lock任务调度锁表，集群模式下保证同一时间只有一个实例触发任务
xxl_job_group执行器信息表，维护任务执行器信息
xxl_job_info调度扩展信息表，保存任务分组、任务名、执行器、执行入参等
xxl_job_log调度日志表，保存调度结果、执行结果等历史信息
xxl_job_log_report调度日志报表，供报表功能使用
xxl_job_logglue任务 GLUE 日志，支持 GLUE 版本回溯
xxl_job_registry执行器注册表，维护在线的执行器地址
xxl_job_user系统用户表

五、路由策略 ​

执行器集群部署时，XXL-JOB 提供了丰富的路由策略，决定每次调度由哪台机器执行任务。

路由策略说明适用场景
第一个 / 最后一个固定选择集群中的第一台或最后一台机器指定特定机器执行
轮询类似负载均衡，每次选择不同的机器常规任务，均衡负载
随机随机选择一台机器常规任务
一致性 HASH根据 JobId 进行 HASH 计算，相同任务始终落到同一台机器有状态任务
最不经常使用（LFU）选择使用频率最低的机器负载均衡优化
最近最久未使用（LRU）选择最久未使用的机器负载均衡优化
故障转移按顺序进行心跳检测，第一个成功的机器执行高可用场景
忙碌转移检测机器是否忙碌，选择空闲机器避免任务堆积
分片广播广播触发集群中所有机器执行一次任务大数据量并行处理

1. 分片广播（重点） ​

当路由策略选择“分片广播”时，一次任务调度会广播触发集群中所有执行器执行一次任务，同时系统自动传递分片参数。

分片参数：

java
int shardIndex = XxlJobHelper.getShardIndex();  // 当前执行器序号（从0开始）
int shardTotal = XxlJobHelper.getShardTotal();  // 执行器集群总机器数

使用场景：假如有 10 万条数据要处理，集群有 10 台执行器，使用分片广播后每台机器只需处理 1 万条数据，耗时降低 10 倍。

代码示例：

java
@XxlJob("shardingJobHandler")
public void shardingJobHandler() {
    int shardIndex = XxlJobHelper.getShardIndex();
    int shardTotal = XxlJobHelper.getShardTotal();
    
    // 从数据库查询所有待处理数据
    List<Long> ids = service.getPendingIds();
    
    for (Long id : ids) {
        // 取模运算：只有属于自己的分片才处理
        if (id % shardTotal == shardIndex) {
            process(id);
        }
    }
}

如果其中一台机器故障，不影响其他执行器继续执行。

六、阻塞处理策略 ​

当任务执行时间较长，调度频率过于密集时，执行器可能因上次任务未完成而来不及处理本次调度。阻塞处理策略决定此时的行为：

策略说明
单机串行（默认）请求入队列排队，等前面的执行完后依次执行
丢弃后续调度如果当前有任务正在执行，后续请求直接标记失败，不执行
覆盖之前调度终止正在执行的任务，用新任务覆盖

七、触发策略 ​

XXL-JOB 支持多种触发方式：

  • Cron 触发：基于 Cron 表达式定时触发
  • 固定间隔触发：按固定时间间隔触发
  • 固定延时触发：固定延时后触发
  • API 事件触发：通过 API 接口手动触发
  • 人工触发：在管理界面点击“执行”按钮
  • 父子任务触发：任务执行完成后触发子任务

八、快速上手 ​

1. 下载源码 ​

bash
git clone https://github.com/xuxueli/xxl-job.git

源码目录结构：

xxl-job/
├── doc/                    # 文档资料
│   └── db/                 # 调度数据库建表脚本
├── xxl-job-admin/          # 调度中心（Spring Boot 项目）
├── xxl-job-core/           # 公共 jar 包依赖
└── xxl-job-executor-samples/ # 执行器示例项目

2. 初始化数据库 ​

执行 doc/db/tables_xxl_job.sql 脚本，创建调度数据库。

3. 配置并启动调度中心 ​

修改 xxl-job-admin 的 application.properties：

properties
# 数据库连接
spring.datasource.url=jdbc:mysql://127.0.0.1:3306/xxl_job
spring.datasource.username=root
spring.datasource.password=123456

# 访问 Token（执行器需保持一致）
xxl.job.accessToken=default_token

启动调度中心，访问 http://localhost:8080/xxl-job-admin 即可看到管理界面。

4. 配置并启动执行器 ​

修改执行器示例的 application.properties：

properties
# 调度中心地址（执行器向此地址注册）
xxl.job.admin.addresses=http://localhost:8080/xxl-job-admin

# 执行器 AppName（与调度中心配置一致）
xxl.job.executor.appname=xxl-job-executor-sample

# 执行器端口（RPC 通信端口，默认 9999）
xxl.job.executor.port=9999

启动执行器，它会自动注册到调度中心。

XXL-JOB 通过“调度中心”与“执行器”分离的架构设计，实现了调度与任务的解耦，是一个功能强大、易于使用的分布式任务调度平台。

十二、完整流程 ​

  1. 服务注册：执行器启动时，根据 AppName 将自身 IP 和端口注册到数据库 xxl_job_registry 表，并每 30 秒发送心跳续约。调度中心的后台线程（JobRegistryMonitorHelper）会扫描该表，90 秒未收到心跳则自动摘除节点，实现集群节点的动态感知。

  2. 抢锁：调度中心集群的所有节点通过数据库 xxl_job_lock 表的数据库行锁（悲观锁）（SELECT ... FOR UPDATE） 来抢占调度令牌。只有抢到锁的 Leader 节点才能执行调度，且锁只保护“毫秒级”的扫库+放入内存过程，一旦任务被加载进时间轮，事务立即提交释放锁，避免长时占用。

  3. 预加载到时间轮： 在抢到锁的事务内，Leader 节点的 scheduleThread 线程（每秒自旋对齐整秒边界）扫描 xxl_job_info 表，通过 trigger_next_time <= 当前时间 + 预读毫秒数（默认 5 秒） 条件，找出即将触发的任务列表，并按执行秒数（0~59）放入本机内存的时间轮（ConcurrentMap<Integer, List<Integer>>）中。随后释放锁，其他节点可竞争下一轮扫库。

  4. 轮询触发： Leader 节点的触发线程ringThread，定期拨动时间轮指针（默认每秒一次，自旋对齐整秒边界），取出当前秒数格子的所有任务，提交给异步线程池进行触发。避免了高频扫库（秒级任务）带来的性能瓶颈。

  5. 路由与分片执行：调度中心根据配置的路由策略（轮询、随机、一致性HASH、故障转移、忙碌转移、分片广播等）选定执行器节点，通过 HTTP 协议发起触发请求。若是分片广播模式，会向该 AppName 下的所有执行器节点发送请求，并传递 总分片数 和 当前分片序号，各节点并行处理属于自己的数据子集，从而实现水平扩展。

  6. 执行与结果回调：执行器收到请求后，由 JobThread 线程池执行，并支持配置阻塞处理策略。执行完毕后，通过 HTTP 异步回调调度中心的 /callback 接口上报结果。调度中心更新 xxl_job_log 日志和 xxl_job_info 的 trigger_last_time/trigger_next_time，完成一次完整的调度闭环。

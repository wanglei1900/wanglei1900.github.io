事件溯源 - 快照机制学习笔记 ​

🎯 快照机制的核心概念 ​

为什么需要快照？ ​

在纯事件溯源系统中，重建聚合状态需要重放所有历史事件：

  • 性能问题：事件数量庞大时，重建时间线性增长
  • 资源消耗：频繁的全量重放浪费计算资源
  • 用户体验：响应时间变长，影响系统可用性

快照机制通过在特定时间点保存聚合的完整状态，解决了这些问题。

🏗️ 快照机制架构 ​

mermaid
graph TB
    A[命令请求] --> B[聚合加载]
    B --> C{检查快照是否存在}
    C -->|存在| D[从快照恢复状态]
    C -->|不存在| E[从事件流重建]
    D --> F[重放快照后的事件]
    E --> G[处理新命令]
    F --> G
    G --> H[生成新事件]
    H --> I[保存事件到事件存储]
    I --> J{满足快照条件?}
    J -->|是| K[创建快照]
    J -->|否| L[完成]
    K --> L
    
    M[快照存储] --> D
    N[事件存储] --> E
    N --> F

📝 快照触发策略 ​

1. 基于事件数量的快照 ​

javascript
class SnapshotPolicy {
    constructor(threshold = 100) {
        this.threshold = threshold;
    }
    
    shouldTakeSnapshot(aggregate, newEvents) {
        return aggregate.version >= this.threshold &&
               aggregate.version % this.threshold === 0;
    }
}

2. 基于时间的快照 ​

javascript
class TimeBasedSnapshotPolicy {
    constructor(intervalMinutes = 60) {
        this.interval = intervalMinutes * 60 * 1000;
        this.lastSnapshotTime = new Map();
    }
    
    shouldTakeSnapshot(aggregateId) {
        const now = Date.now();
        const lastTime = this.lastSnapshotTime.get(aggregateId) || 0;
        
        if (now - lastTime >= this.interval) {
            this.lastSnapshotTime.set(aggregateId, now);
            return true;
        }
        return false;
    }
}

class BusinessRuleSnapshotPolicy {

3. 聚合加载器（含快照） ​

java
public class SnapshotAwareAggregateLoader {
    private final EventStore eventStore;
    private final SnapshotRepository snapshotRepository;
    
    public <T extends AggregateRoot> T load(Class<T> aggregateClass, String aggregateId) {
        // 1. 尝试加载最新快照
        Optional<AggregateSnapshot> snapshot = 
            snapshotRepository.getLatestSnapshot(aggregateId);
            
        long startVersion = 0;
        T aggregate = createAggregateInstance(aggregateClass, aggregateId);
        
        if (snapshot.isPresent()) {
            AggregateSnapshot snap = snapshot.get();
            aggregate.loadFromSnapshot(snap);
            startVersion = snap.getVersion() + 1;
        }
        
        // 2. 加载快照后的事件
        List<DomainEvent> events = eventStore.getEventsAfterVersion(
            aggregateId, startVersion);
            
        // 3. 重放事件
        aggregate.loadFromHistory(events);
        
        return aggregate;
    }
}

💾 存储策略 ​

1. 快照存储位置选择 ​

存储类型优点缺点适用场景
同一事件存储一致性保证，简化架构可能影响事件查询性能中小型系统
独立数据库性能优化，存储分离需要处理分布式事务大型系统
内存缓存极快读取速度数据易失，需要持久化备份高频访问聚合
文件系统存储成本低查询复杂，性能一般归档，大数据量

public enum SnapshotSerializationFormat {

            return objectMapper.writeValueAsBytes(state);

⚙️ 快照管理策略 ​

1. 快照清理策略 ​

java
public class SnapshotCleanupStrategy {
    // 保留最新N个快照
    public void keepLatestSnapshots(String aggregateId, int keepCount) {
        List<AggregateSnapshot> snapshots = 
            snapshotRepository.getSnapshots(aggregateId);
            
        if (snapshots.size() > keepCount) {
            snapshots.stream()
                .sorted(Comparator.comparingLong(AggregateSnapshot::getVersion))
                .limit(snapshots.size() - keepCount)
                .forEach(snapshot -> 
                    snapshotRepository.deleteSnapshot(snapshot.getId()));
        }
    }
    
    // 基于时间的清理
    public void cleanupOldSnapshots(Duration maxAge) {
        Instant cutoff = Instant.now().minus(maxAge);
        snapshotRepository.deleteSnapshotsOlderThan(cutoff);
    }
}

2. 快照压缩 ​

java
public class SnapshotCompressor {
    public CompressedSnapshot compress(AggregateSnapshot snapshot) {
        byte[] serializedData = serializeSnapshot(snapshot);
        byte[] compressedData = compressData(serializedData);
        
        return new CompressedSnapshot(
            snapshot.getAggregateId(),
            snapshot.getVersion(),
            compressedData,
            getCompressionRatio(serializedData, compressedData)
        );
    }
    
    private byte[] compressData(byte[] data) {
        // 使用 GZIP、LZ4 等压缩算法
        try (ByteArrayOutputStream bos = new ByteArrayOutputStream();
             GZIPOutputStream gzip = new GZIPOutputStream(bos)) {
            gzip.write(data);
            gzip.finish();
            return bos.toByteArray();
        }
    }
}

1. 延迟快照创建 ​

public class LazySnapshotStrategy {
    private final ThreadPoolExecutor snapshotExecutor;
    private final Queue<SnapshotTask> pendingSnapshots = new ConcurrentLinkedQueue<>();
    
    public void scheduleSnapshot(AggregateSnapshot snapshot) {
        // 异步创建快照，不阻塞命令处理
        snapshotExecutor.submit(() -> {
            try {
                snapshotRepository.saveSnapshot(snapshot);
            } catch (Exception e) {
                // 记录错误但不影响主流程
                logger.error("Failed to create snapshot", e);
            }
        });
    }
}

2. 健康检查 ​

java
@Component
public class SnapshotHealthIndicator implements HealthIndicator {
    private final SnapshotRepository snapshotRepository;
    
    @Override
    public Health health() {
        try {
            // 检查存储可用性
            snapshotRepository.healthCheck();
            
            // 检查存储空间
            long usedSpace = snapshotRepository.getUsedSpace();
            long totalSpace = snapshotRepository.getTotalSpace();
            double usageRatio = (double) usedSpace / totalSpace;
            
            Health.Builder status = usageRatio > 0.9 ? Health.down() : Health.up();
            return status
                .withDetail("usedSpace", usedSpace)
                .withDetail("totalSpace", totalSpace)
                .withDetail("usageRatio", usageRatio)
                .build();
                
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}

🛡️ 容错与恢复 ​

1. 快照损坏处理 ​

java
public class SnapshotRecoveryStrategy {
    public boolean validateSnapshot(AggregateSnapshot snapshot) {
        try {
            // 校验checksum
            String calculatedChecksum = calculateChecksum(snapshot.getData());
            return calculatedChecksum.equals(snapshot.getChecksum());
        } catch (Exception e) {
            return false;
        }
    }
    
    public RecoveryResult recoverFromCorruptedSnapshot(String aggregateId) {
        // 1. 找到最后一个完好的快照
        Optional<AggregateSnapshot> lastGoodSnapshot = 
            findLastValidSnapshot(aggregateId);
            
        if (lastGoodSnapshot.isPresent()) {
            // 2. 从完好快照重建
            return rebuildFromSnapshot(lastGoodSnapshot.get());
        } else {
            // 3. 回退到全事件重放
            return rebuildFromEvents(aggregateId);
        }
    }
}

2. 快照回滚策略 ​

java
public class SnapshotRollbackStrategy {
    public void rollbackToVersion(String aggregateId, long targetVersion) {
        // 1. 删除目标版本后的快照
        snapshotRepository.deleteSnapshotsAfterVersion(aggregateId, targetVersion);
        
        // 2. 从保留的快照重建
        Optional<AggregateSnapshot> snapshot = 
            snapshotRepository.getLatestSnapshot(aggregateId);
            
        if (snapshot.isPresent() && snapshot.get().getVersion() <= targetVersion) {
            // 使用现有快照
            return;
        }
        
        // 3. 如果没有合适的快照，需要重新创建
        createSnapshotAtVersion(aggregateId, targetVersion);
    }
}

📊 最佳实践总结 ​

✅ 推荐做法 ​

  1. 选择合适的快照频率：平衡存储成本与性能收益
  2. 监控快照效果：定期评估快照带来的性能提升
  3. 实施版本兼容：快照格式需要向前兼容
  4. 测试恢复流程：定期验证从快照恢复的正确性

❌ 避免的做法 ​

  1. 过度快照：避免创建过多快照浪费资源
  2. 忽略验证：不验证快照完整性可能导致数据损坏
  3. 单点故障：快照存储不应成为系统单点
  4. 忽略清理：不定期清理会导致存储膨胀

快照机制是事件溯源系统中至关重要的性能优化手段，合理设计和实施快照策略可以显著提升系统性能，同时保持事件溯源的核心优势。

事件溯源与事件存储架构模式完整学习笔记 ​

1. 核心概念 ​

1.1 什么是事件溯源？ ​

事件溯源是一种架构模式，它不存储数据的当前状态，而是将应用程序状态的所有变化捕获为一系列不可变的事件，并按时间顺序持久化在事件存储中。通过按顺序重放这些事件，可以重新构建出数据的任何历史状态以及当前状态。

  • 核心思想：事件是事实的源头。当前状态是事件流推导出的结果，而非权威数据源。
  • 关键规则：
    1. 事件是不可变的，一旦发生就无法被更改或删除。
    2. 事件描述的是过去已经发生的事情，通常使用过去时态命名，例如 OrderPlaced， UserCreated。
    3. 理论上，在任意时间点，你都可以删除当前状态并通过重新处理全部事件来重建整个系统。

1.2 什么是事件存储？ ​

事件存储是事件溯源模式中的专用存储机制，它是一个持久化的事件日志，充当系统的"单一事实来源"。

它不仅仅是数据库，还兼具了消息代理的功能。所有导致状态变化的事件都被顺序追加到事件存储中，并且通常这些事件会被发布给感兴趣的消费者。

2. 工作原理与核心架构 ​

2.1 基本工作流程 ​

事件溯源的基本工作流程涉及命令、聚合和事件的交互，最终通过重放事件来重建状态，其核心数据流可以通过下图展示：

mermaid
flowchart TD
    A[用户命令<br>e.g. 创建订单] --> B(命令处理器)
    B --> C[聚合<br>Aggregate Root]
    C --> D{验证命令并生成<br>领域事件<br>e.g. OrderCreated}
    D --> E[事件存储<br>Event Store]
    E --> F[持久化事件<br>到事件流]
    F --> G[发布新事件]
    G --> H[事件处理器]
    H --> I[重放事件<br>重建状态]
    H --> J[更新查询模型<br>CQRS]
    H --> K[调用外部系统]

流程步骤解读：

  1. 命令处理：用户或外部系统发送一个命令（如"创建订单"）到命令处理器。
  2. 生成事件：命令处理器加载相应的聚合，聚合根据业务逻辑验证命令的有效性。如果有效，聚合会生成一个或多个表示状态变更的领域事件（如 OrderCreated），这些事件包含了变更的所有必要信息。
  3. 持久化事件：生成的事件被持久化到事件存储中，追加到该聚合特定的事件流里。
  4. 发布与处理事件：事件存储发布新事件。各类事件处理器订阅这些事件并执行相应的操作，例如：
    • 重建聚合状态：通过从头到尾重放该聚合的所有事件，重新计算出聚合的当前状态。
    • 更新查询模型：在CQRS架构中，更新为查询优化的物化视图。
    • 通知外部系统：触发与其他微服务的集成。

2.2 事件存储的核心组件 ​

一个完整的事件存储系统通常包含以下核心组件：

组件职责描述
事件(Event)系统状态更改的永久记录，包含描述状态变化所需的所有数据。
事件存储(Event Store)持久化保存事件序列的数据库或日志，保证事件顺序。
聚合(Aggregate)一组相关领域对象的逻辑集合，作为处理命令和生成事件的单元。每个聚合拥有独立的事件流。
命令(Command)表示执行某个操作的请求，由聚合处理并可能触发事件的生成。
投影(Projection)从事件流创建的读取模型，用于高效展示系统当前状态，支持查询。

3. 关键实现机制 ​

3.1 处理并发：乐观锁 ​

当多个命令试图同时更新同一个聚合时，需要使用并发控制机制。事件溯源通常采用乐观锁。

  • 工作原理：每个聚合都有一个版本号（通常随每个事件递增）。当保存新事件时，系统会检查事件存储中的聚合版本是否与命令加载时的版本一致。只有一致时，更新才会成功；否则，操作将被拒绝，需要客户端重试。
  • 好处：在高并发场景下，避免了传统悲观锁的性能瓶颈。

3.2 提升性能：快照 ​

对于生命周期很长、事件数量庞大的聚合，每次重建状态都需要重放成百上千个事件，这会严重影响性能。

  • 快照机制：系统定期（例如，每100个事件）将聚合在某个时间点的完整状态持久化保存为一个快照。
  • 状态恢复：当需要加载聚合时，系统首先加载最新的快照，然后仅重放该快照之后发生的事件。这极大地减少了需要处理的事件数量，显著提升了性能。

3.3 保证消息处理的幂等性 ​

在分布式系统中，消息可能被重复传递。事件溯源系统必须能够幂等地处理消息，即多次处理同一消息与处理一次产生的结果相同。

  • 实现方案：
    • 关系型数据库：在同一个事务中，将事件和接收到的消息ID一起插入数据库。在处理新消息前，先检查该消息ID是否已存在。
    • 非关系型数据库：将处理消息时生成的消息ID存储在事件本身中。在更新聚合前，通过检查聚合事件历史中是否已包含该消息ID来进行重复检测。

3.4 处理事件结构的演化 ​

随着业务发展，事件的结构难免需要调整。如何管理不同版本的事件，保证系统的向后兼容性是一个挑战。

  • 向后兼容的更改：例如，添加新字段通常不会破坏现有系统，因为旧的消费者可以忽略新字段。
  • 不兼容的更改：例如，重命名字段或改变字段含义。解决方案包括：
    • 向上转换：在从事件存储加载旧版本事件时，编写转换器将其升级为新版本的结构。
    • 事件版本号：为每个事件类型添加版本号，以便在加载时识别并执行相应的转换逻辑。

4. 与其他模式的关系 ​

4.1 与CQRS的紧密结合 ​

命令查询职责分离（CQRS）模式与事件溯源是天然互补的，通常一起使用。

下图清晰地展示了两者如何协同工作：

mermaid
flowchart LR
    subgraph C [命令端 Write Side]
        A[命令] --> B[聚合]
        B --> C[事件存储]
    end

    subgraph Q [查询端 Read Side]
        C -- 事件流 --> D[投影<br>Projection]
        D --> E[查询模型<br>Read Model]
        E --> F[查询]
    end

    C ~~~ Q

协作方式：

  • 命令端：负责处理写操作。它接收命令，通过聚合进行验证并生成事件，然后将事件持久化到事件存储中。这部分是事件溯源的核心。
  • 查询端：负责处理读操作。它订阅事件存储中的事件流，通过投影处理这些事件，更新一个或多个为查询量身定制的查询模型（物化视图）。查询模型可以与写模型完全不同，并且针对读性能进行了优化。

优势：

  • 读写分离：允许独立地扩展和处理读写负载。
  • 技术栈自由：可以为命令端和查询端选择最合适的数据库和技术。

4.2 在Saga模式中的应用 ​

在微服务架构中，Saga模式用于管理跨多个服务的分布式事务。事件溯源可以很好地与Saga结合。

  • 协同式Saga：利用事件溯源天然的事件驱动特性，可以让不同聚合的事件处理程序订阅事件并更新各自的聚合，从而简化协同式Saga的实现。
  • 编排式Saga：Saga编排器本身也可以使用事件溯源来实现，将其状态的变化（如"Saga已创建"、"Saga已更新"）持久化为一系列事件，从而可靠地管理Saga的生命周期。

5. 优势与挑战 ​

5.1 优势 ​

  1. 完整的审计与合规性：自动记录了系统所有的状态变更，提供了不可篡改的审计日志。
  2. 时间旅行：可以重建系统在任意历史时间点的状态，用于调试、分析和数据回溯。
  3. 可靠的领域事件发布：事件存储作为可靠的事件源，确保了领域事件能被准确无误地发布给所有消费者。
  4. 灵活的读写模型：与CQRS结合，可以创建高度优化的读模型，提升查询性能。
  5. 业务逻辑清晰化：事件序列清晰地反映了业务的真实发生过程，使领域模型更加直观。

5.2 挑战与应对策略 ​

挑战描述与应对策略
学习曲线思维方式与传统CRUD有较大差异，有一定学习成本。
查询复杂性直接查询事件存储来获取当前状态通常很困难。解决方案：与CQRS结合，维护专门的查询模型。
事件演化事件结构会随时间变化。解决方案：建立事件版本控制和管理策略（如向上转换）。
数据删除由于事件的不可变性，实现数据隐私条例要求的"被遗忘权"较为复杂。解决方案：可使用加密、假名化或标记事件为可忽略等技术。

6. 技术选型与实现 ​

6.1 事件存储的实现选项 ​

  1. 专用事件存储数据库：
    • EventStoreDB：专为事件溯源设计的数据库。
    • Axon Framework, Lagom, Eventuate：这些框架内置或提供了对事件溯源和CQRS的支持。
  2. 通用消息日志/流平台：
    • Apache Kafka：常被用作事件存储和事件总线，其持久化、分区、高可用的日志特性非常适合事件溯源。
  3. 自行构建：
    • 基于关系数据库或文档数据库构建，需要自行处理事件序列化、版本控制和发布等逻辑。

6.2 代码结构示例（以Java为例） ​

以下是一个简化的订单聚合示例，展示了命令处理和事件应用的核心逻辑：

java
// 定义事件
public class OrderCreatedEvent {
    private String orderId;
    private List<String> productIds;
    private String customerId;
    // ... getters, setters, constructor
}

public class PaymentMadeEvent {
    private String orderId;
    private BigDecimal amount;
    // ... getters, setters, constructor
}

// 聚合根
public class OrderAggregate {
    private String orderId;
    private List<String> productIds;
    private String customerId;
    private boolean paymentReceived;

    // 处理命令，生成事件
    public List<DomainEvent> createOrder(String orderId, List<String> productIds, String customerId) {
        // 验证逻辑...
        List<DomainEvent> events = new ArrayList<>();
        events.add(new OrderCreatedEvent(orderId, productIds, customerId));
        return events;
    }

    // 应用事件来更新状态
    public void apply(OrderCreatedEvent event) {
        this.orderId = event.getOrderId();
        this.productIds = event.getProductIds();
        this.customerId = event.getCustomerId();
        this.paymentReceived = false;
    }

    public void apply(PaymentMadeEvent event) {
        if (event.getOrderId().equals(this.orderId)) {
            this.paymentReceived = true;
        }
    }
}

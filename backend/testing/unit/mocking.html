理解了你在学习测试策略、单元测试和Mock技术时需要清晰的梳理。下面这份学习笔记整合了核心概念、实践方法和工具，应该能为你提供有力的支持。

测试策略、单元测试与Mock技术完整学习笔记 ​

1️⃣ 测试策略 ​

测试策略为我们的测试活动提供了总体性的指导和规划。

1.1 基本概念 ​

  • 定义：测试策略描述软件测试的整体方法，其首要目标是减少缺陷的出现和发布。
  • 与测试计划的关系：测试策略是更高层次的指导，测试计划则用于实施测试策略。在复杂系统中，仅有高层策略不够，还需思考测试架构。
  • 制定者：由团队各个角色共同制定，而非仅测试人员。

1.2 测试策略的核心内容 ​

一份测试策略通常需要明确以下几点：

  • 测试目标：明确测试要达成什么。
  • 测试范围与重点：确定"测什么"和重点难点。
  • 测试方法：确定"怎么测"，例如采用哪些测试类型（如功能、性能、安全测试等）和技术。
  • 测试深度与广度：明确测试的细致程度和范围覆盖。
  • 资源与时间安排：需要多少人、物、时间。
  • 准入和准出标准：明确何时开始测试，何时可结束测试。

1.3 流行的测试策略模型 ​

常见的测试策略模型有测试金字塔和测试象限，但需注意它们不具备直接可操作性，需根据项目实际情况定制。

1.3.1 测试金字塔 ​

1.4 制定测试策略的实用方法 ​

可以参考"四步测试策略制定法"：

  1. 分析测试需求：基于质量目标和产品风险。
  2. 确定测试重点与难点：使用风险分析检查清单。
  3. 确定测试深度与广度：参考产品质量评估模型。
  4. 平衡质量、效益与投入：目标是进行"刚刚好"的测试。

2️⃣ 单元测试 ​

单元测试是软件测试金字塔的基石。

2.1 单元测试概述 ​

  • 定义：对软件中的最小可测试单元（如函数、方法、类）进行检查和验证。
  • 目的：尽早发现代码缺陷，提升修复效率。
  • 测试内容：通常包括模块接口测试、局部数据结构测试、边界条件测试、独立执行通路测试和错误处理通路测试。

2.2 单元测试规则与结构 ​

以Go语言为例：

  • 文件名：所有测试文件以_test.go结尾。
  • 函数名：测试函数命名为func TestXxx(*testing.T)。
  • 测试初始化：初始化逻辑放到TestMain中。
go
// 示例：Go单元测试结构
func TestMain(m *testing.M) {
    // 测试前：数据配置和加载
    code := m.Run()
    // 测试后：资源释放等收尾工作
    os.Exit(code)
}

func TestCalculate(t *testing.T) {
    // 测试逻辑
    result := Calculate(2, 3)
    if result != 5 {
        t.Errorf("期望得到5, 但得到 %d", result)
    }
}

2.3 测试覆盖率 ​

  • 定义：被执行的代码行数占有效代码总行数的比例。
  • 要求：
    • 基本要求：50% ~ 60%
    • 较高要求：80%+（较重要的项目）
  • 提示：
    • 测试分支应相互独立，全面覆盖
    • 函数尽量写的小一点，更容易覆盖

2.4 单元测试中的依赖问题 ​

单元测试应快速运行且结果稳定。但当代码依赖外部资源（数据库、网络、文件等）时，直接测试会遇到问题：

  • 速度慢：实际外部操作（如数据库查询）比内存操作慢得多。
  • 结果不稳定：网络波动、数据状态变化可能导致测试时而过、时而失败。
  • 环境依赖：缺乏特定环境（如测试数据库）时无法运行测试。

解决方案：使用Mock技术模拟这些依赖。

3️⃣ Mock技术 ​

3.1 Mock的概念 ​

  • 核心思想：用模拟对象替换真实依赖，使测试聚焦于当前单元，隔离外部影响。
  • 优势：
    • 测试更快：避免真实外部调用。
    • 结果稳定：模拟行为可控，结果可预测。
    • 模拟复杂场景：可轻松模拟异常、超时等难以真实构造的场景。

3.2 Mock的实现方式与工具 ​

3.2.1 前端Mock：Mock.js ​

  • 作用：拦截前端Ajax请求，生成随机模拟数据。
  • 基本原理：通过重写XMLHttpRequest对象，使用代理模式拦截请求。
  • 示例语法：
javascript
// Mock.js 数据模板
Mock.mock({
    'list|1-10': [{ // 随机生成1到10个数组元素
        'id|+1': 1,    // 属性值自动加1
        'name': '@cname',  // 随机中文名字
        'email': '@email'  // 随机邮箱
    }]
})
  • 应用场景：
    • 前后端并行开发
    • 原型演示
    • 测试前端健壮性（如生成特殊长度字符串、null/undefined等）

3.2.2 后端Mock：Mockito / PowerMock ​

Mockito（Java）：

  • 用于模拟接口/类对象，验证交互行为。
  • 示例：
java
// 使用Mockito模拟依赖
UserRepository mockRepo = Mockito.mock(UserRepository.class);
Mockito.when(mockRepo.findById(1L)).thenReturn(new User("John"));
UserService userService = new UserService(mockRepo);
User user = userService.getUserById(1L);
Assert.assertEquals("John", user.getName());

PowerMock（Java）：

  • 扩展了Mockito，能Mock 静态方法、final类/方法、私有方法等。
  • 示例：
java
// 使用PowerMock模拟静态方法
@RunWith(PowerMockRunner.class)
@PrepareForTest({StaticUtility.class})
public class TestClass {
    @Test
    public void testStaticMethod() {
        PowerMockito.mockStatic(StaticUtility.class);
        PowerMockito.when(StaticUtility.getConfig()).thenReturn("mock-config");
        // 测试逻辑
    }
}

3.2.3 单元测试中的Mock：monkey ​

  • Go语言的monkey库可用于函数打桩，替换原函数执行。
  • 示例：
go
// 使用monkey进行函数打桩
monkey.Patch(OriginalFunction, MockedFunction)
defer monkey.Unpatch(OriginalFunction)
// 执行测试逻辑

3.3 Mock的原则与最佳实践 ​

  1. 适度使用：不要过度Mock，否则测试会与实现耦合过紧。
  2. 聚焦单元：只Mock当前单元的直接依赖。
  3. 模拟行为，而非数据：关注对象如何交互，而不仅仅是返回数据。
  4. 及时重构：当测试因Mock变得复杂时，考虑重构被测试代码（如提取接口、依赖注入）。

4️⃣ 测试策略与测试架构 ​

随着系统复杂度提升（微服务、物联网、大数据、AI等），简单应用测试策略模型可能不够，需要以软件系统架构的思维去思考整个测试体系，形成测试架构。

4.1 测试架构的核心关注点 ​

  • 理清测试间联系：将各个维度上的测试有效联系起来。
  • 示例：前后端分离的Web系统
    • 各层（前端、后端API、第三方依赖、数据库）有自己的单元测试、集成测试。
    • 使用契约测试联通前端和后端API。
    • 使用Stub处理第三方依赖系统的契约测试或监控测试。
    • 使用测试数据生成工具准备测试数据。

4.2 测试策略的调整 ​

测试策略和测试架构需根据项目的软件架构、技术栈、业务需求、人员技能等因素定制。在版本执行时，还需根据当前版本质量评估情况，更新策略以达到产品交付质量目标。

这份笔记涵盖了从高层测试策略到底层Mock技术的核心知识。实际应用中，记得根据具体项目上下文灵活调整和裁剪。扎实的测试策略、充分的单元测试和恰当的Mock技术，是构建高质量软件的重要保障。

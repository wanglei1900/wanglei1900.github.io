🏗️ 服务与架构 ​

架构演进 ​

单体架构 → SOA → 微服务 → 云原生 → 服务网格

微服务架构 ​

组件职责常用技术
API网关路由、认证、限流Kong, Spring Cloud Gateway
服务注册发现服务治理Eureka, Consul, Nacos
配置中心统一配置管理Apollo, Nacos, Config
服务调用服务间通信Feign, RestTemplate, gRPC
熔断降级故障隔离Hystrix, Sentinel, Resilience4j

核心特性 ​

  • 服务自治：独立开发、部署、扩展
  • 单一职责：每个服务专注特定业务能力
  • 去中心化治理：技术栈灵活选择
  • 容错设计：快速失败，优雅降级

⚖️ 开发原则 ​

SOLID 原则 ​

原则描述示例
SRP 单一职责一个类只负责一个功能领域用户管理类只处理用户相关逻辑
OCP 开闭原则对扩展开放，对修改关闭使用策略模式替代if-else
LSP 里氏替换子类必须能替换父类正方形不是长方形的子类
ISP 接口隔离多个专用接口优于一个通用接口分离读写接口
DIP 依赖倒置依赖抽象而非具体实现依赖接口而非具体类

其他重要原则 ​

🎨 设计模式 ​

创建型模式 ​

java
// 1. 单例模式
public class DatabaseConnection {
    private static volatile DatabaseConnection instance;
    
    private DatabaseConnection() {}
    
    public static DatabaseConnection getInstance() {
        if (instance == null) {
            synchronized (DatabaseConnection.class) {
                if (instance == null) {
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance;
    }
}

// 2. 工厂模式
public interface Notification {
    void send();
}

public class EmailNotification implements Notification {
    @Override
    public void send() {
        System.out.println("发送邮件通知");
    }
}

public class NotificationFactory {
    public static Notification createNotification(String type) {
        switch (type) {
            case "email": return new EmailNotification();
            case "sms": return new SmsNotification();
            default: throw new IllegalArgumentException("未知通知类型");
        }
    }
}

结构型模式 ​

java
// 1. 适配器模式
public interface ModernInterface {
    void modernMethod();
}

public class LegacyClass {
    public void legacyMethod() {
        System.out.println("老方法");
    }
}

public class Adapter implements ModernInterface {
    private LegacyClass legacy;
    
    public Adapter(LegacyClass legacy) {
        this.legacy = legacy;
    }
    
    @Override
    public void modernMethod() {
        legacy.legacyMethod();
    }
}

// 2. 装饰器模式
public interface Coffee {
    double getCost();
    String getDescription();
}

public class BasicCoffee implements Coffee {
    @Override
    public double getCost() { return 2.0; }
    
    @Override
    public String getDescription() { return "基础咖啡"; }
}

public abstract class CoffeeDecorator implements Coffee {
    protected Coffee decoratedCoffee;
    
    public CoffeeDecorator(Coffee coffee) {
        this.decoratedCoffee = coffee;
    }
}

行为型模式 ​

java
// 1. 策略模式
public interface PaymentStrategy {
    void pay(double amount);
}

public class CreditCardPayment implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        System.out.println("信用卡支付: " + amount);
    }
}

public class PaymentContext {
    private PaymentStrategy strategy;
    
    public void setStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }
    
    public void executePayment(double amount) {
        strategy.pay(amount);
    }
}

// 2. 观察者模式
public interface Observer {
    void update(String message);
}

public class ConcreteObserver implements Observer {
    @Override
    public void update(String message) {
        System.out.println("收到通知: " + message);
    }
}

public class Subject {
    private List<Observer> observers = new ArrayList<>();
    
    public void addObserver(Observer observer) {
        observers.add(observer);
    }
    
    public void notifyObservers(String message) {
        for (Observer observer : observers) {
            observer.update(message);
        }
    }
}

设计模式应用场景 ​

模式类型常用场景解决的问题
创建型对象创建复杂、需要控制实例解耦对象创建与使用
结构型需要组合类或对象形成更大结构类/对象之间的组织关系
行为型对象间的职责分配和通信对象间的交互和职责分配

⚠️ 反模式 ​

架构层面反模式 ​

java
// 1. 上帝对象 - 一个类承担太多职责
public class GodClass {
    public void processUser() { /* 处理用户 */ }
    public void calculateOrder() { /* 计算订单 */ }
    public void generateReport() { /* 生成报表 */ }
    public void sendNotification() { /* 发送通知 */ }
    // ... 更多不相关的方法
}

// 解决方案：拆分职责
public class UserService { /* 用户相关 */ }
public class OrderService { /* 订单相关 */ }
public class ReportService { /* 报表相关 */ }

代码层面反模式 ​

java
// 1. 霰弹式修改 - 修改一个功能需要改很多地方
// 坏例子：验证逻辑分散在各处
public class UserService {
    public void createUser(User user) {
        if (user.getEmail() == null) {
            throw new ValidationException("邮箱不能为空");
        }
        // ...
    }
}

public class OrderService {
    public void createOrder(Order order) {
        if (order.getUserEmail() == null) {
            throw new ValidationException("用户邮箱不能为空");
        }
        // ...
    }
}

// 好例子：集中验证
public class Validator {
    public static void validateEmail(String email) {
        if (email == null || !email.contains("@")) {
            throw new ValidationException("邮箱格式错误");
        }
    }
}

微服务反模式 ​

反模式问题解决方案
分布式单体服务间强耦合，失去微服务优势明确服务边界，独立部署
共享数据库服务间通过数据库耦合每个服务独享数据库
链式调用过长一个请求经过太多服务异步消息，合并服务
缺乏监控问题难以定位完善的日志和监控体系

团队协作反模式 ​

  • 知识孤岛：只有某人了解某块代码
  • 过度工程：为不存在的需求设计复杂方案
  • 复制粘贴编程：重复代码泛滥
  • 分析瘫痪：过度分析而迟迟不行动

💡 最佳实践总结 ​

架构设计 ​

  1. 选择合适的架构：根据团队规模和业务复杂度
  2. 渐进式演进：不要一开始就设计完美架构
  3. 自动化一切：CI/CD、监控、部署

代码质量 ​

  1. 持续重构：小步快跑，保持代码清洁
  2. 代码审查：多人协作，知识共享
  3. 测试驱动：测试保障，安全重构

团队协作 ​

  1. 统一规范：代码风格、提交信息、文档标准
  2. 知识共享：定期技术分享、文档沉淀
  3. 持续学习：跟踪技术发展，定期复盘

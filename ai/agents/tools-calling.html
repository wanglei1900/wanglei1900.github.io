Agent 工具调用（Tools Calling） ​

一、前言 ​

本笔记接续前两篇 Agent 概述与架构设计，聚焦于 AI Agent 工具调用（Tools Calling / Function Calling）这一核心能力模块。在 Agent 的四大核心特征中，工具调用能力被视为 Agent 区别于纯对话模型的最关键要素之一，正是通过调用外部工具，Agent 才得以跨越“只会说、不会做”的能力边界，成为真正意义上的行动实体。

随着 AI Agent 技术从“对话助手”向“数字员工”演进，工具调用已不再仅仅是“让大模型能调用一个天气 API”的简单功能，而是发展成为集协议标准化、动态发现、多工具编排、安全治理于一体的系统性工程。MCP（Model Context Protocol）作为 AI Agent 工具调用的“USB-C 接口”标准，在 2026 年迎来协议层的重大重构，标志着工具调用技术从“实验探索期”进入“工程成熟期”。

Gartner 于 2026 年 5 月发布的数据显示，企业级 AI 编程代理市场年化规模已达约 98 亿至 110 亿美元；Research and Markets 的测算数据则表明，自主智能体平台市场在 2025 年为 41.5 亿美元，2026 年预计增长至 53.2 亿美元（CAGR 28.3%），而更广义的 Agentic AI 工具市场更从 2025 年的 103.8 亿美元跃升至 2026 年的 161.8 亿美元（CAGR 55.9%）。工具调用作为 Agent 技术栈中的关键环节，正处于这一快速增长市场的核心位置。

本笔记将从工具调用的基本概念入手，逐层深入函数调用机制、规划架构中的工具调用策略、标准化协议体系、开发框架实现、安全治理，以及产业生态与未来展望，力求呈现一个完整的技术全貌。

二、工具调用的基本概念 ​

2.1 什么是工具调用 ​

工具调用（Tool Calling，也称 Function Calling）是指 AI 智能体通过结构化接口调用外部函数、API 或服务的能力，其核心本质是通过标准化指令将大语言模型的文本生成能力转化为工具操作能力，从而突破 LLM 的静态知识边界。

从概念上看，工具是赋予 LLM 的“外挂能力”——当模型需要某个数据或服务时，它以特定格式的消息响应，其中包含工具的名称和 JSON 参数。这种设计使得 LLM 不再是纯粹的文本生成器，而成为一个可以“主动请求执行具体操作”的智能控制器。

2.2 Agent 为什么需要工具调用 ​

在 AI Agent 系统中，单纯依赖基座模型面临诸多固有局限：模型本身无记忆（不能跨会话持久化信息）、不能执行代码、知识有截止日期、缺乏与现实世界系统交互的能力。工具调用正是破解这一困境的关键机制——通过工具，Agent 可以访问实时数据（如天气、股价）、操作外部系统（如数据库查询、文件读写、API 调用）、执行确定性计算（如数学运算、代码解释），从而将 LLM 的语义理解能力与实际业务操作能力无缝衔接。

如果说大模型是 Agent 的“大脑”，那么工具调用体系就是 Agent 的“双手”和“五官”，是实现“从说出到做到”这一跨越的核心工程支撑。

2.3 工具调用的三层技术层次 ​

Agent 工具调用体系按照抽象程度可分为三个技术层次：

第一层：原生函数调用（Function Calling） —— 大模型厂商在模型层内置的标准化能力，例如 OpenAI Function Calling、Google Gemini Function Calling 等。其核心是通过结构化输出格式（通常为 JSON Schema）引导模型生成符合工具调用的响应，是最基础的机制。

第二层：工具抽象与编排（Tool Framework） —— 在函数调用之上构建的开发者工具层，LangChain 的 Tool 系统、CrewAI 的 Tool 集成等均属此类。该层负责工具的注册、绑定、执行路由以及多工具编排。

第三层：标准化协议（Protocol Standardization） —— 旨在解决 Agent 与工具之间、不同 Agent 之间的互操作性问题。MCP（Model Context Protocol）统一了 LLM 与外部数据源和工具的通信方式，A2A（Agent-to-Agent Protocol）则专注于 Agent 间的协作。

三、函数调用机制：基础层原理 ​

3.1 Function Calling 的技术原理 ​

Function Calling 采用“意图识别-工具匹配-参数校验”的三段式处理流程。其核心组件包括工具注册表（维护可调用工具的元数据与参数 Schema）和参数解析器（从自然语言中提取结构化参数）。

以“预订明天 10 点的会议室”为例，系统执行流程如下：

  1. 意图识别：LLM 解析用户输入，判断需要调用“会议室预订”工具
  2. 路由匹配：路由引擎匹配已注册的 book_meeting_room 工具
  3. 参数提取：从自然语言中提取时间、人数等关键参数
  4. 执行调用：执行器调用工具 API 完成预订

从代码实现角度看，工具调用通常遵循“工具创建 → 工具绑定 → 工具调用 → 工具执行”的四步流程。

3.2 工具定义与参数规范 ​

工具的标准化定义是 Function Calling 的基础。在主流框架中，工具通常通过 @tool 装饰器或在工具类中声明 name、description 和 input_schema（通常使用 Pydantic 或 Zod Schema 定义）来完成声明。以 LangChain 为例，工具示例：

python
from langchain_core.tools import tool
@tool
def get_word_length(word: str) -> int:
    """计算一个单词中字母的数量。"""
    return len(word)

工具定义完成后，需要通过 .bind_tools() 方法将工具绑定到支持工具调用的模型，从而使模型了解工具及其所需的输入模式。

3.3 模型层面的函数调用实现 ​

不同模型提供商在函数调用机制上虽各有实现细节，但整体遵循统一的架构模式：模型在接收到用户输入后，判断是否需要调用外部工具；若需要，则生成符合指定 JSON Schema 的响应（包含工具名称和参数），而非直接返回文本答案。客户端接收到包含 tool_calls 字段的响应后，执行相应的工具调用，并将执行结果（以 ToolMessage 的形式）返回给模型，模型据此继续推理或生成最终答案。

这一机制的关键价值在于：它将“决策权”保留在模型端，而将“执行权”交由应用层控制。模型决定“什么情况下调用什么工具、传入什么参数”，应用层负责“如何安全地执行该工具、如何处理执行结果”。二者的解耦正是 Agent 系统的核心设计原则之一。

3.4 Function Calling 的局限性 ​

尽管 Function Calling 是 Agent 工具调用的核心基础，但在工程实践中暴露出多个明显短板：

  • 工具变更需重新部署整个系统：每新增或修改一个工具，都需要重新部署 Agent 服务
  • 复杂任务需要人工拆解步骤：面对多步骤复杂任务，模型不具备自动拆解能力
  • 异常处理依赖预设规则：工具调用失败、超时等异常情况需要预先编写大量容错逻辑

这些问题催生了更高层次的规划架构（如 ReAct）和标准化协议（如 MCP）的诞生。现代 Agent 框架通过策略引擎实现工具调用的动态路由，Function Calling 与 ReAct 正是这种演进下的典型产物。

四、ReAct 中的工具调用：认知-行动循环 ​

4.1 ReAct 模式的工具调用机制 ​

ReAct（Reasoning + Acting）模式通过引入“思考（Thought）→行动（Action）→观察（Observation）”的认知循环，将工具调用从“一次函数调用”升级为“动态决策循环”。在 ReAct 中，工具调用不是预定义的单一操作，而是在推理过程中根据上下文动态选择和执行。

以“规划三天两夜的城市旅行”为例，系统会：

  • 思考阶段：生成思考“需要先确定目的地和预算”
  • 行动阶段：调用 get_user_preference() 工具获取用户偏好
  • 观察阶段：获知用户偏好自然风光、预算 5000 元
  • 循环：更新记忆，继续思考“根据偏好推荐目的地”，调用 destination_recommendation 工具…… 直至任务完成。

4.2 静态规划 vs 动态工具链 ​

Function Calling 本质上是“静态匹配”——给定输入，模型在预定义的工具集合中选择一个（或少数几个）最匹配的工具执行。而 ReAct 模式下，工具链是在执行过程中动态构建的：Agent 根据前一步的观察结果决定下一步调用什么工具，形成自适应的工具调用序列。

这种差异决定了二者适用的场景截然不同：

维度Function CallingReAct
决策方式单步静态匹配多步推理循环
任务处理适合结构化、单一工具任务适合需要多步推理的复杂任务
工具调用模式预定义选择动态链式组装
典型场景数据库查询、API 调用旅行规划、研究分析
延迟特性低延迟（单次调用）较高（多次循环）

4.3 混合策略：Agent 开发的最佳实践 ​

在实际生产环境中，最佳实践通常不是“二选一”，而是采用混合策略：将 Function Calling 作为执行层机制（模型如何调用一个工具），将 ReAct 作为规划层架构（Agent 如何决定调用哪些工具、以什么顺序调用）。这种组合方式既利用了 ReAct 的动态适应能力处理复杂任务，又保留了 Function Calling 在单一工具调用场景中的高效性。

例如，在构建一个智能客服系统时：

  • ReAct 负责决策流程：分析用户问题 → 判断需要查询订单状态 → 调用查询工具 → 根据结果决定是否需要调取物流信息 → 继续循环
  • Function Calling 负责工具执行：每次实际调用数据库 API 时，使用标准的函数调用机制，确保参数格式正确、执行可靠

五、标准化协议：MCP 与 A2A ​

5.1 协议标准化的驱动因素 ​

随着 AI Agent 应用从单一模型调用转向多智能体协同，传统“孤岛式”的智能体集成方式已无法满足复杂任务需求。例如，旅行规划场景需要航班预订、酒店推荐、天气查询等多个 Agent 协作，而电商客服需要同时调用库存系统、物流接口和支付网关。这种趋势催生了两类核心协议：

  • 工具交互协议：解决 Agent 与外部系统（数据库、API）的连接问题
  • Agent 通信协议：规范不同 Agent 之间的协作规则与任务分配机制

MCP 与 A2A 正是这两类协议的典型代表，它们分别聚焦“AI 如何调用工具”和“AI 如何协作”，共同构建了 AI 群体智能的基础设施。

5.2 MCP：模型上下文协议（工具调用标准） ​

MCP 的本质与定位

MCP（Model Context Protocol）是由 Anthropic 于 2024 年 11 月推出的一种开放标准协议，旨在统一大语言模型与外部数据源和工具之间的通信方式。如果说 A2A 是让智能体之间能够交谈，那么 MCP 则是让智能体能够“看见”和“触碰”外部世界的数据和工具。

MCP 的核心价值在于：它通过统一协议替代碎片化的自定义集成，使得 Agent 可以像人类使用 USB 接口连接不同设备一样，以标准化的方式连接各种工具和数据源。MCP 使用客户端-服务器架构，MCP 服务器托管工具目录，MCP 客户端获取这些工具并使其可为 Agent 使用。

MCP 的核心组件

根据协议规范，MCP 包含三个核心组件：

  • 角色定义层：明确各 Agent 的职责边界（如规划者、执行者、验证者）
  • 消息总线层：定义标准化的通信格式（推荐使用 Protocol Buffers 或 JSON-RPC）
  • 协调控制层：实现任务分解、负载均衡等策略

在工具调用层面，MCP 的协议要素包括认证机制（支持 JWT/OAuth2.0）、消息格式（定义请求/响应的 JSON Schema）、错误码体系（标准化工具调用失败的处理）。

MCP 2026-07-28 重大版本更新

2026 年，MCP 协议发布了自推出以来最大规模的版本修订，其候选版本于 2026 年 5 月 21 日发布，最终规范于 2026 年 7 月 28 日正式发布。这次更新中最核心的变化是：MCP 在协议层实现了无状态化（stateless protocol core）。

这一变化对生产部署的影响是直接的。在之前的 2025-11-25 版本中，MCP 在 Streamable HTTP 上调用工具需要先建立会话（initialize 握手），服务器返回 Mcp-Session-Id，后续所有请求都必须携带该 ID，将客户端与特定服务器实例绑定。而在 2026-07-28 版本中，调用变为单个自包含请求，任何服务器实例都可以处理：MCP-Protocol-Version 和 Mcp-Method 头直接携带协议版本和调用方法，消除了会话概念。initialize/initialized 握手被移除，客户端可以缓存 tools/list 响应的 TTL（存活时间），无需每次重新获取工具定义。

此外，新版本还带来了多项其他重要能力：

  • Extensions 框架：支持服务端渲染 UI（通过 MCP Apps）和长期运行任务（通过 Tasks 扩展）
  • 授权强化：与 OAuth 和 OpenID Connect 部署进一步对齐
  • 正式弃用策略：协议可以在不破坏已有实现的情况下持续演进

MCP 的产业生态

MCP 在 2025-2026 年间已成为事实上的 AI 工具使用标准，Anthropic、OpenAI 和 Google 均已采纳该协议。微软于 2026 年 3 月发布了官方 MCP C# SDK 1.0 版本，全面支持 2025-11-25 版本的 MCP 规范。Salesforce 于 2026 年 5 月发布了 Data 360 MCP Server（开发者预览版），通过一种创新的 facade 工具架构，将约 200 个 API 操作打包为可供智能体直接访问的工具。Duolingo 在 2026 年 4 月时已支持约 30 个 MCP 服务器，提供超过 300 个可用工具。第五第三银行（Fifth Third）自 2025 年 12 月引入 MCP 以来，持续扩展其能力以简化集成、提升开发者生产力，确保 AI 系统能够可靠地与企业金融服务交互。这些事实表明，MCP 已成为企业级 Agent 工具集成的普遍选择。

5.3 A2A：Agent 间通信协议（智能体协作标准） ​

A2A 的本质与定位

A2A（Agent-to-Agent Protocol）是谷歌在 2025 年 4 月的 Google Cloud Next 大会上推出的开放协议，旨在为 AI 智能体之间提供标准化的交互方式。A2A 让不同的 AI 智能体能够互相“认识”和“交谈”，无论它们由哪家公司开发、运行在什么平台上。

A2A 解决了智能体之间的互操作性问题，支持长时间任务的协作（可维持数小时甚至数天的对话），并注重多模态交互（支持音频、图像和视频等多种数据交换）。在 A2A 出现之前，各种智能体如同各自筑起高墙的城邦，用户必须在不同系统间手动切换和搬运信息；A2A 正是为了打破这些“系统孤岛”，让智能体能够如人类团队一样分工合作。

A2A 的核心能力

A2A 协议的交互包含四个关键能力：

  • 能力发现：智能体通过“Agent Card”（JSON 格式元数据）公开自身能力，让其他智能体找到最适合执行特定任务的角色
  • 任务管理：定义完整的任务生命周期，支持从即时完成任务到复杂的长期任务
  • 协作沟通：智能体之间交换上下文信息、回复、工件或用户指令，实现真正多智能体协同
  • 用户体验协商：智能体之间就内容展示格式进行协商，适配不同的用户界面能力

A2A 建立在 HTTP、SSE、JSON-RPC 等现有流行标准之上，提供了通用的交互语言。值得注意的是，A2A 现由 Linux 基金会管理，其 GA v1.0 版本于 2026 年 3 月发布，协议的演进已由社区共同治理。微软的 Agent Framework 也已更新至 A2A v1 SDK，支持发现和调用来自任何供应商的远程 A2A Agent，并以符合 A2A 规范的方式暴露自身 Agent。

5.4 MCP 与 A2A 的核心差异与协同 ​

MCP 与 A2A 的本质区别在于协作主体与通信模式：MCP 是“主 AI 驱动的工具调用”，适合能力扩展；A2A 是“智能体自主协同”，适合流程自动化。MCP 采用中心化的“工具与任务管理器”架构，适合复杂、安全敏感的场景；A2A 采用去中心化的“消息传递中间件”架构，适合灵活、轻量级的协作场景。

二者并非竞争关系，而是在不同应用层次上形成互补。MCP 提供标准化接口和灵活传输，是连接多样化外部工具的最优解；A2A 的异步机制和服务发现功能，则在构建跨组织、高并发智能体协作网络时更具优势。

在实际系统中，三者通常协同工作：AI Agent 通过 Function Calling 调用 MCP 协议接口，实现从环境感知到工具操作的全流程自动化。下图展示了 MCP 与 A2A 的协作模式：

六、开发框架中的工具调用实现 ​

6.1 LangChain 工具调用体系 ​

LangChain 在工具调用方面构建了完整的生态系统，其主要概念包括：

工具的创建：使用 @tool 装饰器或继承 BaseTool 类创建工具，将函数本体与输入 Schema 封装为标准化工具，帮助模型以结构化方式触发操作。

工具的绑定：通过 .bind_tools() 方法将工具列表绑定到支持工具调用的模型，使模型能够了解可用的工具及其输入模式。支持工具调用的模型包括 OpenAI、Anthropic、Google 等多个提供商。

工具调用响应：模型在适当时机决定调用工具，确保其响应符合工具的输入模式；执行器使用模型提供的参数执行工具。

ToolExecutor 与 ToolNode：LangGraph 内置了 ToolExecutor 和 ToolNode 两种方式来简化工具的执行与路由。Agent（LLM）负责生成 tool_calls，ToolExecutor 负责根据 tool_calls 中的 name 字段调用正确的函数。

LangChain 的工具系统已实现对 MCP 工具的动态加载支持，工具使用 @regist_tool 装饰器注册，并被转换为实现 LangChain BaseTool 接口的适配器实例。LangGraph 与 MCP 框架的深度整合已在企业级 AI 工作流中得到验证，典型场景下开发效率可提升 300%，运维成本降低 60%。

6.2 多工具路由与选择性调用 ​

在生产级 Agent 中，Agent 通常需要从多个工具中选择一个或多个来执行，而非简单绑定单个工具。LangGraph 实现的多工具路由模式通过动态决策实现工具的选择性调用。

在多工具场景中，关键区别在于：Agent 不仅需要判断“是否使用工具”，还需要判断“使用哪个工具”。LangGraph 的 ToolExecutor 通过匹配 tool_calls 中的 name 字段实现这一路由逻辑。should_continue 决策函数检查 state[‘messages’][-1].tool_calls 是否存在，若存在则路由至 ToolNode 执行工具，若不存在则结束。

LangGraph 还实现了更复杂的 Router Pattern，其核心思想是语言模型可以动态控制执行流程，在直接响应和工具调用之间路由。当存在 tool_calls 时，消息被路由到 ToolNode 执行，执行后附加 ToolMessage 到状态中。这种设计将决策逻辑与执行逻辑彻底解耦，使 Agent 能够在运行时根据输入内容智能选择工具。

6.3 CrewAI 工具集成 ​

CrewAI 作为多智能体编排框架，在工具集成方面提供了三种接入方式：

  1. 原生工具：直接调用框架内置工具库，包括 SerperDevTool（Google 搜索）、ScrapeWebsiteTool（网页抓取）、FileReadTool（文件读取）、CodeInterpreterTool（代码执行）等。
  2. HTTP 工具：封装 RESTful API 调用，将任何 HTTP API 转换为 Agent 可调用的工具。
  3. 自定义工具：通过 Python 类扩展，使用 @tool 装饰器即可定义自定义工具。

CrewAI 在工具集成方面的一大亮点是：其工具系统兼容 LangChain Tools，开发者使用 LangChain 编写的工具可以直接在 CrewAI 中复用。这一特性大幅降低了开发者在不同框架间的迁移成本。在应用层面，某制造企业的设备监控系统通过自定义工具将 PLC 数据采集、异常检测、报警通知整合到统一流程中，使设备故障响应时间从 15 分钟降至 90 秒。

CrewAI 也支持 MCP 集成，可以在运行时从 MCP 服务器 URL 加载可用工具，无需手动注册。截至 2026 年，CrewAI 已在代码托管平台获得 44.7k 星标，被 48% 的全球 500 强企业用于核心业务系统，每月执行超 1000 万次 AI 代理任务。

6.4 AutoGen 工具调用 ​

AutoGen 是微软推出的多智能体框架，在工具调用方面支持 MCP 集成，提供结构化工具调用、消息历史处理和模型编排能力。通过 Composio 的 Tool Router，AutoGen 可以动态发现和服务合适的工具。其工作流通常采用“工具调用智能体 + 其他专业智能体”的协作模式。

七、工具调用的安全与治理 ​

7.1 工具调用的安全挑战 ​

随着 Agent 工具调用能力从“单一 API 调用”扩展到“数百个工具的动态调用”，安全治理挑战日益凸显。主要挑战包括：

  • 权限边界的动态化：Agent 根据上下文动态决定调用哪些工具，传统的静态权限模型难以覆盖
  • 参数注入风险：Agent 生成的工具参数可能绕过输入验证机制
  • 循环调用与资源耗尽：Agent 可能陷入工具调用的死循环，造成计算资源浪费
  • 工具间的副作用传播：一个工具调用的失败或错误可能影响后续依赖工具

7.2 安全护栏（Guardrails）设计 ​

针对工具调用场景的安全治理，业界已形成多层次的安全护栏设计：

认证与授权层：MCP 协议已支持 JWT 和 OAuth2.0 等多模式认证，企业部署中需结合 OAuth 和 OpenID Connect 实施统一的身份认证机制。

参数验证层：采用双重验证机制——模型生成的参数首先通过 Schema 校验（确保类型正确、必填字段完整），进入工具执行阶段前再通过业务规则验证（如范围检查、权限校验）。

执行边界控制：设置超时、重试次数限制和资源配额。在 Agent 配置中设定 max_iter 参数防止陷入死循环（推荐 5-10 次）。对于长时间运行的工具调用，MCP 的 Tasks 扩展提供了对长期运行工作的标准化支持。

审计与可观测性：LangSmith 等平台提供 Agent 行为的可视化分析与审计追踪，包括工具调用日志、参数记录、执行耗时和错误率。

7.3 最佳实践建议 ​

在企业级部署中，以下工具调用安全实践值得采纳：

  • 最小权限原则：每个 Agent 仅被授予完成其任务所需的最小工具集合和权限范围
  • 人在回路机制：对于高风险操作（如支付、数据删除），设置人工审批节点
  • 熔断降级：当工具调用失败率达到阈值时，自动熔断并切换到备用工具或回退策略
  • 沙箱隔离：代码执行类工具应在隔离的沙箱环境中运行，防止对宿主系统造成影响

第五第三银行金融 MCP：该银行自 2025 年 12 月引入 MCP 以来，通过扩展能力持续简化集成、提升开发者生产力，确保 AI 系统能够可靠地与企业金融服务交互。其关键经验在于：金融等高合规要求的行业，MCP 的标准化 API 调用契约和错误码体系大大简化了安全审计和合规验证工作。

九、未来趋势与挑战 ​

9.1 协议标准的持续演进 ​

MCP 2026-07-28 版本的无状态化重构标志着协议技术路线的重要方向：从“面向会话”走向“面向请求”。这一演进使得 MCP 服务器可以部署在普通轮询负载均衡器后面，无需粘性会话或共享会话存储，极大地简化了生产级部署的运维复杂度。

同时，MCP Apps 的引入让服务端可以呈现渲染后的 UI 界面，意味着工具调用不再局限于纯数据交换场景，而是可以涵盖更复杂的用户交互流程。当 Agent 调用某个工具时，工具可以向用户直接展示交互界面（如表单、按钮、图表），形成“Agent 主导→工具辅助→用户参与”的新型工作模式。

9.2 从工具调用到自主执行 ​

随着工具调用能力的不断提升，Agent 正在从“用户指示的工具执行者”向“自主驱动的行动者”演进。这一演进涉及三大技术方向：

  1. 零样本工具发现：Agent 在运行时可动态发现新的工具，无需预配置工具列表
  2. 跨域工具链组装：Agent 自主组合来自不同领域（数据、代码、业务系统）的工具完成复杂任务
  3. 工具调用的自我优化：通过 Reflection 模式对工具调用效果进行事后分析，持续优化决策质量

9.3 工具调用的规模化挑战 ​

尽管取得了显著进展，工具调用的规模化部署仍然面临多个关键挑战：

  • 工具发现的标准化：当工具数量从几十扩展到成千上万时，如何高效发现和选择合适工具是核心难题
  • 调用成本的优化：在 MCP 基础设施之上，工具调用的参数解析、结果处理和记忆管理带来了显著的 token 开销
  • 调用可解释性：对于高风险行业（医疗、金融），工具调用的决策过程需要完全可追溯和可解释
  • 调用可靠性：在复杂工具链中实现幂等性设计、事务回滚机制仍是工程难点

十、总结 ​

本笔记系统梳理了 AI Agent 工具调用的核心知识体系，归纳要点如下：

  1. 工具调用的技术层次：从底层函数调用（Function Calling）到中间层框架工具系统（LangChain/CrewAI 工具），再到上层标准化协议（MCP/A2A），构成了完整的工具调用技术栈。三者协同工作：Agent 通过 Function Calling 调用 MCP 协议接口，实现从环境感知到工具操作的全流程自动化。

  2. Function Calling vs ReAct：Function Calling 适合结构化、低延迟的单工具调用场景；ReAct 通过“推理-行动-观察”循环构建动态工具链，适合多步骤复杂任务。现代 Agent 开发通常采用混合策略，将 ReAct 作为规划架构、Function Calling 作为执行机制。

  3. MCP 协议：已演进为 AI 工具使用的行业标准，2026-07-28 版本实现了协议层无状态化，消除了会话概念，支持扩展框架、MCP Apps 和长期运行任务（Tasks 扩展），极大地简化了生产环境部署。

  4. A2A 协议：专注于 Agent 间协作的标准化，通过 Agent Card 实现能力发现、任务管理、协作沟通与用户体验协商。A2A 与 MCP 形成互补关系，共同构成多智能体系统的通信基础设施。

  5. 开发框架实现：LangChain 提供完整的工具创建、绑定与路由体系；CrewAI 提供三层工具集成方案（原生工具 / HTTP 工具 / 自定义工具）；AutoGen 支持 MCP 集成下的结构化工具调用。多框架均实现了对 MCP 协议的集成兼容。

  6. 安全治理：工具调用需建立认证授权、参数验证、执行边界控制和审计追溯的多层安全护栏，企业部署中应遵循最小权限、人在回路、熔断降级和沙箱隔离等安全原则。

  7. 市场与前景：企业级 Agent 市场正处于爆发式增长阶段，工具标准化协议（MCP/A2A）的采用率正在加速提升。零样本工具发现、跨域工具链组装和工具调用自我优化将是下一阶段的研究重点。

Agent 框架（Agent Frameworks） ​

一、前言 ​

本笔记是 AI Agent 开发系列笔记的第五篇，接续前四篇概述、架构设计、工具调用与多 Agent 协作，聚焦于 Agent 开发框架这一工程实践的核心议题。若说大语言模型是 Agent 的“大脑”、工具调用是 Agent 的“双手”，那么 Agent 框架就是承载这一切协同运作的“骨架”与“血管系统”——它决定了 Agent 系统从概念验证到生产部署的可行性和效率边界。

2024 年被称为 Agent 框架的“寒武纪大爆发”期，GitHub 上高星 Agent 仓库数量在 12 个月内激增 535%，形成技术百花齐放的局面。经过 2025–2026 年的优胜劣汰，行业已形成三大技术共识：标准化协议体系（MCP）、多智能体协作范式（A2A）与工程化能力的跃迁。与此同时，2026 年的框架生态也经历了一次深刻的洗牌：AutoGen 进入维护模式、Microsoft Agent Framework 成为其推荐继任者、LangGraph 和 CrewAI 继续迭代进化。

Gartner 预测 2026 年 40% 的企业应用将嵌入任务型 AI 智能体，这一预测正在全球范围内加速兑现。本笔记将从框架分类体系入手，逐层深入主流框架的技术解析、跨框架协议标准、选型决策与未来趋势，力求为开发者提供一份系统性、可操作的 Agent 框架全景指南。

二、Agent 框架的定义与分类 ​

2.1 Agent 框架的定义 ​

Agent 框架（Agent Framework）是为构建、编排和部署 AI 智能体系统而设计的软件基础设施，旨在将基座模型的智能能力转化为生产级应用可依赖、可扩展、可维护的软件架构。

从技术层次来看，Agent 框架通常承担以下职责：

  • Agent 生命周期管理：从创建、运行到销毁的全流程管理
  • 工具集成与调用编排：统一管理 Agent 可用的工具集，处理工具调用的序列化与错误恢复
  • 状态与记忆管理：支持跨会话、长时间任务的上下文保持与状态持久化
  • 多智能体协作：实现 Agent 间的通信协议、任务分配与结果聚合
  • 生产级基础设施：可观测性、安全护栏、人机协作等工程化特性

2.2 框架分类的三维坐标 ​

2026 年的主流 Agent 框架可划分为三大技术流派：

第一派：确定性控制框架——以状态图、工作流或角色化机制为核心，强调执行流程的确定性与可控性。代表：LangGraph、CrewAI。适合风控、金融等强一致性场景。

第二派：自适应学习框架——以强化学习、记忆机制和动态规划为核心，强调系统的持续优化能力。代表：AutoGen（及其后续演进）、ReAct。适合客服、个性化推荐等持续交互场景。

第三派：混合架构框架——融合前两派特性，通过模块化设计实现灵活组合。代表：Microsoft Agent Framework、Google ADK。适合企业级综合应用场景。

值得强调的是，Agent 框架的选型并非“非此即彼”的单选题。许多生产级系统实际采用混合架构组合使用多个框架——用 LangGraph 编排核心流程、用 CrewAI 组织专业化团队、用 MAF 连接更广泛的模型生态。

2.3 2024–2026 年技术演进与生态洗牌 ​

2024 年被称为 Agent 框架的“寒武纪大爆发”期，GitHub 上高星 Agent 仓库数量在 12 个月内激增 535%。这一阶段的技术呈现出百花齐放的特征，但也带来了严重的碎片化问题——各种 Agent 实现方案各行其是，代码复用率低、维护成本高昂。

进入 2025–2026 年，行业进入优胜劣汰与加速整合期。MCP（Model Context Protocol）成为模型上下文管理的事实标准，A2A 协议的兴起推动 Agent 从单体应用向分布式系统演进。与此同时，框架生态经历了一次深刻的洗牌：AutoGen 进入维护模式，Microsoft Agent Framework 成为其推荐的继任者，LangGraph 和 CrewAI 继续迭代进化。经过两年优胜劣汰，行业已形成三大技术共识：标准化协议体系（MCP）、多智能体协作范式（A2A）与工程化能力的跃迁。

三、主流 Agent 框架深度解析 ​

3.1 LangChain 1.0：Agent 开发范式的标准化重构 ​

3.1.1 版本演进与核心痛点 ​

LangChain 自诞生以来，一直是最早也是使用最广的 LLM 应用开发框架之一。早期版本通过提供统一的模型接口和预置代理模式，显著降低了 AI 能力接入门槛。但企业级应用场景加深后，开发者逐渐反馈三大痛点：

  • 过度封装导致灵活性受限：高层抽象难以满足定制化流程需求
  • 包体积膨胀影响部署效率：主包包含大量低频功能模块
  • 状态管理成本高企：复杂流程需要手动实现持久化机制

与此同时，旧版 Agent 实现的碎片化问题也日益突出——开发者需要面对多种 Agent 实现方案（如 ReAct、Plan-and-Execute 等），每种方案都定义了不同的执行逻辑和接口规范，导致代码复用率低、维护成本高。

3.1.2 1.0 版核心架构升级 ​

LangChain 1.0 版本通过架构重构和功能分层，系统性解决了上述问题。

全新 Agent 抽象层：新版本引入 create_agent 核心接口，构建 Agent 的流程简化为标准化三步：

python
# LangChain 1.0 Agent 统一创建入口（示例）
from langchain.agents import create_agent

agent = create_agent(
    model="gpt-4",
    tools=[search_tool, calculator_tool],
    system_prompt="You are a professional assistant, please provide accurate answers..."
)

这一抽象层具备三大特性：

  • 模型透明化：开发者可直接指定底层 LLM 参数
  • 工具链解耦：工具定义与 Agent 逻辑完全分离
  • 执行链可观测：内置日志系统记录完整推理过程

标准化内容块机制：为解决跨模型输出格式不一致问题，引入“标准内容块”规范，强制要求所有模型输出必须包含结构化数据字段、来源追溯信息、质量评估指标及扩展字段预留。

模块化重构：通过功能分层实现主包体积减少 40%，同时保持 100% 向后兼容。

3.1.3 LangGraph：Agent 的底层运行时引擎 ​

LangChain 1.0 的最大创新在于，所有 Agent 的底层执行运行在 LangGraph 运行时之上——create_agent 底层已经运行在 LangGraph 运行时，LangGraph 事实上成了 LangChain 生态的执行引擎。技术栈形成了明确的分层：用 create_agent 处理标准工具调用循环；当需要自定义工作流拓扑时，下沉到原生 LangGraph。

LangGraph 为 Agent 提供了“操作系统”级的核心能力：

  • 自动状态快照：每步执行后保存完整上下文
  • 断点恢复能力：进程崩溃后可从最近快照恢复
  • 多实例同步：支持分布式环境下的状态共享

3.1.4 LangChain 1.0 的核心评价 ​

LangChain 1.0 的发布标志着 Agent 框架正式进入生产就绪阶段，为复杂业务场景提供了从快速原型到企业级落地的完整解决方案。其三大核心能力——流程定义、中间件控制和模型抽象——有效解决了旧版在灵活性、可控性和可维护性方面的根本问题。某物流企业的测试显示，新架构使工作流开发效率提升 40%，代码量减少 55%。

3.2 LangGraph：图式架构的 Agent 运行时 ​

3.2.1 设计哲学：把 Agent 变成一张图 ​

LangGraph 的设计哲学极为简洁：把 Agent 系统的执行流程建模为一张有向状态图。一个 LangGraph 应用由三样核心要素构成：

  • State（状态） ：Agent 的记忆，在节点之间流动，保存对话历史、中间结果
  • Node（节点） ：流程图的方块，每个节点是一个接收状态并返回更新的 Python 可调用对象
  • Edge（边） ：流程图的箭头，决定下一步走哪个节点，支持静态路由和动态条件分支

这三者组合成 StateGraph——LangGraph 的核心对象。Agent 可以沿着图往前走、可以回头、可以分叉、可以形成循环，开发者不再需要手动管理状态与分支逻辑。

3.2.2 传统线性管道 vs. 图式架构 ​

LangChain 早期版本的核心设计理念是“线性管道”（LCEL 模式），通过链式调用将组件串联，形成“输入→处理→输出”的简单流程。但在复杂场景下暴露出三大缺陷：

  • 控制流僵化：分支判断依赖硬编码条件，循环结构需手动实现
  • 状态管理混乱：中间状态分散在各组件中，缺乏统一记录机制
  • 扩展性瓶颈：并发任务需通过外部编排实现

LangGraph 通过图式架构重构了开发范式，将“思考-行动-观察”循环建模为有向状态图，实现了三大技术突破：

动态条件路由：通过路由函数根据状态动态决定下一节点：

python
# 条件路由示例
def router_fn(state: AgentState) -> str:
    if "计算" in state["question"]:
        return "calc_node"
    elif "百科" in state["question"]:
        return "wiki_node"
    else:
        return "respond_node"

多节点合并机制：支持多个节点更新同一状态字段，通过合并策略（覆盖、追加、求和等）解决冲突。

持久化与可观测性：

  • 中间状态记录：每个节点执行后自动追加思考日志，形成完整推理轨迹
  • 流式调度：支持 .stream() 方法实现逐节点事件输出
  • 持久化支持：状态字典可序列化，支持会话中断后恢复执行

3.2.3 持久化执行与可恢复性 ​

LangGraph 的核心价值在于将持久化执行（Durable Execution）提升为一等公民。其内置的状态检查点机制允许工作流在执行任意节点后被暂停、序列化并在相同或不同进程中恢复。这一特性使 Agent 能够执行运行数小时甚至数天的长周期任务，而无需担心进程崩溃或服务重启带来的状态丢失。

自 2025 年 10 月发布 v1.0 正式版以来，LangGraph 已在 Uber、LinkedIn 和 Klarna 等企业支撑生产级 Agent。2026 年 Q2 即将发布的 2.0 版本计划加入 A2A 多 Agent 协议和内置 Guardrail 节点。

3.2.4 状态检查点与“时光回溯”调试 ​

LangGraph 的状态检查点机制（Checkpointing）为调试和生产运维提供了独特价值。开发者可以在 Agent 执行的任意节点“暂停”流程、检查状态、甚至在需要时回溯到更早的检查点重新执行。这种“时光回溯调试”能力在生产环境中尤其宝贵——当 Agent 出现意外行为时，开发者可以直接重放到错误发生的节点进行诊断，无需从头运行整个任务。结合 LangSmith Deployment 的全生命周期支持，LangGraph 提供了从本地开发到云部署、混合部署和自托管的完整部署路径。

3.3 CrewAI：角色驱动的多智能体协作框架 ​

3.3.1 团队协作的设计哲学 ​

如果说 LangGraph 关注的是“流程的图”，CrewAI 关注的则是“团队的形”。CrewAI 的设计灵感来自人类团队的分工协作——每个智能体被赋予明确的角色职责，多个智能体组成“团队”（Crew）协同完成复杂任务。

截至 2026 年，CrewAI 在 GitHub 获得超 44.7k 星标，每月处理千万级 AI 代理任务，被近半数世界 500 强企业采用。

3.3.2 五层协作模型 ​

CrewAI 采用五层模型实现组件解耦：

第一层：工具层（Tool） —— 智能体的技能载体，支持三类扩展方式：

  • 自定义 Tool：通过继承基类实现业务逻辑
  • HTTP 工具：封装 RESTful API 调用
  • 第三方工具集成：复用 LangChain 等生态中的已有工具

第二层：代理层（Agent） —— 自治执行单元，具备角色感知能力。每个 Agent 通过 role 参数声明专业领域，工具链配置实现能力扩展，知识库注入建立初始认知基础。

第三层：任务层（Task） —— 动态分配单元，支持优先级标记与状态追踪。

第四层：流程层（Process） —— 协作控制器，提供顺序（按固定顺序依次执行）、并行（多个 Agent 同时执行）和层级（分级指挥）三种执行模式。

第五层：团队层（Crew） —— 智能体集合，通过共享内存实现上下文感知。

3.3.3 核心技术特性 ​

角色化设计与自主委托：每个 Agent 可配置专属工具集与决策逻辑。当任务超出能力范围时，Agent 可自动触发任务转交。

三层记忆架构：CrewAI 构建了“热-温-冷”三层存储模型：

  • 工作记忆（Working Memory）：存储当前任务执行期间的上下文信息，容量约 10MB
  • 情景记忆（Episodic Memory）：基于向量相似度的语义搜索，存储过去任务的事件记录，生命周期可配置
  • 语义记忆（Semantic Memory）：永久存储结构化知识图谱与非结构化文档，如企业法规、产品文档等

输出标准化：内置 Pydantic 模型验证，确保数据结构一致性。

模型兼容层：通过适配器模式支持主流 LLM 接入，无厂商锁定。

3.3.4 典型应用场景与路线图 ​

CrewAI 在多个企业级场景中已实现规模化应用：

  • 智能客服系统：构建意图识别、知识检索、对话生成的代理团队，实现 7×24 小时服务
  • 自动化数据分析：组合数据采集、清洗、建模、可视化代理，将分析周期从天级缩短至分钟级
  • 供应链优化：通过需求预测、库存管理、物流调度代理的协同，降低 15% 运营成本

根据项目路线图，2026 年将重点突破多模态协作、自进化团队（通过强化学习优化代理协作策略）及边缘计算部署。

3.4 微软生态：从 AutoGen 到 Microsoft Agent Framework ​

微软在这一轮 Agent 框架浪潮中的角色最为特殊——它拥有两个领先项目（AutoGen 与 Semantic Kernel），并选择在 2025–2026 年完成两者的战略整合。

3.4.1 AutoGen：开创“群聊式”多智能体协作 ​

AutoGen 于 2023 年末由 Microsoft Research 发布，以“群聊式协作”迅速成为多智能体系统的标杆。其核心心智模型是：智能体是对话的参与者，整个系统就是一个群聊。

AutoGen 开创的协作范式包含两个核心角色：

  • AssistantAgent：负责生成回答、推理和代码编写
  • UserProxyAgent：负责执行代码并反馈执行结果

智能体之间可以委派任务、互相批评与纠正、调用工具、编写并执行代码、向人类发起询问，在目标达成后自行终止。没有中央控制器需要提前知晓完整计划。早期 Demo 在编码、研究分析、股票分析等任务上展现出比单智能体高 2–10 倍的表现。

3.4.2 AutoGen v0.4：技术巅峰 ​

v0.4 版本（2025 年初发布）本质上是 AutoGen 2.0。旧的阻塞式同步 GroupChat 被三层新架构取代：autogen-core 负责底层事件驱动原语；autogen-agentchat 提供高层 API；autogen-ext 作为可插拔的扩展层。核心改进包括完全异步化带来的更好可扩展性与可观测性、模块化的自定义组件、改进的错误恢复与检查点机制。

3.4.3 Microsoft Agent Framework（MAF）：统一的 Agent 开发底座 ​

2025 年末，微软正式将 AutoGen 与 Semantic Kernel 合并，统一为 Microsoft Agent Framework（MAF）。MAF 在 2026 年 4 月发布 v1.0 正式版，支持 Python 和 .NET 双语言。微软官方如此阐述其定位：随着 MAF 的推出，开发者再无需在 Semantic Kernel 和 AutoGen 之间做选择。

MAF 的三大统一抽象：

  • Agent 抽象：Agent 不再是“一次模型调用”，而是可持久化交互、可挂载中间件、可持有会话状态的运行时实体
  • Workflow 抽象：复杂任务不再完全依赖 Agent 自由发挥，而是通过基于图的 workflows 将 Agent 与函数按显式流程组织，支持顺序、并发、handoff、group chat 等模式，并具备 checkpointing、human-in-the-loop、类型安全路由等工程能力
  • 能力封装抽象（Skills） ：这是 1.0 版本最关键的补齐点，将“领域知识、操作说明、脚本资源、模板资产”封装为统一可复用的形态

核心能力：v1.0 版本包括多模型与多 Agent 平台支持（Azure OpenAI、Anthropic Claude、Google Gemini、Amazon Bedrock 等）、Workflows、与 Foundry 的原生集成以及开箱即用的 MCP、A2A 和 OpenAPI 支持。

工程化信号：MAF v1.0 不仅是一次功能更新，更重要的是它传达的“工程化”信号——能力边界更清晰、核心抽象更稳定、复杂度可被有效组织。如同微软官方博客所述，它“不再是单纯调用模型的 SDK，而是一个面向生产的 Agent Runtime 基础设施”。

MAF 的 AutoGen 前身已于 2025 年 9 月发布最后一个独立版本 v0.7.5，之后仅接收维护更新。新开发工作完全在统一代码库中进行，建议开发者将现有的 AutoGen 项目尽早迁移至 MAF。

3.5 Google Agent Development Kit（ADK）与 A2A ​

3.5.1 ADK v1.0：Google 生态的原生开发框架 ​

Google 于 2026 年 Cloud Next 大会上进行了全面的 Agent 平台战略调整：Vertex AI 更名为 Gemini Enterprise Agent Platform，同时发布了 Google Agent Development Kit（ADK）v1.0 稳定版，支持四种语言的 Agent 开发。ADK 与 Google 自家模型生态（Gemini 系列）深度整合，提供了 Agent Designer（可视化流程画布）、Agent Engine Sessions（持久化交互上下文）、Memory Bank（跨会话状态保持）等企业级能力。

3.5.2 A2A 协议：跨平台 Agent 互操作的桥梁 ​

Agent-to-Agent（A2A）协议是 Google 于 2025 年 4 月推出的开放协议，旨在解决不同供应商、不同框架构建的 AI 智能体之间的互操作问题。A2A 定义了四个核心概念：

  • Agent Cards：Agent 通过标准的 /.well-known/agent-card.json 公开其能力元数据，实现自动服务发现
  • Task 生命周期：定义任务从提交、工作中、需输入、完成到失败/取消/拒绝的完整生命周期管理
  • Transport：基于 HTTP、SSE 和 JSON-RPC 2.0 等现有标准进行通信
  • 协作模式：支持任务的委派、并行执行和结果汇总

A2A 现由 Linux 基金会管理，自发布以来发展迅速。截至 2026 年 4 月，已有超过 150 家组织在生产环境中支持 A2A 协议，包括 Google、Microsoft、AWS、Salesforce、SAP、ServiceNow 等多家行业巨头。Azure AI Foundry、Amazon Bedrock AgentCore 和 Google Cloud 均已原生集成 A2A 协议。Google Cloud Next 2026 上披露，已有 150 家组织在生产环境中使用 A2A（而非仅停留在试点阶段）在各个平台构建的 Agent 之间路由真实任务。

3.6 其他主流框架概览 ​

3.6.1 OpenAI Agents SDK：原生工具调用集成 ​

OpenAI Agents SDK 是 OpenAI 推出的 Provider-Native 框架，主打与 OpenAI 模型生态的最紧密集成。其核心优势在于 Tool Call 和任务交接（handoff）的无缝衔接。对于以 OpenAI 模型为核心、且主要在受控环境中运行 Agent 的团队，该 SDK 能够显著降低工程复杂性。

3.6.2 Mastra：TypeScript 原生的 Agent 框架 ​

Mastra 是专为 TypeScript 生态构建的 Agent 框架，在 2026 年成为关注度持续上升的新兴力量。它提供 TS-first 的 Agent 开发体验，内置 memory、traces 和 workflows 等核心能力。对于以 Node.js/TypeScript 为主要技术栈、希望 Agent 开发与现有前端/全栈工程体系无缝融合的 Web 团队，Mastra 是理想选择。

3.6.3 Pydantic AI：类型安全的 Python Agent 框架 ​

Pydantic AI 是围绕 Pydantic 的类型系统构建的轻量级 Agent 框架，强调类型安全和可测试性。对于已经深度依赖 Pydantic 的 Python 项目（如 FastAPI 应用），Pydantic AI 提供了低摩擦的 Agent 集成路径。

3.6.4 字节跳动 Coze（扣子）：无代码 Agent 开发平台 ​

字节跳动的 Coze（扣子）平台走的是不同于开源框架的另一条路径——面向终端用户的无代码 Agent 开发。2026 年 1 月，扣子发布 2.0 版本，核心引入了 Agent Skills 和 Agent Plan 两大概念。

Agent Skills 的本质是“场景最佳实践 + 所需工具”的封装，将特定工作流、工具调用逻辑及行业经验打包成可复用的技能模块。用户可通过“技能商店”上传或下载这些封装好的能力，实现了隐性职业经验的代码化流转。

Agent Plan（长期计划）解决长链路任务的自动化问题：用户只需设定长期目标（如“运营账号涨粉”），AI 会尝试自主拆解阶段性任务、制定策略并按周期执行，交互范式从“Prompt 指令”向“目标导向”转变。

2026 年 4 月，扣子 2.5 版本进一步推出“Agent World”——为 AI Agent 提供独立的云设备、记忆与身份系统，构建了一个开放的智能体协作与进化生态。字节跳动 Seed 团队与中国人民大学联合提出的 Agent-World 开源框架，构建了包含 1978 个环境、近 2 万个工具的大规模训练集，旨在推动通用智能体智能的发展。

四、跨框架互操作标准：MCP 与 A2A ​

4.1 标准化的必要性 ​

在 Agent 框架体系快速演进的背景下，跨框架的互操作性成为决定 Agent 技术能否真正走向规模化的关键瓶颈。不同框架之间、不同供应商之间的 Agent 如何进行能力发现、任务委派和信息交换？MCP 与 A2A 正是回答这一问题的答案。

MCP（Model Context Protocol） 聚焦于 Agent 与外部数据源和工具之间的标准化连接。MCP 自 2024 年推出以来，已获得 Anthropic、OpenAI、Google、Microsoft 等行业巨头的采纳，并在 2026 年取得显著进展。Google Cloud 宣布通过 Apigee 作为 API-to-Agent 桥接提供托管 MCP 服务器，Anthropic 的 MCP 生态已达 10,000 个服务器和 9,700 万月 SDK 下载量。

A2A（Agent-to-Agent Protocol） 专注于多智能体间的自主协作，由 Google 于 2025 年 4 月提出，现由 Linux 基金会管理。A2A 和 MCP 形成互补——MCP 解决“Agent 如何与工具和数据交互”，A2A 解决“Agent 之间如何对话与协作”。

4.2 MCP 2026-07-28 版本更新：走向无状态化 ​

MCP 在 2026 年 7 月 28 日发布了重大版本更新，最核心的变化是在协议层实现了无状态化。新版本消除了会话握手（initialize/initialized）概念，任何服务器实例都可以处理单个请求，无需绑定特定客户端。这一变化直接解决了 MCP 服务器在普通轮询负载均衡器后的部署难题，无需粘性会话或共享会话存储，极大地简化了生产级部署的运维复杂度。MCP 还引入了 Extensions 框架，支持服务端渲染 UI（MCP Apps）和长期运行任务（Tasks 扩展），与 OAuth/OpenID Connect 的授权强化进一步对齐。

4.3 A2A v1.0 GA：跨组织 Agent 互操作的里程碑 ​

A2A 协议在 2026 年 3 月发布了 GA v1.0 版本，协议的演进由社区共同治理。各大主流云平台——Azure AI Foundry、Amazon Bedrock AgentCore 和 Google Cloud——均已原生集成 A2A。跨平台、跨供应商的 Agent 协作不再是理论设想，而是正在落地的现实。

但值得注意的是，A2A 合规性本身并不足够——即使两个 Agent 都支持 A2A 协议，在真正协作之前仍然需要一个共享的上下文层来对齐业务定义和领域知识。这一点提醒我们：协议标准化解决的是“能不能通”，而要解决“通得好不好”，还需要在业务语义层面进行对齐。

5.2 核心维度对比 ​

各框架在生产级部署关键维度上的差异，集中体现在以下几个方面：

  • 持久化能力：LangGraph 的 Durable Execution 和状态检查点机制在长周期任务中优势显著；CrewAI 和 MAF 也提供不同程度的持久化支持
  • 调试体验：LangGraph 的“时光回溯调试”能力在定位故障时成本最低；CrewAI 提供结构化日志；MAF 集成 OpenTelemetry 提供全链路追踪
  • 多语言支持：MAF 同时支持 Python 和 .NET；Mastra 和 Pydantic AI 分别覆盖 TypeScript 和 Python；其他框架以 Python 为主
  • 开源许可：LangGraph 和 CrewAI 均采用 MIT 许可证，对商业使用友好
  • 托管服务：LangGraph 有 LangSmith Deployment 和 LangGraph Platform，CrewAI 有 CrewAI AMP Cloud，MAF 集成 Microsoft Foundry Agent Service

5.3 选型决策树 ​

如果需求是“生产级可靠、有状态、需持久化执行” → 选 LangGraph LangGraph 在有状态 Agent 和检查点支持方面表现最佳，已为 Uber、LinkedIn 和 Klarna 等企业提供生产支撑。对于长周期任务（运行数小时至数天）和需要流程恢复的复杂工作流，LangGraph 的 Durable Execution 是当前最成熟的选择。

如果需求是“角色分工明确的协作、模拟人类团队” → 选 CrewAI CrewAI 提供开箱即用的角色化协作和多种执行模式（顺序/并行/分层），开发者无需从零构建工作流拓扑。对于客服、数据分析、供应链优化等需要多个专业角色配合的场景，CrewAI 能够显著降低多智能体系统的构建门槛。

如果需求是“企业级 .NET/Python 混合部署、统一抽象” → 选 Microsoft Agent Framework MAF 整合了 Semantic Kernel 的企业级基础与 AutoGen 的多智能体创新，同时支持 Python 和 .NET，提供 Agent Skills、Workflows 和内置 MCP/A2A 支持。对于已有 .NET 技术栈的团队，MAF 是优先选择。

如果需求是“TypeScript 原生、Web 团队优先” → 选 Mastra Mastra 在 TypeScript 原生的 Agent 框架中关注度持续上升，提供 memory、traces 和 workflows 等核心能力，与 Node.js 生态无缝融合。

如果需求是“Google 生态深度整合” → 选 Google ADK ADK 与 Vertex AI、Gemini 模型和 Google Workspace 原生集成，提供可视化编排界面和企业级会话管理。

如果需求是“低代码、快速搭建、个人/小团队” → 选 Coze Coze（扣子）提供无代码 Agent 开发体验，2.0 版本引入 Agent Skills（场景能力封装）和 Agent Plan（长周期任务自主执行），大幅降低了 Agent 应用的门槛。

如果正在使用 AutoGen 开发或计划新项目：建议直接将新项目迁移到 MAF。AutoGen 已于 2025 年 9 月发布最后一个独立版本 v0.7.5，此后仅进入维护模式，不再接收重大功能更新。

5.4 选型常见误区与避坑指南 ​

在多框架并存的生态中，开发者容易出现以下选型偏差：

  • 误区一：唯 Stars 论。AutoGen 的 GitHub 星标数（57.8k）虽然高于其他框架，但它已进入维护模式。在生产选型中，维护状态（Active development matters more than stars）的权重应高于 Stars。
  • 误区二：单一框架打天下。生产级系统实际采用混合架构组合使用多个框架是常见做法——用 LangGraph 编排核心流程、用 CrewAI 组织专业化团队、用 MAF 连接更广泛的模型生态。切勿为了“用一个框架解决所有问题”而牺牲系统的最佳适配性。
  • 误区三：忽略许可与供应链合规。不同框架虽然都声称 MIT/Apache 2.0，但需仔细阅读实际许可条款，避免引入隐含的商业限制。
  • 误区四：忽视协议扩展性。当下选择的框架是否支持 MCP/A2A，决定了未来能否与更广泛的 Agent 生态系统互操作。

六、未来趋势 ​

6.1 “微服务化”趋势 ​

正如软件架构从单体应用演进为微服务，Agent 框架也在从“单体 Agent”向“Agent Mesh”演进。A2A 协议的广泛采用和 MCP 的持续迭代，正在促成跨框架、跨平台、跨供应商的“Agent 群体智能”成为现实。Gartner 预测超过 15% 的日常工作决策将交由 AI 智能体自主完成，这一预测正在加速兑现。

6.2 框架收敛与专业化分工 ​

从 2024 年的“寒武纪大爆发”到 2026 年的优胜劣汰与加速整合，Agent 框架领域已经完成了从百花齐放到格局初定的过渡。未来演进将呈现两条并行路径：

  • 收敛：少数核心框架（LangGraph、CrewAI、MAF）确立行业主导地位，形成标准的工程化模式
  • 专业化：针对特定语言生态、特定使用场景的轻量级框架继续繁荣，满足差异化需求

6.3 协议驱动的互操作时代 ​

2026 年是 Agent 互操作协议走向成熟的关键年份。A2A 从概念到 150+ 组织生产级部署仅用了一年时间；MCP 从协议走向无状态化演进。这些标准化协议构筑了 Agent 生态的“通用语言”基础设施，跨供应商、跨框架的 Agent 协作正在从愿景变为日常实践。

6.4 从“框架竞争”到“平台竞争” ​

各大厂商（微软、Google、AWS）正在将 Agent 框架与各自的云平台深度绑定。微软的 Microsoft Foundry Agent Service、Google 的 Gemini Enterprise Agent Platform 和 Amazon Bedrock AgentCore 都是这一趋势的缩影。框架选型不仅是技术选择，也意味着对特定云生态的战略绑定。未来 Agent 开发的竞争格局将越来越体现为“全栈平台能力”的竞争。

七、总结 ​

本笔记系统梳理了 AI Agent 框架的核心知识体系，归纳要点如下：

  1. 框架定义与分类：Agent 框架是构建、编排和部署 AI 智能体系统的软件基础设施。2026 年的主流框架可分为确定性控制（LangGraph、CrewAI）、自适应学习（AutoGen）和混合架构（MAF）三大技术流派。

  2. LangChain 1.0：通过 create_agent 统一入口、标准化内容块和 LangGraph 底层运行时，实现了 Agent 架构从碎片化到标准化的关键跨越，主包体积减少 40%，代码量减少 55%。

  3. LangGraph：以状态图为核心的 Agent 运行时引擎，通过状态、节点、边三要素建模执行流程，支持动态路由、多节点合并和持久化执行。1.0 GA 已为 Uber、LinkedIn、Klarna 等企业提供生产支撑。

  4. CrewAI：角色驱动的多智能体协作框架，采用五层模型（工具 → 代理 → 任务 → 流程 → 团队）实现组件解耦。GitHub 44.7k 星标，被近半数世界 500 强企业采用。

  5. 微软生态：AutoGen 开创了“群聊式”多智能体范式，现已并入 Microsoft Agent Framework（v1.0 发布于 2026 年 4 月）。MAF 统一了 Agent 抽象、Workflow 抽象和 Skills 封装三大能力，成为 AutoGen 和 Semantic Kernel 的推荐继任者。AutoGen 已进入维护模式，新项目建议直接使用 MAF。

  6. 互操作协议：MCP（Agent-工具连接）与 A2A（Agent-Agent 协作）形成互补。A2A 已获 150+ 组织生产部署，由 Linux 基金会管理，v1.0 于 2026 年 3 月发布。

  7. 选型建议：有状态长周期任务→LangGraph；角色分工团队→CrewAI；企业级 .NET/Python 混合部署→MAF；TypeScript 生态→Mastra；低代码快速搭建→Coze；新项目避坑→避免在 AutoGen 上继续开发。

  8. 未来趋势：从“单体 Agent”向“Agent Mesh”演进，协议驱动的互操作成为基础设施，框架与云平台深度绑定的“全栈竞争”加速，框架收敛与专业化分工并行。

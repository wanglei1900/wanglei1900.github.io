GitLab CI/CD 与 .gitlab-ci.yml 详解学习笔记 ​

一、CI/CD 基础概念 ​

1.1 持续集成（CI） ​

  • 定义：频繁将代码集成到主干分支（通常每天多次）
  • 目标：尽早发现集成错误
  • 核心实践：
    • 代码提交触发自动构建
    • 运行自动化测试套件
    • 快速反馈构建状态

1.2 持续交付（CD） ​

  • 定义：确保代码始终处于可部署状态
  • 目标：快速、可靠地发布软件
  • 核心实践：
    • 自动化部署流程
    • 环境配置管理
    • 发布审批流程

1.3 GitLab CI/CD 架构 ​

GitLab Repository
    ↓ (触发事件)
GitLab CI/CD Pipeline
    ↓
GitLab Runner（执行器）
    ↓
Jobs（具体任务）

二、GitLab CI/CD 核心概念 ​

2.1 Pipeline（流水线） ​

  • 一次完整的CI/CD执行流程
  • 由特定事件触发（push、merge request等）
  • 包含多个Stage和Job

2.2 Stage（阶段） ​

  • 定义Job的执行顺序
  • 相同Stage的Job并行执行
  • 不同Stage的Job串行执行
  • 默认阶段：.pre → build → test → deploy → .post

2.3 Job（作业/任务） ​

  • Pipeline的最小执行单元
  • 包含具体的执行脚本
  • 每个Job必须属于一个Stage

2.4 Runner（执行器） ​

  • 实际执行Job的代理
  • 类型：
    • Shared Runner：共享给所有项目
    • Group Runner：群组级别
    • Specific Runner：项目级别
  • 执行器类型：
    • Shell
    • Docker
    • Kubernetes
    • SSH

三、.gitlab-ci.yml 文件结构详解 ​

3.1 基础结构示例 ​

yaml
# 定义流水线阶段
stages:
  - build
  - test
  - deploy

# 定义变量（可在所有作业中使用）
variables:
  DOCKER_IMAGE: "registry.example.com/myapp"
  NODE_VERSION: "16"

# 定义缓存（加速后续构建）
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/
    - .npm/
  policy: pull-push

# 定义工件（Artifacts）
artifacts:
  paths:
    - dist/
    - reports/
  expire_in: 1 week

# 预定义模板（可被其他作业继承）
.base_template:
  image: node:${NODE_VERSION}
  before_script:
    - npm ci --cache .npm --prefer-offline
    - echo "Starting job for $CI_JOB_NAME"

# 具体作业定义
build_job:
  extends: .base_template
  stage: build
  script:
    - npm run build
    - echo "Build completed successfully"
  artifacts:
    paths:
      - dist/
    reports:
      junit: test-results/junit.xml
  only:
    - merge_requests
    - main
    - develop

test_unit:
  extends: .base_template
  stage: test
  script:
    - npm run test:unit
    - npm run coverage
  coverage: '/Statements\s*:\s*([^%]+)/'
  artifacts:
    reports:
      junit: test-results/unit-tests.xml
      cobertura: coverage/cobertura-coverage.xml

test_integration:
  extends: .base_template
  stage: test
  script:
    - npm run test:integration
  services:
    - postgres:13-alpine
    - redis:alpine
  variables:
    POSTGRES_DB: myapp_test
    POSTGRES_USER: runner
    POSTGRES_PASSWORD: password
    REDIS_URL: redis://redis:6379
  environment: test
  artifacts:
    paths:
      - integration-test-results/

deploy_staging:
  stage: deploy
  image: alpine:latest
  script:
    - apk add --no-cache openssh-client rsync
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | ssh-add -
    - mkdir -p ~/.ssh
    - chmod 700 ~/.ssh
    - rsync -avz -e "ssh -o StrictHostKeyChecking=no" dist/ user@staging-server:/var/www/app/
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - main
  when: manual
  dependencies:
    - build_job

deploy_production:
  stage: deploy
  image: docker:20.10
  services:
    - docker:dind
  variables:
    DOCKER_HOST: tcp://docker:2375
    DOCKER_TLS_CERTDIR: ""
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $DOCKER_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $DOCKER_IMAGE:$CI_COMMIT_SHORT_SHA
    - docker tag $DOCKER_IMAGE:$CI_COMMIT_SHORT_SHA $DOCKER_IMAGE:latest
    - docker push $DOCKER_IMAGE:latest
    # 滚动更新生产环境
    - kubectl set image deployment/myapp app=$DOCKER_IMAGE:$CI_COMMIT_SHORT_SHA -n production
  environment:
    name: production
    url: https://example.com
  only:
    - main
  when: manual
  needs:
    - test_unit
    - test_integration

四、关键配置详解 ​

4.1 Stages 配置 ​

yaml
# 自定义阶段顺序
stages:
  - .pre          # 特殊阶段：在所有阶段前执行
  - validate      # 代码验证
  - build         # 构建
  - security_scan # 安全扫描
  - test          # 测试
  - staging       # 预发布
  - production    # 生产发布
  - .post         # 特殊阶段：在所有阶段后执行

4.2 Job 控制流 ​

条件执行 ​

yaml
job1:
  # 传统方式（已逐渐被rules替代）
  only:
    - main
    - /^feature-.*$/
    - merge_requests
  except:
    - schedules
    - web

  # 推荐方式：rules（更灵活）
  rules:
    # 如果提交到main分支，且是合并请求
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"'
      when: always
    
    # 如果标签以v开头
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: on_success
    
    # 如果是计划任务
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
      when: manual
    
    # 默认规则
    - when: never

4.4 缓存和工件（Artifacts） ​

缓存配置 ​

yaml
cache:
  # 按分支缓存
  key: ${CI_COMMIT_REF_SLUG}
  
  # 更细粒度的key
  key:
    files:
      - package-lock.json
    prefix: ${CI_COMMIT_REF_SLUG}
  
  paths:
    - node_modules/
    - .npm/
    - .cache/
  
  # 缓存策略
  policy: pull-push  # 默认：下载并上传
  # policy: pull      # 只下载不上传
  # policy: push      # 只上传不下载
  # policy: undefined # 不使用缓存
  
  # 设置缓存失效时间
  untracked: true
  when: on_success

工件配置 ​

yaml
build:
  artifacts:
    # 指定路径
    paths:
      - dist/
      - build/
      - reports/
    
    # 排除文件
    exclude:
      - dist/**/*.map
      - node_modules/
    
    # 过期时间
    expire_in: 30 days
    
    # 工件名称
    name: "$CI_COMMIT_REF_NAME-build"
    
    # 依赖工件
    dependencies:
      - test
    
    # 工件类型
    reports:
      junit: test-results/junit.xml
      cobertura: coverage/cobertura-coverage.xml
      terraform: terraform-plan.json
    
    # 发布条件
    when: on_success
    expose_as: "Build Output"

trigger_docker_build:

  stage: test

8.1 完整的微服务流水线 ​

yaml
# .gitlab-ci.yml for microservice
include:
  - template: Security/SAST.gitlab-ci.yml
  - template: Security/Dependency-Scanning.gitlab-ci.yml

variables:
  DOCKER_REGISTRY: $CI_REGISTRY
  SERVICE_NAME: $CI_PROJECT_NAME
  DOCKER_IMAGE: $DOCKER_REGISTRY/$CI_PROJECT_PATH

stages:
  - validate
  - test
  - build
  - security
  - package
  - deploy

.validate_template:
  image: alpine:latest
  before_script:
    - apk add --no-cache git

validate_code:
  extends: .validate_template
  stage: validate
  script:
    - git diff --check $CI_MERGE_REQUEST_TARGET_BRANCH_SHA $CI_COMMIT_SHA
    - echo "Code validation passed"

lint:
  extends: .validate_template
  stage: validate
  image: node:16-alpine
  script:
    - npm ci
    - npm run lint
  cache:

unit_tests:

integration_tests:

  variables:
    NODE_ENV: test

build_docker:
  stage: build
  image: docker:20.10
  services:
    - docker:20.10-dind
  variables:
    DOCKER_TLS_CERTDIR: ""
    DOCKER_BUILDKIT: "1"
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - |
      docker build \
        --build-arg NODE_ENV=production \
        --cache-from $DOCKER_IMAGE:latest \
        --tag $DOCKER_IMAGE:$CI_COMMIT_SHA \
        --tag $DOCKER_IMAGE:latest \

    - docker push $DOCKER_IMAGE:$CI_COMMIT_SHA
    - docker push $DOCKER_IMAGE:latest
  only:
    - main
    - merge_requests

deploy_staging:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - |
      kubectl set image deployment/$SERVICE_NAME \
        $SERVICE_NAME=$DOCKER_IMAGE:$CI_COMMIT_SHA \
        -n staging
    - kubectl rollout status deployment/$SERVICE_NAME -n staging
  environment:
    name: staging
    url: https://staging.example.com
  only:
    - main

deploy_production:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - |
      # 蓝绿部署策略
      kubectl apply -f k8s/production-blue.yaml
      kubectl rollout status deployment/$SERVICE_NAME-blue -n production

    name: production
    url: https://example.com
  when: manual
  only:
    - tags

十、最佳实践总结 ​

  1. 保持配置文件简洁：使用include和extends复用配置
  2. 安全第一：使用CI/CD变量存储敏感信息，启用安全扫描
  3. 快速反馈：将重要测试放在流水线前段
  4. 资源优化：合理使用缓存，设置并行和矩阵构建
  5. 环境一致性：使用容器确保环境一致
  6. 监控和日志：收集构建指标，设置合理的超时时间
  7. 渐进式部署：使用蓝绿部署或金丝雀发布
  8. 文档化：在配置中添加注释说明

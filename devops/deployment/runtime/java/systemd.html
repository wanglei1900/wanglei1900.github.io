学习笔记：应用运行时部署 - Java生态 & Systemd服务化 ​

核心目标 ​

将传统的通过 java -jar 命令行启动的 Java 应用（如 Spring Boot、Tomcat 应用、JAR/WAR 包），转变为由 Systemd 管理的、具备生产级特性的系统服务。实现开机自启、高可用、集中化日志、资源管控和便捷的生命周期管理。

第一部分：为什么选择 Systemd 管理 Java 应用？ ​

1.1 传统部署方式的痛点 ​

  • 手工操作：依赖人工 SSH 登录执行 nohup java -jar & 或写简易 shell 脚本。
  • 无高可用：进程意外退出后不会自动重启。
  • 缺乏管控：难以方便地查看状态、停止、重启或设置资源限制（CPU、内存）。
  • 日志混乱：控制台日志通常重定向到文件，难以切割、归档和集中查看。
  • 依赖启动顺序：无法很好地处理应用依赖的服务（如数据库、缓存）就绪后再启动。
  • 非标准：难以与现有的运维体系（监控、告警、配置管理）集成。

1.2 Systemd 带来的优势 ​

  • 标准化服务管理：统一的 systemctl start/stop/restart/status <service> 命令。
  • 自动重启：可配置进程崩溃、异常退出后的重启策略（如 on-failure）。
  • 开机自启：通过 systemctl enable 简单设置。
  • 资源管理与隔离：可以方便地设置 CPU 权重、内存限制、文件句柄数等（通过 CGroup）。
  • 集成化日志：标准输出和错误会自动接入 Journal，可通过 journalctl 统一查看、筛选和持久化。
  • 依赖与顺序：可声明性地配置服务启动顺序（After=, Requires=）。
  • 安全增强：可以以非 root 用户运行，限制文件系统访问范围，降低安全风险。
  • 状态与探活：支持定义健康检查命令，并与服务状态关联。

第二部分：部署前准备 ​

2.1 环境与权限 ​

  1. 操作系统：主流的 Linux 发行版（如 CentOS 7+, RHEL, Ubuntu 16.04+, Debian 8+），它们已默认使用 Systemd。
  2. Java 环境：
    • 安装 JDK 8 或更高版本（建议使用稳定版本，如 OpenJDK 11/17 LTS）。
    • 通过 java -version 验证。
    • 建议将 JAVA_HOME 设置为全局环境变量（例如在 /etc/environment 或 /etc/profile.d/java.sh 中）。
  3. 应用准备：
    • 准备好最终的可执行 JAR 包或 WAR 包（例如 myapp-1.0.0.jar）。
    • 清晰的应用配置文件（如 application.yml, application-prod.properties），建议将其与 JAR 包分离存放。

2.2 目录结构规划（推荐） ​

一个清晰、符合 Linux 标准的目录结构有利于维护。

bash
# 创建应用专用用户和组（非 root，安全考虑）
sudo groupadd -r appgroup
sudo useradd -r -s /bin/false -g appgroup appuser

# 创建应用目录
sudo mkdir -p /opt/myapp                         # 主目录
sudo mkdir -p /opt/myapp/logs                    # 应用自定义日志（如果需要）
sudo mkdir -p /opt/myapp/config                  # 配置文件目录
sudo mkdir -p /var/lib/myapp                     # 数据目录（如 SQLite 数据库、上传文件等）
sudo mkdir -p /opt/myapp/bin                     # 启动脚本（备用）

# 复制应用文件
sudo cp myapp-1.0.0.jar /opt/myapp/
sudo cp application-prod.yml /opt/myapp/config/

# 设置权限
sudo chown -R appuser:appgroup /opt/myapp /var/lib/myapp
sudo chmod 750 /opt/myapp
sudo chmod 640 /opt/myapp/config/*.yml           # 配置文件通常不需执行权限

第三部分：核心实践 - 编写 Systemd Unit 文件 ​

3.1 Unit 文件位置 ​

  • 系统级服务：/etc/systemd/system/ （推荐放置在这里，优先级最高）
  • 我们在此创建服务文件：sudo vim /etc/systemd/system/myapp.service

3.2 详解一个完整的 Unit 文件模板 ​

ini
[Unit]
Description=My Awesome Java Application        # 服务描述
Documentation=https://wiki.mycompany.com/myapp # 可选的文档链接
After=syslog.target network.target             # 在哪些系统目标之后启动
Requires=network.target                        # 强依赖，此服务失败会导致本服务失败
Wants=postgresql.service                       # 弱依赖，希望此服务启动，但不强制
After=postgresql.service                       # 确保在 PostgreSQL 之后启动

[Service]
Type=simple                                    # 核心类型：simple（默认）、forking、notify
User=appuser                                   # 以哪个用户运行
Group=appgroup                                 # 以哪个用户组运行

# 关键：设置环境变量，特别是 JAVA_HOME 和应用参数
Environment="JAVA_HOME=/usr/lib/jvm/java-11-openjdk"
Environment="APP_HOME=/opt/myapp"
Environment="SPRING_PROFILES_ACTIVE=prod"      # Spring Boot 激活的配置文件
Environment="JAVA_OPTS=-Xms512m -Xmx1024m -XX:+UseG1GC -Djava.security.egd=file:/dev/./urandom"
Environment="APP_CONFIG=/opt/myapp/config/application-prod.yml"

# 工作目录，相对路径会基于此目录
WorkingDirectory=/opt/myapp

# 启动命令 - 最核心的部分
# ExecStart 必须是一个前台进程（不能是后台的 &）
ExecStart=${JAVA_HOME}/bin/java \
          $JAVA_OPTS \
          -jar ${APP_HOME}/myapp-1.0.0.jar \
          --spring.config.location=${APP_CONFIG}

# 优雅停止信号和超时（Spring Boot 默认监听 SIGTERM）
ExecStop=/bin/kill -s TERM $MAINPID
KillMode=process                                # 只杀主进程，不杀整个进程组
SuccessExitStatus=143                           # SIGTERM (128+15) 也被认为是成功退出
TimeoutStopSec=30                               # 停止超时时间

# 重启策略
Restart=on-failure                             # 在非正常退出（非0，非信号杀死）时重启
RestartSec=10s                                 # 重启前等待时间
StartLimitInterval=60s
StartLimitBurst=3                              # 60秒内最多重启3次，超过则放弃

# 资源限制（通过 CGroup）
LimitNOFILE=65536                              # 最大打开文件数
LimitNPROC=4096                                # 最大进程数
LimitMEMLOCK=infinity
# MemoryMax=1G                                 # systemd v227+，最大内存（硬限制）
# MemoryHigh=800M                              # systemd v227+，内存建议限制（软限制）

# 安全加固（可选）
NoNewPrivileges=yes
PrivateTmp=yes                                 # 使用私有的 /tmp 和 /var/tmp
ProtectSystem=strict                           # 严格保护系统目录（只读）
ReadWritePaths=/var/lib/myapp                  # 明确指定可写的应用数据目录

# 日志重定向到 Journal（可选，默认已做）
# StandardOutput=journal
# StandardError=journal

[Install]
WantedBy=multi-user.target                     # 系统以多用户模式启动时，启用此服务

3.3 重点参数解析 ​

  • Type=simple：Systemd 认为启动命令（ExecStart）将是前台进程。这是 Spring Boot Executable Jar 的正确选择。
  • Type=forking：如果使用传统的启动脚本，脚本会 fork 出子进程后自己退出，则需要用这个类型，并指定 PIDFile=。
  • Environment：这是为服务设置环境变量的最佳方式，尤其是 JAVA_OPTS。
  • Restart=on-failure：生产环境常用，确保应用崩溃后能自动恢复。
  • SuccessExitStatus=143：Java 应用收到 SIGTERM（kill -15）会正常关闭并退出码为 143，让 Systemd 知道这是正常停止，不应触发 Restart。
  • LimitNOFILE：非常重要！防止文件描述符耗尽，尤其是高并发应用。
  • 安全选项：PrivateTmp, ProtectSystem 等能有效限制应用权限，实现沙箱化。

第四部分：服务生命周期管理 ​

4.1 加载与启用 ​

bash
# 重新加载 systemd 配置，使新的 unit 文件生效
sudo systemctl daemon-reload

# 启动服务
sudo systemctl start myapp.service

# 设置开机自启
sudo systemctl enable myapp.service

# 查看服务状态（最重要、最常用的命令）
sudo systemctl status myapp.service
# 输出示例：
# ● myapp.service - My Awesome Java Application
#    Loaded: loaded (/etc/systemd/system/myapp.service; enabled; vendor preset: disabled)
#    Active: active (running) since Mon 2023-10-16 10:00:00 UTC; 5s ago
#      Docs: https://wiki.mycompany.com/myapp
#  Main PID: 12345 (java)
#    CGroup: /system.slice/myapp.service
#            └─12345 /usr/lib/jvm/java-11-openjdk/bin/java -Xms512m -Xmx1024m ... -jar /opt/myapp/myapp-1.0.0.jar

4.2 日常操作 ​

bash
# 停止服务
sudo systemctl stop myapp

# 重启服务（先stop再start）
sudo systemctl restart myapp

# 只重新加载配置（如果应用支持，如 Spring Boot Actuator 的 `/refresh` 端点）
# 通常需要配合自定义机制，Systemd 本身不支持配置热重载。
# 更常见的方法是：`systemctl restart myapp`

# 查看启动日志（最后若干行）
sudo journalctl -u myapp -n 50 -f   # -f 实时跟踪

4.3 查看与监控日志 ​

bash
# 查看此服务的所有日志
sudo journalctl -u myapp

# 查看今天的日志
sudo journalctl -u myapp --since today

# 查看特定时间段的日志，并按优先级过滤
sudo journalctl -u myapp --since "2023-10-16 09:00:00" --until "2023-10-16 10:00:00" -p err

# 以 JSON 格式输出，便于日志采集器（如 Filebeat）抓取
sudo journalctl -u myapp -o json

# 将日志持久化到文件（需要在 `/etc/systemd/journald.conf` 中配置 Storage=persistent）

第五部分：高级主题与最佳实践 ​

5.1 支持部署多实例 ​

有时需要在一台机器上部署同一个应用的多个实例（例如，不同端口）。

  • 方法：使用 Systemd 的 模板 Unit 文件。
  • 创建：/etc/systemd/system/myapp@.service
  • 内容：在 Unit 文件中使用 %i 作为实例标识符。
ini
[Service]
...
Environment="APP_INSTANCE=%i"
Environment="SERVER_PORT=808${i}" # 实例 myapp@1 的端口为 8081
ExecStart=${JAVA_HOME}/bin/java ... --server.port=${SERVER_PORT}
WorkingDirectory=/opt/myapp-%i    # 每个实例有独立目录
User=appuser-%i                   # 每个实例使用独立用户（更安全）
...
  • 管理：
    bash
    sudo systemctl start myapp@1
sudo systemctl start myapp@2
sudo systemctl enable myapp@1 myapp@2

5.2 与外部配置中心结合 ​

  • 原则：将易变的配置（数据库URL、密码、功能开关）外置。
  • 实现：
    1. 在 JAVA_OPTS 中通过 -D 参数指定配置中心地址或外部配置文件路径。
    2. 使用 Spring Cloud Config、Apollo、Nacos 等。
    3. 确保启动时网络可用（After=network.target），并考虑配置中心未就绪的重试策略（可能需要自定义启动脚本）。

5.3 健康检查与集成 ​

  • Spring Boot Actuator：暴露 /actuator/health 端点。
  • Systemd 集成：Systemd 可以通过 ExecStartPost 运行一个脚本来调用健康端点，并根据结果影响服务状态，但这并非原生完美支持。更常见的做法是：
    • 监控工具（如 Prometheus Blackbox Exporter）定期探活。
    • 使用 systemctl is-active myapp 检查服务是否在运行。

5.4 资源限制调优 ​

  • 内存（Xmx）：JAVA_OPTS 中的 -Xmx 必须小于 Systemd 设置的 MemoryMax（如果设置了），否则 Java 会先于 Systemd 触发 OOM。
  • CPU：使用 CPUQuota=150% 来限制一个服务最多使用 1.5 个核心的 CPU 时间。
  • 磁盘 I/O：IOWeight, LimitIOPS 等（较新版本 Systemd 支持）。

第六部分：故障排查指南 ​

  1. 服务启动失败 (systemctl status 显示 failed)：

    • 首要命令：sudo journalctl -u myapp -xe 查看详细错误。
    • 常见原因：
      • 权限问题：检查 User/Group，以及应用目录和文件的权限。
      • Java 命令未找到：检查 JAVA_HOME 环境变量。
      • JAR 包路径错误：检查 ExecStart 中的路径。
      • 端口已被占用：检查 SERVER_PORT。
      • 依赖服务未就绪：检查 After 和 Requires 的服务状态。

  2. 服务不断重启 (Restart=on-failure 循环)：

    • 查看 journalctl -u myapp 找到崩溃前的最后一个异常。
    • 可能是应用内 Bug、内存泄漏（OOM）、数据库连接池耗尽等。
    • 临时停止重启以调试：sudo systemctl edit myapp.service，在覆盖文件中添加 [Service]\nRestart=no，然后 sudo systemctl restart myapp。

  3. 无法优雅停止（stop 超时）：

    • 检查应用是否正确处理 SIGTERM。Spring Boot 默认会。
    • 增加 TimeoutStopSec。
    • 检查 KillMode，如果设为 mixed 或 control-group 可能杀死了不该杀的子进程。

总结 ​

将 Java 应用通过 Systemd 服务化部署，是从“可运行”到“可生产运维”的关键一步。它提供了标准化、健壮性、可观察性和可控性。遵循本笔记中的目录规划、Unit 文件编写规范和最佳实践，可以构建出稳定、易于维护的 Java 应用运行时环境。

核心工作流：

  1. 规划目录与用户 -> 2. 编写详细的 myapp.service 文件 -> 3. daemon-reload -> 4. start & enable -> 5. 通过 status 和 journalctl 验证 -> 6. 纳入监控与配置管理。

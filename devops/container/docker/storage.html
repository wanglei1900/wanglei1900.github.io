Docker 存储驱动选择 - 完整学习笔记 ​

一、存储驱动核心概念 ​

1.1 什么是存储驱动？ ​

  • 定义：Docker 用来管理镜像层和容器层数据的技术实现
  • 作用：实现联合文件系统（Union File System），支持写时复制（CoW）和用时复制（CuW）
  • 位置：位于 /var/lib/docker/<storage-driver>/

1.2 关键特性对比 ​

特性写时复制 (Copy-on-Write)用时复制 (Copy-on-Read)
原理修改时才复制底层数据读取时复制到可写层
性能写操作较慢，读操作快读操作较慢，写操作快
适用场景频繁读，少量写频繁写，少量读
典型驱动overlay2, aufsdevicemapper (旧版)

二、主流存储驱动详解 ​

2.1 Overlay2（推荐默认驱动） ​

2.1.1 架构原理 ​

容器视图（merged）    ← 用户看到的统一文件系统
    │
容器层（upperdir）    ← 可写层，存放修改
    │
镜像层（lowerdir）    ← 只读层，可多个镜像层叠加
    │
基础层（workdir）     ← 内部工作目录

2.1.2 目录结构 ​

bash
/var/lib/docker/overlay2/
├── l/                    # 硬链接目录，减少磁盘占用
│   ├── 6Y...            # 指向镜像层的硬链接
│   └── 7Z...
├── <layer-id>           # 镜像层目录
│   ├── diff/            # 该层内容变更
│   └── link             # 指向硬链接的名称
└── <container-id>       # 容器层目录
    ├── diff/            # 容器修改内容
    ├── merged/          # 统一视图挂载点
    ├── upper/           # 可写层（同diff）
    └── lower/           # 指向所有底层镜像层

2.1.3 性能特征 ​

  • 优点：
    • 高性能，接近原生文件系统
    • 支持最多128层镜像（实际测试更多）
    • 内存使用少
    • 与Page Cache良好协作
  • 缺点：
    • inode耗尽问题（需监控）
    • 需要Linux内核4.0+（推荐4.0+）

2.1.4 配置示例 ​

bash
# 查看当前驱动
docker info | grep "Storage Driver"

# 配置overlay2（/etc/docker/daemon.json）
{
  "storage-driver": "overlay2",
  "storage-opts": [
    "overlay2.override_kernel_check=true",
    "overlay2.size=20G",           # 限制单个容器大小
    "overlay2.mountopt=nodev"      # 挂载选项
  ]
}

2.2 AUFS（Advanced Multi-Layered Unification Filesystem） ​

2.2.1 架构原理 ​

读写层 (容器层)    ← 容器修改保存于此
    │
  分支层           ← 镜像层，可多个分支
    │
只读层 (基础镜像)   ← 最底层

2.2.2 目录结构 ​

bash
/var/lib/docker/aufs/
├── diff/                    # 各层内容
│   ├── <layer-id>          # 每层独立的修改
│   └── ...
├── layers/                 # 层关系映射
│   ├── <layer-id>          # 记录该层的父层
│   └── ...
├── mnt/                    # 挂载点
│   ├── <container-id>      # 容器合并视图
│   └── ...

2.2.3 性能特征 ​

  • 优点：
    • 稳定成熟（Docker早期默认）
    • 内存效率高
    • 支持大量容器
  • 缺点：
    • 未并入内核主线（需额外安装）
    • 最大层数限制：127层
    • 性能低于overlay2（尤其大量小文件）
    • 不支持XFS，仅支持ext4

2.2.4 适用场景 ​

  • Ubuntu/Debian系统（内核不支持overlay2时）
  • 传统部署环境
  • 稳定性优先的场景

2.3 DeviceMapper ​

2.3.1 两种模式对比 ​

模式直接模式 (direct-lvm)环回模式 (loop-lvm)
存储位置块设备（LVM）稀疏文件
性能生产环境推荐仅测试用途
扩容动态扩展固定大小
稳定性高低

2.3.2 架构原理（direct-lvm） ​

容器读写层 (thin pool) ← 动态分配空间
          │
    thin provisioning ← 精简配置
          │
 块设备 /dev/sdb1    ← LVM物理卷

2.3.3 配置示例（生产环境） ​

bash
# 1. 准备LVM
pvcreate /dev/sdb1
vgcreate docker /dev/sdb1

# 2. 创建thin pool
lvcreate --wipesignatures y -n thinpool docker -l 95%VG
lvcreate --wipesignatures y -n thinpoolmeta docker -l 1%VG
lvconvert -y --zero n -c 512K \
  --thinpool docker/thinpool \
  --poolmetadata docker/thinpoolmeta

# 3. 配置自动扩展
cat > /etc/lvm/profile/docker-thinpool.profile << EOF
activation {
  thin_pool_autoextend_threshold=80
  thin_pool_autoextend_percent=20
}
EOF
lvchange --metadataprofile docker-thinpool docker/thinpool

# 4. Docker配置
{
  "storage-driver": "devicemapper",
  "storage-opts": [
    "dm.thinpooldev=/dev/mapper/docker-thinpool",
    "dm.use_deferred_removal=true",
    "dm.use_deferred_deletion=true",
    "dm.fs=ext4",
    "dm.basesize=10G"
  ]
}

2.3.4 性能特征 ​

  • 优点：
    • 块级别操作，适合I/O密集型
    • 支持高级存储特性（快照、瘦分配）
    • RHEL/CentOS官方支持
  • 缺点：
    • 配置复杂
    • 存储池可能耗尽（需监控）
    • 内存使用较高

2.4 Btrfs ​

2.4.1 架构原理 ​

子卷 (subvolume) 结构：
/var/lib/docker/btrfs/
├── subvolumes/           # 每个容器/镜像一个子卷
│   ├── <container-id>    ← 可写快照
│   └── <image-id>        ← 只读快照
└── snapshots/           # 快照管理

2.4.2 配置示例 ​

bash
# 1. 准备Btrfs文件系统
mkfs.btrfs /dev/sdb1
mount -o compress=zstd /dev/sdb1 /var/lib/docker

# 2. Docker配置
{
  "storage-driver": "btrfs",
  "storage-opts": [
    "btrfs.min_space=1G"
  ]
}

2.4.3 性能特征 ​

  • 优点：
    • 内置压缩（zstd, lzo, zlib）
    • 写时复制效率高
    • 快照创建速度快
    • 数据校验和修复
  • 缺点：
    • 稳定性争议（生产环境需谨慎）
    • 磁盘空间回收复杂
    • 需要专门的文件系统

2.5 ZFS ​

2.5.1 架构原理 ​

数据集 (dataset) 结构：
docker/
├── <image-id>@readonly   ← 镜像只读快照
├── <container-id>        ← 容器克隆（可写）
└── .children            ← 层级关系

2.5.2 配置示例 ​

bash
# 1. 准备ZFS池
zpool create -f zpool-docker /dev/sdb1
zfs create -o mountpoint=/var/lib/docker zpool-docker/docker

# 2. 配置属性
zfs set compression=lz4 zpool-docker/docker
zfs set atime=off zpool-docker/docker

# 3. Docker配置
{
  "storage-driver": "zfs",
  "storage-opts": [
    "zfs.fsname=zpool-docker/docker"
  ]
}

2.5.3 性能特征 ​

  • 优点：
    • 数据完整性保证
    • 高效的快照和克隆
    • 高级压缩选项
    • 去重功能（需大量内存）
  • 缺点：
    • 内存消耗大（尤其开启去重）
    • 配置复杂
    • 社区支持相对较少

3.2 工作负载适配建议 ​

3.2.1 Web应用/微服务 ​

yaml
推荐驱动: overlay2
理由:
  - 读多写少（配置文件、代码）
  - 快速启动和销毁
  - 内存占用小
配置优化:
  - 使用SSD存储
  - 合理设置层级（避免过多层）

3.2.2 数据库容器 ​

yaml
推荐方案: 数据卷 + overlay2
不推荐: 在存储驱动中存数据
理由:
  - 数据库需要持久化
  - 需要直接I/O访问
  - 避免CoW性能开销
配置:
  docker run -v /data/db:/var/lib/mysql mysql

3.2.3 高密度容器环境 ​

yaml
推荐驱动: overlay2
备选: aufs
理由:
  - 内存效率高
  - 支持大量容器并发
  - 层共享减少磁盘使用
监控重点:
  - inode使用率
  - 磁盘空间

3.2.4 I/O密集型应用 ​

yaml
推荐驱动: devicemapper (direct-lvm)
备选: 考虑主机存储+数据卷
理由:
  - 块级操作性能更好
  - 避免文件系统开销
注意事项:
  - 监控thin pool使用率
  - 设置合理的基础大小

四、存储驱动配置与调优 ​

4.1 诊断当前配置 ​

bash
# 1. 查看当前存储驱动
docker info --format '{{.Driver}}'

# 2. 查看详细存储信息
docker system df
docker system df -v

# 3. 检查文件系统使用
df -h /var/lib/docker
df -i /var/lib/docker  # inode使用情况

# 4. 查看容器存储详情
docker inspect <container> --format='{{.GraphDriver.Data}}'

4.2 切换存储驱动 ​

bash
# ⚠️ 警告：切换会删除现有容器和镜像！

# 1. 停止Docker服务
systemctl stop docker

# 2. 备份数据
cp -r /var/lib/docker /var/lib/docker.backup

# 3. 清理原有数据
rm -rf /var/lib/docker/*

# 4. 修改配置
cat > /etc/docker/daemon.json << EOF
{
  "storage-driver": "overlay2",
  "storage-opts": [
    "overlay2.override_kernel_check=true"
  ]
}
EOF

# 5. 启动服务
systemctl start docker

# 6. 验证切换
docker info | grep "Storage Driver"

4.3 性能调优参数 ​

4.3.1 Overlay2 调优 ​

json
{
  "storage-driver": "overlay2",
  "storage-opts": [
    "overlay2.size=20G",           // 限制容器大小
    "overlay2.mountopt=nodev,noexec,nosuid",  // 安全选项
    "overlay2.override_kernel_check=true"    // 跳过内核检查
  ],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }

4.3.2 DeviceMapper 调优 ​

json
{
  "storage-driver": "devicemapper",
  "storage-opts": [
    "dm.thinpooldev=/dev/mapper/docker-thinpool",
    "dm.use_deferred_removal=true",
    "dm.use_deferred_deletion=true",

  ]
}

4.4 监控与告警 ​

4.4.1 关键监控指标 ​

yaml
# Prometheus监控指标示例
docker_engine_daemon_storage_driver:
  - pool_blocks_used    # 存储块使用
  - pool_blocks_total   # 总存储块
  - pool_blocks_free    # 空闲块
  
docker_engine_daemon_storage_layer:
  - size_bytes         # 层大小
  - count             # 层数量

# 自定义监控脚本
#!/bin/bash
# 监控thin pool使用率
THIN_POOL=$(dmsetup status docker-thinpool | awk '{print $2}')
USED_BLOCKS=$(echo $THIN_POOL | cut -d'/' -f1)
TOTAL_BLOCKS=$(echo $THIN_POOL | cut -d'/' -f2)
USAGE_PERCENT=$((USED_BLOCKS * 100 / TOTAL_BLOCKS))
echo "Thin pool usage: ${USAGE_PERCENT}%"

4.4.2 告警阈值建议 ​

overlay2:
  - inode使用率 > 85%   → 警告
  - 磁盘使用率 > 80%    → 警告
  - 容器层数 > 50       → 警告

devicemapper:
  - thin pool使用率 > 80% → 警告
  - 元数据使用率 > 60%    → 警告
  - 数据块使用率 > 90%    → 紧急

五、常见问题与解决方案 ​

5.1 磁盘空间耗尽 ​

bash
# 1. 清理无用数据
docker system prune -a --volumes

# 2. 查找大容器/镜像
docker ps -s  # 查看容器大小
docker images --format "{{.Size}}\t{{.Repository}}" | sort -h

# 3. Overlay2特定清理
# 清理孤儿层
docker rmi $(docker images -q -f dangling=true)

# 4. DeviceMapper清理
# 清理thin pool空间
fstrim /var/lib/docker

5.2 性能下降排查 ​

bash
# 1. 检查I/O等待
iostat -x 1

# 2. 检查存储驱动状态
dmsetup status docker-thinpool  # devicemapper
cat /sys/fs/btrfs/<uuid>/space_info  # btrfs

# 3. 文件系统缓存
free -h
cat /proc/sys/vm/drop_caches  # 谨慎使用

# 4. 容器I/O限制检查
docker inspect <container> | grep -i blkio

# 切换后

bash

# 恢复数据卷

  alpine tar xzf /backup/backup.tar.gz -C /data

六、最佳实践总结 ​

6.1 选择决策树 ​

6.2 生产环境推荐配置 ​

yaml
通用场景:
  驱动: overlay2
  文件系统: XFS或ext4
  配置:
    - 使用SSD存储
    - 定期清理无用数据
    - 监控inode和磁盘使用

高I/O场景:
  驱动: devicemapper (direct-lvm)
  配置:
    - 独立磁盘或分区
    - 启用自动扩展
    - 设置合理的basesize

特殊需求:
  - 需要压缩: btrfs + lzo/zstd
  - 需要去重: zfs (内存充足)
  - 稳定性优先: overlay2 + ext4

存储驱动管理 ​

bash
# 查看驱动信息
docker info | grep -A5 "Storage"

# 查看详细存储统计
docker system df
docker system df -v

# 清理存储
docker system prune -a --volumes
docker builder prune  # 清理构建缓存

故障诊断 ​

bash
# 查看存储驱动日志
journalctl -u docker --since "1 hour ago"

# 检查内核模块
lsmod | grep -E "overlay|aufs|btrfs"

# 测试I/O性能（容器内）
docker run --rm -it alpine dd if=/dev/zero of=test bs=1M count=1000

性能测试 ​

bash
# 使用fio测试存储性能
docker run --rm -v /tmp:/tmp ljishen/fio \
  fio --name=test --directory=/tmp --ioengine=libaio \
  --rw=randwrite --bs=4k --numjobs=1 --size=1G --runtime=60 \
  --time_based --group_reporting

最终建议：对于大多数场景，overlay2 是最佳选择。它的性能、稳定性和社区支持都很好。特殊需求时再考虑其他驱动，并确保充分测试。记住：存储驱动只是Docker存储的一部分，合理使用数据卷对于生产环境至关重要。

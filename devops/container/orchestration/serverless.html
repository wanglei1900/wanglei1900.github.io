第一部分：Serverless 与 Knative 基础概念 ​

1.1 Serverless 演进历程 ​

物理服务器 → 虚拟机 → 容器 → 编排平台 → Serverless
演进特点：
├── 资源粒度：物理机 → VM → 容器 → 函数
├── 管理责任：全部自理 → 部分托管 → 完全托管
├── 计费模式：整机购买 → 按VM计费 → 按容器计费 → 按请求计费
└── 伸缩速度：数小时 → 数分钟 → 数秒 → 毫秒级

1.2 Serverless 核心特征 ​

四大核心特性：

  1. 零服务器管理：无需管理基础设施
  2. 弹性伸缩：自动从零扩展到无穷大
  3. 按使用付费：只为实际消耗的资源付费
  4. 高可用性：内置容错和自动恢复机制

三大实现模式：

yaml
# 1. 函数即服务 (FaaS)
- 事件驱动，执行单个函数
- 临时容器，冷启动问题
- 示例：AWS Lambda、Google Cloud Functions

# 2. 后端即服务 (BaaS)
- 托管的后端服务
- 数据库、认证、存储等
- 示例：Firebase、Supabase

# 3. 容器即服务 (CaaS)
- 基于容器的 Serverless
- 支持任意运行时
- 示例：Knative、Google Cloud Run

1.3 Knative 是什么？ ​

定义：基于 Kubernetes 的开源 Serverless 平台，提供构建、部署和管理现代 Serverless 工作负载所需的一组中间件组件。

核心价值主张：

  • Kubernetes 原生：完全基于 Kubernetes API 构建
  • 多云兼容：在任何 Kubernetes 集群上运行
  • 语言无关：支持任意容器化应用
  • 事件驱动：内置事件处理框架
  • 开发者友好：简化应用部署和运维

1.4 Knative 组件架构 ​

Knative 三大核心组件：
┌─────────────────────────────────────────┐
│          Knative Serving                 │
│  应用部署、扩缩容、流量管理、网络        │
├─────────────────────────────────────────┤
│          Knative Eventing                │
│  事件源、事件路由、事件处理              │
├─────────────────────────────────────────┤
│          Knative Functions (可选)         │
│  函数开发框架和工具链                    │
└─────────────────────────────────────────┘

依赖组件：
├── Istio / Contour / Kourier (网络层)
├── Cert-Manager (证书管理)
├── Tekton / Cloud Native Buildpacks (构建)
└── Metrics Server / KEDA (指标收集)

第二部分：Knative Serving 深度解析 ​

2.1 Serving 核心概念 ​

Service (ksvc) ​

yaml
# 核心概念：Knative Service 管理应用的全生命周期
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: hello-world
  namespace: default
spec:
  template:
    spec:
      containers:
        - image: gcr.io/knative-samples/helloworld-go
          env:
            - name: TARGET
              value: "World"
  # 流量管理配置
  traffic:
    - percent: 100
      latestRevision: true

Revision ​

yaml
# Revision：不可变的代码和配置快照
# 自动为每次配置变更创建新 Revision
apiVersion: serving.knative.dev/v1
kind: Revision
metadata:
  name: hello-world-00001
  labels:
    serving.knative.dev/service: hello-world
    serving.knative.dev/configuration: hello-world
    serving.knative.dev/configurationGeneration: "1"
spec:
  containerConcurrency: 0  # 并发数（0=无限）
  timeoutSeconds: 300     # 请求超时时间
  containers:
    - image: gcr.io/knative-samples/helloworld-go:v1

Configuration ​

yaml
# Configuration：Revision 的期望状态描述
apiVersion: serving.knative.dev/v1
kind: Configuration
metadata:
  name: hello-world-config
spec:
  template:
    spec:
      containers:
        - image: gcr.io/knative-samples/helloworld-go:v2

Route ​

yaml
# Route：流量路由和拆分规则
apiVersion: serving.knative.dev/v1
kind: Route
metadata:
  name: hello-world-route
spec:
  traffic:
    - revisionName: hello-world-00001
      percent: 90
      tag: v1
    - revisionName: hello-world-00002
      percent: 10
      tag: v2
    - latestRevision: true
      percent: 0  # 预留容量

2.2 Serving 核心特性 ​

自动扩缩容 (Autoscaler) ​

yaml
# Autoscaler 配置示例
apiVersion: autoscaling.internal.knative.dev/v1alpha1
kind: PodAutoscaler
spec:
  containerConcurrency: 10  # 每个容器并发请求数
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hello-world-deployment
  
# 扩展指标类型：
1. 并发请求数 (concurrency)
2. RPS (requests-per-second)
3. CPU 利用率
4. 内存利用率
5. 自定义指标

扩缩容策略配置：

yaml
# 通过注解配置扩缩容行为
annotations:
  # KPA (Knative Pod Autoscaler) 配置
  autoscaling.knative.dev/class: kpa.autoscaling.knative.dev
  autoscaling.knative.dev/metric: concurrency  # 或 rps
  autoscaling.knative.dev/target: "10"  # 目标并发数
  autoscaling.knative.dev/targetUtilizationPercentage: "70"
  
  # 扩缩容边界
  autoscaling.knative.dev/minScale: "1"     # 最小副本数
  autoscaling.knative.dev/maxScale: "50"    # 最大副本数
  
  # 扩缩容行为
  autoscaling.knative.dev/window: "60s"     # 稳定窗口
  autoscaling.knative.dev/panicWindowPercentage: "10.0"
  autoscaling.knative.dev/panicThresholdPercentage: "200.0"

从零扩展 (Scale-to-Zero) ​

yaml
# Scale-to-Zero 配置
annotations:
  autoscaling.knative.dev/minScale: "0"  # 启用从零扩展
  autoscaling.knative.dev/scaleToZeroPodRetentionPeriod: "30s"  # 优雅关闭期

# Scale-to-Zero 工作原理：
1. 没有流量时，副本数缩减到 0
2. Activator 接收所有入站请求
3. 新请求触发 Activator 启动新 Pod
4. 冷启动延迟：Pod 启动 + 应用启动时间

网络与路由 ​

yaml
# 网络配置注解
annotations:
  # 域名配置
  networking.knative.dev/visibility: cluster-local  # 或 external
  
  # TLS 配置
  networking.knative.dev/disablePublicTLS: "false"
  
  # 入口网关
  networking.knative.dev/ingress.class: "istio.ingress.networking.knative.dev"

# 默认域名模式：
# {service-name}.{namespace}.{cluster-domain}
# 示例：hello-world.default.example.com

3.1 Eventing 核心概念 ​

事件模型 ​

CloudEvents 标准 (CNCF 项目)：
{
  "specversion": "1.0",
  "type": "com.example.object.created",
  "source": "/projects/{project-id}",
  "id": "A234-1234-1234",
  "time": "2023-01-02T12:34:56.789Z",
  "datacontenttype": "application/json",
  "data": {
    "objectId": "12345",
    "action": "created"
  }
}

事件源 (Event Sources) ​

yaml
# PingSource 示例（定时事件源）
apiVersion: sources.knative.dev/v1
kind: PingSource
metadata:
  name: test-ping-source
spec:
  schedule: "*/1 * * * *"  # 每分钟
  data: '{"message": "Hello world!"}'
  sink:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: event-display

# APIServerSource 示例（K8s API 事件）
apiVersion: sources.knative.dev/v1
kind: ApiServerSource
metadata:
  name: k8s-events
spec:
  serviceAccountName: events-sa
  mode: Resource
  resources:
  - apiVersion: v1
    kind: Pod
  sink:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: pod-event-processor

Broker 和 Trigger ​

yaml
# Broker：事件路由中心
apiVersion: eventing.knative.dev/v1
kind: Broker
metadata:
  name: default
  annotations:
    eventing.knative.dev/broker.class: MTChannelBasedBroker
spec:
  config:
    apiVersion: v1
    kind: ConfigMap
    name: config-br-default-channel
    namespace: knative-eventing

# Trigger：事件过滤器
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: order-trigger
spec:
  broker: default
  filter:
    attributes:
      type: com.example.order.created
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: order-processor

3.2 Eventing 组件详解 ​

Channel ​

yaml
# Channel 类型：
1. InMemoryChannel：内存通道（开发测试）
2. KafkaChannel：Apache Kafka 后端
3. NatssChannel：NATS Streaming 后端
4. GoogleCloudPubSubChannel：GCP Pub/Sub

# Channel 配置示例
apiVersion: messaging.knative.dev/v1
kind: Channel
metadata:
  name: my-channel
  annotations:
    messaging.knative.dev/subscribable: v1
spec:
  channelTemplate:
    apiVersion: messaging.knative.dev/v1alpha1
    kind: KafkaChannel
    spec:
      numPartitions: 3
      replicationFactor: 1

Subscription ​

yaml
# Subscription：定义 Channel 到 Subscriber 的连接
apiVersion: messaging.knative.dev/v1
kind: Subscription
metadata:
  name: my-subscription
spec:
  channel:
    apiVersion: messaging.knative.dev/v1
    kind: Channel
    name: my-channel
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: message-handler
  # 重试策略
  delivery:
    deadLetterSink:
      ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: dead-letter-handler
    retry: 5
    backoffDelay: "PT1S"
    backoffPolicy: exponential

      name: myapp-v1

      - image: myapp:v1

    - percent: 100
      revisionName: myapp-v1

# 步骤2：部署新版本
# 更新服务配置
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: myapp
spec:
  template:
    metadata:
      name: myapp-v2
    spec:
      containers:
      - image: myapp:v2
  traffic:
    - percent: 0      # v2 暂不接收流量
      revisionName: myapp-v2
      tag: candidate
    - percent: 100    # 所有流量到 v1
      revisionName: myapp-v1

# 步骤3：逐步切换流量
kubectl apply -f - <<EOF
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: myapp
spec:
  traffic:
    - percent: 10     # 10% 流量到 v2
      revisionName: myapp-v2
    - percent: 90     # 90% 流量到 v1
      revisionName: myapp-v1
EOF

# 步骤4：完全切换
kubectl apply -f - <<EOF
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: myapp
spec:
  traffic:
    - percent: 100    # 所有流量到 v2
      revisionName: myapp-v2
      tag: current
    - percent: 0      # v1 作为回滚备选
      revisionName: myapp-v1
      tag: previous
EOF

学习路线建议 ​

初级阶段（1-2周） ​

  1. 理解 Serverless 概念和 Knative 架构
  2. 安装 Knative 并部署第一个服务
  3. 掌握 Knative Serving 基础：Service、Revision、Route
  4. 实践基本流量管理和自动扩缩容

中级阶段（2-3周） ​

  1. 掌握 Knative Eventing：Broker、Trigger、Event Source
  2. 实践蓝绿部署、金丝雀发布等部署策略
  3. 配置 TLS、域名、认证等生产特性
  4. 集成监控和日志系统

高级阶段（3-4周） ​

  1. 深入理解 Knative 内部架构和扩展机制
  2. 设计复杂的事件驱动架构
  3. 性能调优和成本优化
  4. 多集群部署和灾难恢复

专家阶段（持续） ​

  1. 贡献 Knative 社区
  2. 开发自定义事件源和扩展
  3. 大规模生产环境运维
  4. 与其他云原生技术深度集成

Kubernetes架构设计原理 深度解析 ​

一、Kubernetes 架构总览 ​

1.1 核心设计理念 ​

Kubernetes采用声明式API和控制器模式，遵循以下核心理念：

  • 声明式而非命令式：用户描述期望状态，系统负责实现和维护
  • 控制器模式：通过控制循环不断协调实际状态与期望状态
  • 解耦设计：组件松耦合，通过API进行通信
  • 可扩展性：所有核心功能都可被替换或扩展

二、控制平面（Control Plane）组件详解 ​

2.1 API Server (kube-apiserver) ​

核心功能：集群的统一入口，所有组件交互的中枢

设计特点： ​

  • 唯一可直连etcd的组件：确保数据一致性和安全性
  • RESTful API设计：支持HTTP/HTTPS，提供CRUD接口
  • 认证、授权、准入控制：
    • 认证：客户端证书、Bearer Token、基本认证等
    • 授权：RBAC、ABAC、Node授权等
    • 准入控制：Mutating/Validating Webhook
  • API版本管理：支持多版本共存和转换
  • Watch机制：实现事件监听和实时同步

内部架构： ​

go
// 简化的API Server处理流程
Request → Authentication → Authorization → Admission → Schema Conversion → Validation → etcd

2.2 etcd ​

分布式键值存储，Kubernetes的"唯一数据源"

关键特性： ​

  • 强一致性：使用Raft共识算法
  • 高可用性：通常部署3或5个节点
  • 数据模型：
    • 按路径组织：/registry/<资源类型>/<命名空间>/<资源名>
    • 例如：/registry/pods/default/my-pod
  • Watch支持：客户端可监听键变化
  • 事务支持：保证多键操作的原子性

数据存储结构： ​

/registry
├── pods
│   ├── default
│   │   ├── pod-1 → {pod spec}
│   │   └── pod-2 → {pod spec}
├── services
├── deployments
└── configmaps

2.3 Controller Manager (kube-controller-manager) ​

控制器的大本营，包含多个独立的控制循环

核心控制器： ​

控制器职责工作模式
Node Controller监控Node状态，处理Node故障周期性检查Node心跳
Replication Controller维护Pod副本数（已渐被ReplicaSet取代）监听RC对象变化
Deployment Controller管理Deployment的发布和回滚监听Deployment和ReplicaSet
StatefulSet Controller管理有状态应用的Pod保证Pod的顺序性和稳定性
DaemonSet Controller确保每个Node运行指定Pod监听DaemonSet和Node变化
Job/CronJob Controller管理批处理任务监听Job对象，创建Pod
Endpoint Controller维护Service与Pod的映射关系监听Service和Pod变化
Service Account Controller创建命名空间的默认ServiceAccount监听Namespace变化
Namespace Controller管理Namespace生命周期监听Namespace对象

控制器通用模式： ​

go
for {
    desiredState := getDesiredState()
    currentState := getCurrentState()
    if !reflect.DeepEqual(desiredState, currentState) {
        reconcile(desiredState, currentState)
    }
    time.Sleep(resyncPeriod)
}

2.4 Scheduler (kube-scheduler) ​

智能调度器，决定Pod运行在哪个Node

调度流程（两阶段设计）： ​

阶段1：过滤（Filtering）

所有节点 → 预选策略 → 可行节点列表

预选策略示例：

  • PodFitsResources：节点资源是否充足
  • PodFitsHostPorts：节点端口是否冲突
  • MatchNodeSelector：节点标签是否匹配
  • CheckNodeMemoryPressure：节点内存压力
  • NoVolumeZoneConflict：卷区域冲突检查

阶段2：评分（Scoring）

可行节点列表 → 优选策略打分 → 选择最高分节点

优选策略示例：

  • LeastRequestedPriority：选择资源请求最少的节点
  • BalancedResourceAllocation：平衡CPU和内存使用
  • NodeAffinityPriority：节点亲和性权重
  • TaintTolerationPriority：考虑污点和容忍

调度器扩展机制： ​

  • 调度器扩展（Scheduler Extender）：HTTP方式扩展调度逻辑
  • 多调度器：可运行多个调度器，Pod通过schedulerName指定
  • 调度框架（Scheduling Framework）：插件化架构，更灵活的扩展

三、工作节点（Node）组件详解 ​

3.1 Kubelet ​

节点代理，管理Pod生命周期

核心职责： ​

  1. Pod管理：

    • 通过文件、HTTP端点、API Server接收Pod定义
    • 创建、修改、删除容器
    • 监控容器状态和资源使用

  2. 容器运行时接口（CRI）：

    • 通过gRPC与容器运行时通信
    • 支持Docker、containerd、CRI-O等

  3. 容器网络接口（CNI）：

    • 配置Pod网络
    • 调用CNI插件设置网络命名空间

  4. 容器存储接口（CSI）：

    • 管理卷的挂载和卸载
    • 支持多种存储类型

  5. 节点状态报告：

    • 定期向API Server报告节点状态
    • 包括资源容量、分配情况、条件等

工作流程： ​

go
// 简化的Pod同步流程
func syncPod(pod *v1.Pod) {
    // 1. 计算Pod变化
    // 2. 停止不需要的容器
    // 3. 创建必要的沙箱（pause容器）
    // 4. 启动初始化容器（如有）
    // 5. 启动业务容器
    // 6. 执行postStart钩子（如有）
    // 7. 设置健康检查探针
}

3.2 Kube-proxy ​

网络代理，实现Service的负载均衡

三种工作模式： ​

1. userspace模式（已废弃）

  • 代理在用户空间运行
  • 性能较差，不推荐使用

2. iptables模式（默认）

bash
# 示例iptables规则
-A KUBE-SERVICES -d 10.96.0.1/32 -p tcp -m tcp --dport 443 -j KUBE-SVC-XXXX
-A KUBE-SVC-XXXX -m statistic --mode random --probability 0.3333 -j KUBE-SEP-AAA
-A KUBE-SVC-XXXX -m statistic --mode random --probability 0.5000 -j KUBE-SEP-BBB
-A KUBE-SVC-XXXX -j KUBE-SEP-CCC

优点：性能好，内核空间处理 缺点：规则线性查找，大规模集群性能下降

3. IPVS模式（推荐生产）

bash
# 使用IPVS负载均衡算法
ipvsadm -A -t 10.96.0.1:443 -s rr
ipvsadm -a -t 10.96.0.1:443 -r 10.244.1.2:8443 -m
ipvsadm -a -t 10.96.0.1:443 -r 10.244.2.3:8443 -m

优点：

  • 哈希表O(1)查找复杂度
  • 支持多种负载均衡算法（rr, wrr, lc, wlc等）
  • 更好的性能和可扩展性

3.3 容器运行时（Container Runtime） ​

容器执行环境，负责运行容器

架构演进： ​

传统：Docker → dockerd → containerd → runc
现代：Kubelet → CRI → containerd/CRI-O → runc

容器运行时接口（CRI）： ​

protobuf
service RuntimeService {
    rpc RunPodSandbox(RunPodSandboxRequest) returns (RunPodSandboxResponse) {}
    rpc StopPodSandbox(StopPodSandboxRequest) returns (StopPodSandboxResponse) {}
    rpc CreateContainer(CreateContainerRequest) returns (CreateContainerResponse) {}
    rpc StartContainer(StartContainerRequest) returns (StartContainerResponse) {}
}

service ImageService {
    rpc PullImage(PullImageRequest) returns (PullImageResponse) {}
    rpc ListImages(ListImagesRequest) returns (ListImagesResponse) {}
}

四、核心资源对象与API设计 ​

4.1 资源模型 ​

API分组（API Groups）： ​

核心组（无组名）：/api/v1
    - pods, services, nodes, namespaces, configmaps, secrets
    
命名组：/apis/<group>/<version>
    - apps/v1: deployments, daemonsets, statefulsets
    - networking.k8s.io/v1: ingresses, networkpolicies
    - storage.k8s.io/v1: storageclasses, csinodes
    - batch/v1: jobs, cronjobs
    - rbac.authorization.k8s.io/v1: roles, rolebindings

资源版本（API Versions）： ​

  1. Alpha版本 (v1alpha1)：默认禁用，可能包含bug
  2. Beta版本 (v1beta1)：默认启用，API可能变更
  3. 稳定版本 (v1)：长期支持，API保持兼容

4.2 Pod设计原理 ​

为什么需要Pod？ ​

  • 原子调度单位：容器组作为最小部署单元
  • 资源共享：同一Pod内容器共享：
    • 网络命名空间（localhost通信）
    • IPC命名空间（共享内存/信号量）
    • 存储卷（共享文件系统）
    • PID命名空间（可选）

Pod生命周期： ​

Pending → Running → Succeeded/Failed
         ↓
   (可能) Unknown

Pod预设（Presets）： ​

  • Init Containers：在主容器前运行，完成初始化任务
  • Sidecar Containers：辅助容器，提供日志收集、代理等功能
  • Ephemeral Containers：临时调试容器

4.3 控制器模式（Controller Pattern） ​

声明式API的工作流： ​

用户操作 kubectl apply -f deployment.yaml
         ↓
    API Server (验证并存储到etcd)
         ↓
Deployment Controller (检测到新对象)
         ↓
创建 ReplicaSet (控制循环)
         ↓
ReplicaSet Controller (检测到新对象)
         ↓
创建 Pod (副本数不足时)
         ↓
Scheduler (为Pod选择节点)
         ↓
Kubelet (创建并运行容器)

水平伸缩（HPA）原理： ​

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

工作流程：

  1. Metrics Server收集Pod指标
  2. HPA控制器定期查询当前指标
  3. 计算期望副本数：期望副本 = ceil(当前副本数 × (当前指标 / 目标指标))
  4. 更新Deployment的副本数

五、网络架构设计 ​

5.1 网络模型原则 ​

  1. Pod间直接通信：无需NAT
  2. Node与Pod直接通信：无需NAT
  3. Pod看到自己的IP：与别人看到的相同

5.2 四种通信模式 ​

1. Pod内部通信：localhost（网络命名空间共享）
2. Pod间通信：CNI插件实现的覆盖网络
3. Pod到Service通信：kube-proxy + ClusterIP
4. 外部到Service通信：NodePort/LoadBalancer/Ingress

5.3 Service实现机制 ​

ClusterIP类型： ​

yaml
apiVersion: v1
kind: Service
spec:
  selector:
    app: nginx
  ports:
  - port: 80
    targetPort: 9376
  clusterIP: 10.96.0.1  # 虚拟IP

Endpoint维护：

Service创建 → Endpoint Controller → Endpoints对象
                                    ↓
                           kube-proxy更新规则

服务发现： ​

  • 环境变量：每个Service创建{SVCNAME}_SERVICE_HOST和{SVCNAME}_SERVICE_PORT
  • DNS：CoreDNS提供<service>.<namespace>.svc.cluster.local解析

5.4 CNI插件架构 ​

Kubelet → CNI插件 → 网络配置
          ↓
   容器网络命名空间

常见CNI插件：

  • Flannel：简单的覆盖网络
  • Calico：BGP路由，网络策略
  • Cilium：eBPF-based，高性能
  • Weave Net：完整的网络解决方案

六、存储架构设计 ​

6.1 卷（Volume）生命周期 ​

Provisioning → Binding → Attaching → Mounting → Using → Unmounting → Detaching

6.2 存储类（StorageClass） ​

yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

6.3 持久卷（PersistentVolume）流程 ​

1. 管理员创建PV（静态供给）
  或
  用户创建PVC → StorageClass动态创建PV
      ↓
2. PVC绑定PV（一对一）
      ↓
3. Pod使用PVC挂载卷
      ↓
4. 容器访问存储

七、安全架构 ​

7.1 四大安全支柱 ​

  1. 认证（Authentication）

    • X.509客户端证书
    • 静态令牌文件
    • Bootstrap令牌
    • ServiceAccount令牌
    • Webhook令牌
    • OpenID Connect令牌

  2. 授权（Authorization）

    • RBAC（推荐）：Role/RoleBinding, ClusterRole/ClusterRoleBinding
    • ABAC：基于属性的访问控制
    • Node：节点授权
    • Webhook：外部授权服务

  3. 准入控制（Admission Control）

    • MutatingAdmissionWebhook：修改对象（如注入sidecar）
    • ValidatingAdmissionWebhook：验证对象
    • 内置控制器：NamespaceLifecycle, LimitRanger, ResourceQuota等

  4. 网络安全

    • NetworkPolicy：定义Pod间通信规则
    • Pod安全策略（PSP）：已废弃，由Pod Security Standards替代

7.2 ServiceAccount工作机制 ​

ServiceAccount创建 → 自动创建Secret（包含token）
                             ↓
                     Pod通过volume挂载token
                             ↓
                    容器内访问API Server

八、高可用架构 ​

8.1 控制平面高可用 ​

多Master节点（至少3个）
    ↓
etcd集群（奇数节点，推荐3或5）
    ↓
负载均衡器（API Server前端）
    ↓
组件多实例 + Leader选举

8.2 故障恢复策略 ​

  1. etcd数据备份与恢复
  2. 组件健康检查与自动重启
  3. Pod驱逐策略：当节点不健康时
  4. Pod中断预算（PDB）：保证最小可用副本数

十、设计模式总结 ​

10.1 Kubernetes核心设计模式 ​

  1. 声明式API模式：描述期望状态
  2. 控制器模式：协调实际与期望状态
  3. Sidecar模式：扩展容器功能
  4. Ambassador模式：代理网络请求
  5. Adapter模式：标准化接口输出

10.2 最佳实践原则 ​

  1. 面向失败设计：假设任何组件都可能失败
  2. 最终一致性：系统趋向一致而非强一致
  3. 关注点分离：组件职责单一
  4. 可观察性：日志、指标、追踪全方位监控

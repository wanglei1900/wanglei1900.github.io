Kubernetes 服务暴露策略 深度解析 ​

一、服务暴露基础概念 ​

1.1 为什么需要服务暴露？ ​

容器化应用需要被访问的四种场景：

  1. 集群内访问：微服务间通信
  2. 集群外访问：外部客户端访问
  3. 公网访问：互联网用户访问
  4. 混合云/跨集群访问：多环境互通

1.2 核心挑战 ​

  • 动态IP问题：Pod IP不固定
  • 负载均衡需求：多副本流量分发
  • 网络隔离：命名空间/网络安全策略
  • 协议适配：HTTP/HTTPS/TCP/UDP/WebSocket等
  • SSL/TLS终结：证书管理
  • 路径路由：基于URL的路由规则

二、Service：服务发现与负载均衡 ​

2.1 Service 核心原理 ​

Service 类型对比： ​

类型作用范围IP类型访问方式适用场景
ClusterIP集群内部虚拟IP集群内Pod内部微服务通信
NodePort节点级别节点IP<NodeIP>:<NodePort>开发测试，简单外部访问
LoadBalancer公网/内网负载均衡器IP外部客户端云环境生产部署
ExternalNameDNS级别CNAME域名解析集成外部服务
Headless集群内部无ClusterIPDNS直接解析Pod IP有状态服务，如数据库

Service YAML 示例： ​

yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
  namespace: default
spec:
  selector:
    app: my-app
  type: ClusterIP  # NodePort, LoadBalancer, ExternalName
  clusterIP: 10.96.0.100  # 可选，固定ClusterIP
  ports:
  - name: http
    port: 80          # Service端口
    targetPort: 8080  # Pod端口
    protocol: TCP
  - name: https
    port: 443
    targetPort: 8443
    protocol: TCP
  sessionAffinity: ClientIP  # 会话保持
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800

2.2 ClusterIP（集群内部服务） ​

工作原理： ​

Client Pod → ClusterIP(10.96.0.100) → kube-proxy(iptables/IPVS) → 后端Pod

服务发现机制： ​

  1. 环境变量注入（传统方式）：
bash
MY_SERVICE_SERVICE_HOST=10.96.0.100
MY_SERVICE_SERVICE_PORT=80
MY_SERVICE_PORT_80_TCP_ADDR=10.96.0.100
  1. DNS解析（推荐方式）：
bash
# 完全限定域名
my-service.default.svc.cluster.local

# 缩写（同一命名空间）
my-service

# DNS记录类型
A记录：my-service → 10.96.0.100
SRV记录：_http._tcp.my-service → 端口信息

高级配置： ​

yaml
apiVersion: v1
kind: Service
spec:
  # 无头服务（Headless Service）
  clusterIP: None  # 重要：没有ClusterIP
  
  # 自定义端点
  externalIPs:
  - 192.168.1.240  # 外部可达的IP
  
  # 流量策略
  internalTrafficPolicy: Local  # 节点内优先
  externalTrafficPolicy: Local  # 保留客户端源IP

2.3 NodePort（节点端口暴露） ​

架构原理： ​

外部客户端 → NodeIP:NodePort → kube-proxy → 后端Pod
    ↓
可能经过：LoadBalancer → NodePort

配置示例： ​

yaml
apiVersion: v1
kind: Service
metadata:
  name: nodeport-service
spec:
  type: NodePort
  selector:
    app: web
  ports:
  - port: 80          # Service端口
    targetPort: 8080  # Pod端口
    nodePort: 30080   # 节点端口(30000-32767)
    protocol: TCP

端口分配策略： ​

  • 自动分配：不指定nodePort时，K8s分配30000-32767
  • 手动指定：确保端口不冲突
  • 多节点访问：需要外部负载均衡器或DNS轮询

局限性： ​

  • 端口范围有限（30000-32767）
  • 每个服务占用所有节点的相同端口
  • 需要维护防火墙规则
  • 不支持基于主机的路由

2.4 LoadBalancer（云提供商负载均衡器） ​

工作原理： ​

互联网用户 → 云负载均衡器 → NodePort/ClusterIP → Pod

云平台集成： ​

yaml
apiVersion: v1
kind: Service
metadata:
  name: loadbalancer-service
  annotations:
    # AWS ELB 特定配置
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-internal: "true"
    service.beta.kubernetes.io/aws-load-balancer-ssl-cert: "arn:aws:acm..."
    
    # GCP 特定配置
    cloud.google.com/load-balancer-type: "Internal"
    
    # Azure 特定配置
    service.beta.kubernetes.io/azure-load-balancer-internal: "true"
    
    # 通用配置
    service.beta.kubernetes.io/load-balancer-source-ranges: "10.0.0.0/8,192.168.0.0/16"
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 8080
  loadBalancerIP: 203.0.113.10  # 特定IP（如果云提供商支持）
  externalTrafficPolicy: Local   # 保留客户端IP

保留客户端源IP： ​

yaml
spec:
  externalTrafficPolicy: Local

工作原理：

  • 当设置为Local时，kube-proxy只代理到本地有Pod的节点
  • 需要确保Pod在所有节点均匀分布，或使用DaemonSet
  • 缺点：可能导致流量分布不均

2.5 ExternalName（外部服务集成） ​

用途： ​

将集群外服务映射为集群内服务名

yaml
apiVersion: v1
kind: Service
metadata:
  name: external-database
spec:
  type: ExternalName
  externalName: database.example.com  # 外部域名

工作原理： ​

Pod访问 external-database.default.svc.cluster.local
    ↓
DNS CNAME解析 → database.example.com
    ↓
访问外部服务

三、Ingress：HTTP/HTTPS路由 ​

3.1 Ingress 核心概念 ​

与Service的关系： ​

互联网 → Ingress Controller → Ingress规则 → Service → Pod

Ingress 资源定义： ​

yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
  namespace: default
  annotations:
    # Ingress Controller特定注解
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx  # 指定Ingress Controller
  tls:
  - hosts:
    - www.example.com
    secretName: example-tls-secret  # TLS证书
  rules:
  - host: www.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /web
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
  - host: admin.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: admin-service
            port:
              number: 8080

3.2 主流Ingress Controller ​

1. Nginx Ingress Controller ​

最流行的Ingress Controller

yaml
# 安装（使用Helm）
helm upgrade --install ingress-nginx ingress-nginx \
  --repo https://kubernetes.github.io/ingress-nginx \
  --namespace ingress-nginx --create-namespace

# 高级配置示例
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress
  annotations:
    # 负载均衡配置
    nginx.ingress.kubernetes.io/load-balance: "ip_hash"
    nginx.ingress.kubernetes.io/upstream-hash-by: "$remote_addr"
    
    # 限流配置
    nginx.ingress.kubernetes.io/limit-connections: "10"
    nginx.ingress.kubernetes.io/limit-rps: "100"
    
    # 认证配置
    nginx.ingress.kubernetes.io/auth-type: basic
    nginx.ingress.kubernetes.io/auth-secret: basic-auth
    nginx.ingress.kubernetes.io/auth-realm: "Authentication Required"
    
    # CORS配置
    nginx.ingress.kubernetes.io/enable-cors: "true"
    nginx.ingress.kubernetes.io/cors-allow-origin: "*"
    
    # 重写规则
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/use-regex: "true"
    
    # SSL配置
    nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"

2. Traefik Ingress Controller ​

云原生动态路由

yaml
# Traefik IngressRoute (CRD方式)
apiVersion: traefik.containo.us/v1alpha1
kind: IngressRoute
metadata:
  name: traefik-route
spec:
  entryPoints:
    - web
    - websecure

    - name: auth

    options:
      name: default
      namespace: default

AWS云原生集成

      - path: /*

3.3 Ingress 高级特性 ​

1. 路径匹配策略 ​

yaml
spec:
  rules:
  - http:
      paths:
      - path: /exact
        pathType: Exact     # 精确匹配 /exact
      - path: /prefix
        pathType: Prefix    # 前缀匹配 /prefix, /prefix/xxx
      - path: /regex.*\.html
        pathType: ImplementationSpecific  # 依赖于Ingress Controller

2. 默认后端 ​

yaml
spec:
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80

3. 通配符主机 ​

yaml
spec:
  rules:
  - host: "*.example.com"  # 通配符子域名
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: ...

四、Gateway API：下一代服务暴露 ​

4.1 Gateway API 与 Ingress 对比 ​

特性IngressGateway API
设计目标简单HTTP路由通用L4-L7路由
扩展性依赖注解原生可扩展

4.2 Gateway API 核心资源 ​

1. GatewayClass ​

定义网关实现类型

yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: GatewayClass
metadata:
  name: public-gateway
spec:
  controllerName: example.com/gateway-controller
  parametersRef:
    name: public-gateway-params
    group: example.com
    kind: GatewayClassConfig

2. Gateway ​

网关实例配置

yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: Gateway
metadata:
  name: internet-gateway
spec:
  gatewayClassName: public-gateway
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: All
  - name: https
    port: 443
    protocol: HTTPS
    tls:
      mode: Terminate
      certificateRefs:
      - name: example-com
    allowedRoutes:
      namespaces:
        from: Selector
        selector:
          matchLabels:
            environment: production

3. HTTPRoute ​

HTTP路由规则

yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: HTTPRoute
metadata:
  name: http-route
spec:
  parentRefs:
  - name: internet-gateway
    namespace: default
  hostnames:
  - "www.example.com"
  - "api.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: api-service
      port: 80
      weight: 90
    - name: api-canary
      port: 80
      weight: 10
  - matches:
    - headers:
      - type: Exact
        name: version
        value: v2
    backendRefs:
    - name: api-v2
      port: 80

5.1 金丝雀发布（Canary Release） ​

使用Service实现： ​

yaml
# 主服务
apiVersion: v1
kind: Service
metadata:
  name: main-service
spec:
  selector:
    app: my-app
    version: stable
  ports: [...]

# 金丝雀服务
apiVersion: v1
kind: Service
metadata:
  name: canary-service
spec:
  selector:
    app: my-app
    version: canary
  ports: [...]

# Ingress路由（Nginx示例）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: canary-ingress
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"  # 10%流量
    # 或基于header
    nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"
    nginx.ingress.kubernetes.io/canary-by-header-value: "always"
    # 或基于cookie
    nginx.ingress.kubernetes.io/canary-by-cookie: "canary"

使用Istio实现： ​

yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: canary-vs
spec:
  hosts:
  - myapp.example.com
  http:
  - match:
    - headers:
        endpoint:
          exact: canary
    route:
    - destination:
        host: myapp-canary
  - route:
    - destination:
        host: myapp-stable
      weight: 90
    - destination:
        host: myapp-canary
      weight: 10

八、最佳实践总结 ​

8.1 选择策略的决策树 ​

需要暴露服务吗？
    ↓
是 → 访问来源？
        ↓
        集群内 → ClusterIP（无头服务用于有状态应用）
        ↓
        特定节点 → NodePort（开发测试）
        ↓
        公网访问 → 需要高级路由？
            ↓
            否 → LoadBalancer（云环境）
            ↓
            是 → Ingress（HTTP/HTTPS）
                ↓
                需要现代API → Gateway API（未来标准）
                ↓
                需要微服务治理 → 服务网格（Istio/Linkerd）

总结 ​

Kubernetes服务暴露是一个多层次、多方案的体系，从基础的Service到复杂的服务网格，每种方案都有其适用场景：

  1. Service：基础的服务发现和负载均衡
  2. Ingress：HTTP/HTTPS流量的智能路由
  3. Gateway API：下一代标准化服务暴露
  4. 服务网格：微服务治理的全套解决方案

选择合适策略时需考虑：

  • 应用协议（HTTP/TCP/UDP）
  • 流量规模
  • 安全需求
  • 团队技术栈
  • 云环境限制
  • 运维复杂度

在生产环境中，通常会结合多种方案，如：Ingress处理南北流量，服务网格处理东西流量，辅以精细的网络策略和安全配置。

Cache-Aside模式（旁路缓存模式）学习笔记 ​

一、模式概述 ​

1.1 什么是Cache-Aside模式 ​

Cache-Aside模式，又称旁路缓存模式或Lazy Loading（延迟加载）模式，是日常开发中最常用、最经典的缓存读写策略。它几乎是互联网应用缓存方案的事实标准，尤其适合读多写少的业务场景。

这个模式之所以被称为“旁路”（Aside），是因为应用程序的写操作完全绕过了缓存，直接操作数据库——缓存像是“站在一旁”的辅助角色，而非必经之路。应用程序扮演了数据流转的“指挥官”，需要同时维护Cache和DB两个数据源。

1.2 核心思想 ​

Cache-Aside模式的核心思想是：按需将数据加载到缓存中。数据不会主动被推入缓存，而是在被请求时（且缓存中不存在时）才从数据库加载并存入缓存。这种“懒惰”的加载方式避免了预加载可能带来的资源浪费。

一句话总结：读时按需加载，写时先更新数据库再删除缓存。

二、工作流程详解 ​

2.1 读操作流程（Read Path） ​

读操作遵循“先查缓存，未命中则查数据库并回填”的流程：

  1. 应用程序尝试从缓存中读取数据
  2. 判断结果：
    • 缓存命中（Hit） ：直接从缓存返回数据，无需访问数据库
    • 缓存未命中（Miss） ：从数据库中读取数据，将数据写入缓存，然后返回给调用方
读流程伪代码：
public Data getData(key) {
    // 1. 先查缓存
    Data data = cache.get(key);
    if (data != null) {
        return data;  // 缓存命中，直接返回
    }
    // 2. 缓存未命中，查数据库
    data = db.get(key);
    // 3. 写入缓存
    cache.set(key, data);
    return data;
}

2.2 写操作流程（Write Path） ​

写操作遵循“先更新数据库，再删除缓存”的流程：

  1. 应用程序将更改写入数据存储（数据库）
  2. 使缓存中对应的项失效（删除）
写流程伪代码：
public void updateData(key, newData) {
    // 1. 先更新数据库
    db.update(key, newData);
    // 2. 再删除缓存
    cache.delete(key);
}

当再次需要该项数据时，Cache-Aside模式会从数据存储中检索更新的数据并重新添加到缓存中。

三、设计原理深度剖析 ​

3.1 为什么是“先更新数据库，再删除缓存”？ ​

绝对不能反过来。如果“先删缓存，后更新数据库”，在高并发下会引入经典的数据不一致问题：

问题场景（写请求A + 读请求B并发） ：

步骤请求A（写）请求B（读）
1删除缓存—
2—缓存为空，读取数据库旧值
3将新值写入数据库—
4—将旧值写入缓存

结果：数据库中是新值，缓存中是旧值，数据不一致。

这就是为什么Cache-Aside模式强制要求先操作数据库，再操作缓存。

3.2 为什么是“删除缓存”而不是“更新缓存”？ ​

如果采用更新缓存（set缓存）的方式，在并发写时可能出现数据不一致：

问题场景（两个并发写请求） ：

步骤请求1请求2
1先操作数据库后操作数据库
2—先set了缓存
3后set了缓存—

由于无法保证时序，可能导致数据库与缓存之间的数据不一致。

结论：Cache-Aside模式建议删除（delete）缓存，而不是更新（set）缓存。删除缓存后，下次读取时会触发cache miss，从而从数据库加载最新数据，保证最终一致性。

3.3 “先更新DB，后删除Cache”就绝对安全吗？ ​

也不是绝对安全的。在极端并发场景下仍可能存在问题：

问题场景（读请求A + 写请求B并发） ：

步骤请求A（读）请求B（写）
1缓存未命中，从DB读到旧值—
2—更新DB为新值，删除缓存
3将旧值写入缓存—

结果：缓存中是旧值，数据库中是新值，数据不一致。

不过，这种场景发生的概率较低，且可以通过分布式锁、版本号等机制来进一步保障。

四、优缺点分析 ​

4.1 优点 ​

优点说明
实现简单逻辑清晰，容易理解和实现
性能提升显著缓存读取速度远快于数据库，显著提高响应速度
降低数据库负载大部分读操作直接从缓存完成，数据库压力大幅降低
缓存与数据库解耦两者相互独立，互不影响
容错性强缓存服务故障时，系统仍可直接访问数据库继续工作
适应性强无需修改后端存储系统的代码或结构

4.2 缺点 ​

缺点说明
不保证强一致性Cache-Aside模式不能保证数据存储和缓存之间的一致性
缓存失效窗口期写入后到下次读取之间，可能读到过期数据
缓存击穿/穿透风险高并发下热点数据失效可能导致数据库压力骤增
缓存删除失败风险删除缓存操作失败会导致数据永久不一致

五、适用场景 ​

Cache-Aside模式适用于以下场景：

  1. 读多写少的业务场景——这是最核心的适用条件
  2. 半静态数据——更新频次低、读取频繁的数据
  3. 应用程序经常重复读取的相同数据
  4. 希望降低数据库负载、提升响应速度的场景
  5. 需要缓存服务故障时仍能正常工作的场景

典型业务场景：

  • 电商商品详情页查询
  • 用户信息缓存
  • 配置信息缓存
  • 热点数据缓存

六、注意事项与最佳实践 ​

6.1 缓存过期时间（TTL）设置 ​

  • 不宜过短：过早过期会导致应用程序不断从数据库检索数据并重新写入缓存
  • 不宜过长：过长会导致缓存数据变得过时
  • 过期策略应与应用程序的数据访问模式相匹配

6.2 缓存逐出策略 ​

大多数缓存空间有限，超出大小时会逐出数据。通常采用LRU（最近最少使用） 策略。

6.3 缓存预热（Priming） ​

可以在系统启动时，将可能需要的热门数据预先加载到缓存中。即使部分数据过期或被逐出，Cache-Aside模式仍然可以发挥作用。

6.4 一致性保障增强方案 ​

针对Cache-Aside模式的弱点，可以采取以下增强措施：

  1. 消息队列重试机制：当缓存删除失败时，将操作信息发送到消息队列，通过重试机制确保最终删除成功
  2. Canal中间件：订阅MySQL binlog，自动感知数据变化并触发缓存更新
  3. 分布式锁：防止并发场景下旧数据覆盖新数据
  4. 版本号机制：缓存中存储数据版本号，写入时校验版本

6.5 降级处理 ​

如果缓存服务发生故障，系统仍然可以通过直接访问数据库进行操作——这是Cache-Aside模式的重要容错优势。

七、代码示例 ​

7.1 Java（Spring Boot + Redis） ​

java
@Service
public class ProductService {
    private static final String CACHE_KEY = "product:";
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    @Autowired
    private ProductRepository productRepository;
    
    // 读操作：Cache-Aside模式
    public Product getProduct(Long id) {
        String key = CACHE_KEY + id;
        
        // 1. 先从缓存读取
        Product product = (Product) redisTemplate.opsForValue().get(key);
        if (product != null) {
            return product;  // 缓存命中
        }
        
        // 2. 缓存未命中，查询数据库
        product = productRepository.findById(id).orElse(null);
        if (product != null) {
            // 3. 写入缓存，设置TTL为10分钟
            redisTemplate.opsForValue().set(key, product, 10, TimeUnit.MINUTES);
        }
        return product;
    }
    
    // 写操作：Cache-Aside模式
    public void updateProduct(Product product) {
        // 1. 先更新数据库
        productRepository.save(product);
        // 2. 再删除缓存
        redisTemplate.delete(CACHE_KEY + product.getId());
    }
}

八、与其他缓存模式的对比 ​

模式特点适用场景
Cache-Aside应用主动管理缓存，读时加载，写时删除读多写少，最通用
Read-Through缓存层自动从DB加载数据，对应用透明希望缓存逻辑与业务解耦
Write-Through写入时同时更新缓存和DB需要强一致性
Write-Behind先更新缓存，异步更新DB写密集型，可接受一定延迟

九、总结 ​

Cache-Aside模式是缓存领域最基础、最经典的模式，掌握它是理解所有缓存策略的起点。其核心要点可概括为：

  • 读：先缓存→未命中则查DB→回写缓存
  • 写：先更新DB→再删除缓存
  • 原则：以数据库结果为准
  • 代价：不保证强一致性，存在短暂的不一致窗口期

在实际项目中，Cache-Aside模式足以覆盖大多数场景。当遇到特定的一致性或性能瓶颈时，再考虑引入其他模式或增强方案。

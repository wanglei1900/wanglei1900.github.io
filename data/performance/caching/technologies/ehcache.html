Ehcache分布式缓存 学习笔记 ​

数据库层开发 → 高性能访问 → 缓存策略 → 缓存技术 → Ehcache分布式缓存

一、Ehcache概述 ​

Ehcache是一款基于Java语言开发的开源进程内缓存框架，由Terracotta公司维护。自2003年诞生以来，Ehcache凭借其轻量、快速、易用的特性，成为Java生态系统中应用最广泛的缓存解决方案之一。作为Hibernate框架的默认缓存提供者，Ehcache被深度集成于Spring Boot等主流开发框架中，是Java EE应用及轻量级容器环境下的首选缓存方案。

核心定位：Ehcache从最初的纯本地缓存框架，逐步演进为既支持本地缓存、又具备分布式缓存能力的综合缓存解决方案。它就像应用进程内部的“数据加速器”，数据与业务线程同处一个JVM进程，访问延迟达到纳秒级别。相比Redis等集中式缓存需要经过网络I/O（1ms起跳），Ehcache的get/put操作仅需几十纳秒。

适用场景：

  • 单节点QPS > 5000的高并发场景
  • 缓存数据量 < 100MB的轻量级场景
  • 可容忍秒级一致性延迟的业务
  • 需要进程内缓存与分布式缓存结合的多级缓存架构
  • Hibernate二级缓存

重要说明：Ehcache存在2.x和3.x两个主要版本分支，架构差异较大。Ehcache 2.x基于net.sf.ehcache包，通过RMI/JGroups等插件实现分布式复制缓存；Ehcache 3.x基于org.ehcache包，通过Terracotta Server实现真正的分布式缓存。本文将以Ehcache 3.x为核心进行阐述，同时兼顾2.x的常见实践。

二、核心架构 ​

2.1 三级存储模型 ​

Ehcache最核心的架构创新在于其独特的三级存储模型：

存储层级实现方式访问速度特点
堆内存（Heap）JVM堆空间纳秒级延迟最低，受GC影响
堆外内存（Off-Heap）DirectByteBuffer微秒级规避GC扫描，适合GB级大容量数据
磁盘存储（Disk）文件系统毫秒级持久化冷数据，容量近乎无限

这种分层设计形成“由快到慢、由小到大”的存储金字塔：高频热点数据驻留堆内存，中等热度数据存储堆外内存，低频冷数据下沉至磁盘。Ehcache 3.0的单进程堆外存储已测试可承载6TB数据。

2.2 堆内缓存工作机制 ​

堆内缓存是访问速度最快的一层，因为对象无需序列化即可直接引用。Ehcache底层依赖于Java的ConcurrentHashMap实现高效的线程安全读写操作。

2.3 架构扩展性 ​

Ehcache具备极强的扩展能力：

  • 监听器接口：CacheManager监听器、Cache事件监听器
  • 装饰器接口：支持缓存行为的动态增强
  • CacheLoader/CacheWriter：自定义数据加载和写入逻辑
  • 异常处理器：捕获并处理缓存操作异常

通过添加Terracotta，Ehcache可扩展到数百个节点的分布式部署架构。

三、缓存策略 ​

3.1 数据淘汰策略 ​

当缓存空间达到上限时，Ehcache需要按策略清理数据。Ehcache支持三种淘汰策略：

策略原理适用场景
LRU（最近最少使用）优先淘汰最长时间未被访问的数据热点数据集中的场景
LFU（最不经常使用）基于访问频率淘汰，频率最低者优先数据访问呈明显周期性的应用
FIFO（先进先出）按数据写入顺序淘汰简单的缓存队列管理

配置示例：

xml
<cache name="productCache" 
       maxEntriesLocalHeap="10000" 
       timeToLiveSeconds="3600" 
       memoryStoreEvictionPolicy="LRU"/>

Ehcache 1.6及以上版本还允许开发者自定义淘汰算法，可利用元素的任意元数据实现更复杂的淘汰逻辑。

3.2 数据过期策略 ​

Ehcache通过Expiry接口控制缓存映射的生命周期：

  • TTL（Time To Live） ：从创建/更新开始计算，到期即失效
  • TTI（Time To Idle） ：从最后一次访问开始计算，闲置到期即失效

过期元素的清理由每个缓存独立的线程负责，定期移除过期元素以释放磁盘空间。

3.3 内存与磁盘混合存储 ​

当内存空间不足时，Ehcache自动将冷数据从内存溢出到磁盘，确保缓存容量不受内存限制。这种机制既能利用内存的高速访问，又能借助磁盘扩展实现近乎无限的容量承载能力。

磁盘持久化配置：

xml
<diskStore path="java.io.tmpdir/ehcache_disk_store"/>

四、分布式集群方案 ​

4.1 为什么需要集群？ ​

在集群化部署的业务场景中，各个节点进程独自维护自己的缓存数据。由于负载均衡器将请求分发到不同节点，可能导致缓存漂移（Cache Drift） 问题——某个节点更新了缓存，其他节点的缓存仍然是旧数据，造成数据不一致。

4.2 Ehcache的五种集群方案 ​

Ehcache从1.7版本开始，支持五种集群方案：

方案类型说明
Terracotta服务端集中式通过Terracotta Server Array实现分布式缓存
RMI点对点（P2P）Java内置远程方法调用技术
JGroups点对点（P2P）基于组通信协议的集群方案
JMS消息中间件通过Java消息服务进行缓存复制
Ehcache Server服务端集中式Ehcache官方提供的缓存服务器方案

4.3 分布式缓存（Terracotta方案）—— Ehcache 3.x推荐 ​

分布式缓存使用Terracotta Server Array，是Ehcache在集群或水平扩展应用环境中的推荐方案。

核心概念：

  • Server Off-Heap Resource：在Terracotta Server端定义的存储资源，缓存可从中为集群层预留存储空间
  • Clustered Tier Manager：服务端组件，为CacheManager赋予集群能力。每个Clustered Tier Manager有唯一标识符，多个CacheManager可连接到同一个Manager共享缓存数据
  • Dedicated Pool（专用池） ：固定大小的存储池，专属于某个缓存集群层
  • Shared Pool（共享池） ：固定大小但可被多个缓存的集群层共享的存储池。注意：共享存储不代表共享数据，每个缓存的数据仍然隔离

工作原理：数据缓存到应用程序节点后，通过Terracotta Server在集群中共享。一个应用实例缓存的数据对所有集群成员可见。可以部署一个或多个镜像服务器提供高可用。

启动Terracotta Server：

bash
# 从Ehcache集群工具包中启动
cd $KIT_DIR/server/bin
./start-tc-server.sh

# 激活集群
$KIT_DIR/tools/bin/configure.sh activate

4.4 复制缓存（Replicated Caching）—— Ehcache 2.x常用方案 ​

复制缓存将数据保存在每个应用节点，通过复制或失效机制在集群中传播变更。

RMI集群模式（最常用）：

RMI是Java内置的远程方法调用技术，Ehcache从1.2版本开始支持RMI方式的缓存集群。

核心要求：所有缓存对象的键和值都必须实现java.io.Serializable接口。

节点发现方式：

  • 手工配置：在每个节点中配置所有其他节点的连接信息（节点变化时需重新配置）
  • 自动发现：通过组播（Multicast）自动发现其他节点

RMI配置示例（两个节点集群）：

节点1配置文件（ehcache-1.xml）：

xml
<ehcache>
    <!-- 缓存定义 -->
    <cache name="users" 
           maxEntriesLocalHeap="200" 
           timeToLiveSeconds="600">
        <cacheEventListenerFactory 
            class="net.sf.ehcache.distribution.RMICacheReplicatorFactory"
            properties="replicateAsynchronously=true, 
                       replicatePuts=true, 
                       replicateUpdates=true, 
                       replicateUpdatesViaCopy=false, 
                       replicateRemovals=true"/>
    </cache>
    
    <!-- 集群节点发现配置 -->
    <cacheManagerPeerProviderFactory 
        class="net.sf.ehcache.distribution.RMICacheManagerPeerProviderFactory"
        properties="hostName=10.10.0.100, 
                   port=40001, 
                   socketTimeoutMillis=2000, 
                   peerDiscovery=manual, 
                   rmiUrls=//10.10.0.101:40001/users"/>
</ehcache>

节点2配置类似，交换IP地址即可。

复制操作类型：

  • put：新增缓存条目
  • update：覆盖已有条目（支持updateViaCopy或updateViaInvalidate两种模式）
  • remove：删除条目

updateViaInvalidate发送移除消息到其他节点，比复制成本更低。

5.2 XML配置模板 ​

xml
<config xmlns="http://www.ehcache.org/v3"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="http://www.ehcache.org/v3 
        http://www.ehcache.org/schema/ehcache-core-3.0.xsd">
    
    <!-- 默认缓存模板 -->
    <cache-template name="default">
        <expiry>
            <ttl unit="minutes">30</ttl>
        </expiry>
        <heap unit="entries">1000</heap>
    </cache-template>
    
    <!-- 订单缓存：热点数据，15分钟过期 -->
    <cache alias="order" uses-template="default">
        <heap unit="MB">64</heap>
        <disk unit="MB">512</disk>
        <expiry>
            <ttl unit="minutes">15</ttl>
        </expiry>
    </cache>
    
    <!-- 字典缓存：基本不变，永久有效 -->
    <cache alias="dict">
        <heap unit="entries">5000</heap>
        <expiry>
            <none/>
        </expiry>
    </cache>
    
    <!-- 磁盘持久化目录 -->
    <persistence directory="spring.tmpdir/caches"/>
</config>

5.3 Java API配置 ​

java
import org.ehcache.Cache;
import org.ehcache.CacheManager;
import org.ehcache.config.builders.CacheConfigurationBuilder;
import org.ehcache.config.builders.CacheManagerBuilder;
import org.ehcache.config.builders.ResourcePoolsBuilder;
import org.ehcache.expiry.Expirations;

public class EhcacheExample {
    public static void main(String[] args) {
        // 构建缓存配置：堆内存100条，1分钟TTL
        CacheConfigurationBuilder<String, String> configBuilder = 
            CacheConfigurationBuilder.newCacheConfigurationBuilder(
                String.class, 
                String.class, 
                ResourcePoolsBuilder.heap(100))
            .withExpiry(Expirations.timeToLiveExpiration(Duration.ofMinutes(1)));
        
        // 构建并初始化CacheManager
        CacheManager cacheManager = CacheManagerBuilder.newCacheManagerBuilder()
            .withCache("myCache", configBuilder)
            .build(true);
        
        // 获取缓存并操作
        Cache<String, String> cache = cacheManager.getCache("myCache", 
            String.class, String.class);
        cache.put("key", "value");
        String value = cache.get("key");
    }
}

5.4 Spring Boot注解使用 ​

java
@Service
public class OrderService {
    
    @Cacheable(value = "order", key = "#id")
    public Order getOrder(Long id) {
        return dao.selectById(id);  // 首次调用加载，后续命中缓存
    }
    
    @CachePut(value = "order", key = "#order.id")
    public Order updateOrder(Order order) {
        return dao.save(order);  // 更新缓存
    }
    
    @CacheEvict(value = "order", key = "#id")
    public void deleteOrder(Long id) {
        dao.deleteById(id);  // 清除缓存
    }
}

性能效果：第一次调用执行SQL耗时2秒，第二次命中缓存仅需0.02毫秒，性能提升5个数量级。

六、最佳实践 ​

6.1 选型建议 ​

Ehcache并非适用于所有场景：

条件推荐
单节点QPS > 5000✅ Ehcache
缓存数据量 < 100 MB✅ Ehcache
可容忍秒级一致性延迟✅ Ehcache
需要强一致性❌ 考虑Redis
跨服务共享缓存❌ 考虑Redis

6.2 缓存对象必须可序列化 ​

在集群环境中，所有缓存对象的键和值都必须实现java.io.Serializable接口，否则会导致序列化异常。

java
@Entity
public class User implements Serializable {
    private Long id;
    private String name;
    // ...
}

6.3 合理设置过期时间 ​

为不同类型的缓存设置差异化的过期时间：

  • 热点数据：较短TTL（如15分钟），保证时效性
  • 字典/配置数据：较长TTL甚至永不过期
  • 会话数据：使用TTI（闲置过期）

6.4 缓存预热 ​

在系统启动时主动加载热点数据到缓存，避免首次访问的缓存缺失导致数据库压力骤增。

6.5 多级缓存架构 ​

在分布式场景中，Ehcache常与Redis配合构建多级缓存：

请求 → Ehcache（L1，纳秒级）→ 未命中 → Redis（L2，微秒级）→ 未命中 → 数据库（毫秒级）

这种架构既利用了Ehcache的超低延迟，又通过Redis解决了跨节点数据共享问题。

6.6 监控与调优 ​

定期监控关键指标并根据数据调整配置：

  • 缓存命中率：核心性能指标
  • 平均访问时间：反映缓存效率
  • 内存使用率：避免OOM

指标说明

7.2 监听器 ​

Ehcache提供丰富的监听器接口：

CacheManager监听器：

  • notifyCacheAdded()：缓存添加时触发
  • notifyCacheRemoved()：缓存移除时触发

Cache事件监听器：

  • notifyElementRemoved()：元素移除时触发
  • notifyElementPut()：元素新增时触发
  • notifyElementUpdated()：元素更新时触发
  • notifyElementExpired()：元素过期时触发

九、常见问题与解决方案 ​

9.1 网络分区导致的数据不一致 ​

问题：在网络不稳定或部分节点间通信中断时，可能出现网络分区，导致数据在不同节点间不一致。

解决方案：使用强一致性复制策略（如ReplicationMode.ALL），虽牺牲性能但确保数据一致性；定期检查网络健康状况。

9.2 缓存雪崩 ​

问题：大量缓存同时失效，请求涌向数据库，造成服务压力骤增。

解决方案：为不同类型缓存设置差异化的过期时间；实施合理的淘汰策略；采用热点数据主动预热。

9.3 配置不当导致性能瓶颈 ​

问题：不恰当的缓存大小、并发级别或淘汰策略配置导致性能低下。

解决方案：根据实际需求和硬件资源合理配置；定期监控并根据数据调优。

9.4 序列化异常 ​

问题：集群环境中缓存对象未实现Serializable接口导致传输异常。

解决方案：确保所有缓存键和值实现java.io.Serializable接口。

十、总结 ​

Ehcache作为Java生态中应用最广泛的缓存框架，其核心价值体系涵盖：

维度关键技术
存储架构三级存储（堆内+堆外+磁盘），单进程可承载6TB数据
淘汰策略LRU/LFU/FIFO，支持自定义淘汰算法
集群方案Terracotta（推荐）、RMI、JGroups、JMS、Ehcache Server
配置方式XML声明式 + Java API + Spring Boot注解
生态集成JSR-107（JCache）标准、Spring Cache、Hibernate二级缓存
监控扩展监听器接口、CacheLoader/CacheWriter、异常处理器

关键数据回顾：

  • 访问延迟：几十纳秒
  • 单进程堆外存储：最高6TB
  • 首次访问 vs 缓存命中：2s → 0.02ms，提升5个数量级
  • 集群节点扩展：可至数百个节点

在实际生产中，Ehcache最适合作为进程内一级缓存（L1） ，与Redis等集中式缓存配合构建多级缓存架构，兼顾纳秒级访问延迟与分布式数据共享的双重需求。对于Ehcache 2.x用户，建议关注RMI/JGroups等复制缓存方案；对于新项目，推荐直接使用Ehcache 3.x + Terracotta的分布式缓存方案。

Redis高级特性 学习笔记 ​

数据库层开发 → 高性能访问 → 缓存策略 → 缓存技术 → Redis高级特性

一、Redis概述与核心优势 ​

Redis（Remote Dictionary Server）是一款基于ANSI C语言开发的开源内存数据库，其设计初衷是解决传统关系型数据库在高并发场景下的性能瓶颈。

核心优势：

优势说明
超高性能单机每秒可处理数十万次请求，响应时间微秒级
丰富数据结构支持String、Hash、List、Set、ZSet等原生数据结构
持久化机制提供RDB和AOF两种方式，平衡数据安全性和性能
高可用架构支持主从复制、哨兵模式和集群部署
多功能性缓存、消息队列、分布式锁、限流、排行榜等

典型应用场景：热点数据缓存（电商商品详情、用户会话）、计数器与排行榜（销量统计、积分排名）、分布式锁、消息队列、限流与熔断等。

二、缓存策略 ​

缓存策略是指在缓存系统中管理数据存储和失效的规则。

2.1 内存淘汰策略 ​

当Redis内存使用达到上限（maxmemory）时，需要按策略逐出数据。Redis共提供8种淘汰策略：

淘汰设置了过期时间的键（volatile-xxx） ：

  • volatile-lru：淘汰最近最少使用的键
  • volatile-lfu：淘汰最不经常使用的键
  • volatile-ttl：淘汰将要过期的键
  • volatile-random：随机淘汰

淘汰所有键（allkeys-xxx） ：

  • allkeys-lru：从所有键中淘汰最近最少使用的
  • allkeys-lfu：从所有键中淘汰最不经常使用的
  • allkeys-random：随机淘汰

不淘汰：

  • no-eviction：内存满时写操作报错

配置示例：

bash
# 设置最大内存
CONFIG SET maxmemory 4gb
# 启用LRU策略
CONFIG SET maxmemory-policy allkeys-lru
# 启用LFU策略
CONFIG SET maxmemory-policy allkeys-lfu

策略选择建议：

  • LRU：适用于频繁访问最新数据的场景，如新闻首页缓存
  • LFU：适用于长期缓存热点数据的场景，如电商商品详情页
  • TTL：适用于需要定期更新数据的场景，如用户会话管理
  • Random：适用于对缓存命中率要求不高的场景，一般用于测试环境

2.2 数据过期策略 ​

Redis采用定期删除 + 惰性删除的组合策略：

  • 惰性删除：只有在访问key时才检查是否过期，对CPU友好，但可能导致过期key积压
  • 定期删除：每隔一段时间抽取一批key检查过期，默认每秒扫描10次（hz配置），每次抽20个，若过期比例超25%则循环抽取，最大执行时间25ms

TTL设置示例：

bash
SET user:123 "John Doe" EXPIRE user:123 60

三、持久化机制 ​

Redis提供两种持久化方案解决内存数据库的数据丢失风险。

3.1 RDB快照 ​

原理：定时将内存数据以二进制格式写入磁盘文件。

配置示例：

bash
save 900 1    # 900秒内至少1个键被修改则触发RDB
save 300 10   # 300秒内至少10个键被修改则触发RDB

优势：文件体积小，恢复速度快，适合大规模数据备份。

局限：可能丢失最后一次快照后的数据，大数据集时Fork子进程可能导致服务阻塞。

3.2 AOF日志 ​

原理：记录所有写操作命令，服务重启时重放日志。

配置示例：

bash
appendonly yes
appendfsync everysec   # 每秒同步一次

优势：数据安全性更高（最多丢失1秒数据），日志文件可读性强。

局限：文件体积较大，恢复速度较慢。

3.3 混合持久化（推荐） ​

Redis 4.0版本支持混合持久化，在AOF重写时将RDB快照嵌入AOF头部，兼顾恢复速度与数据完整性。

bash
aof-use-rdb-preamble yes

重启时Redis优先加载AOF恢复数据。这是生产环境的推荐配置。

四、高可用架构 ​

Redis通过三种递进的架构方案实现不同级别的高可用。

4.1 主从复制 ​

原理：允许从节点从主节点拷贝完整数据备份，主库可读写，写操作自动同步到从库，从库只读。

同步机制：

  • 全量复制：slave请求增量同步被拒后，master生成RDB发送，slave清空本地数据加载RDB
  • 增量复制：master将RDB期间的命令记入repl_baklog，持续发送给slave

特点：提供数据冗余和读写分离，但无法自动故障转移。

4.2 哨兵模式（Sentinel） ​

定位：在主从复制基础上增加自动故障转移功能。

工作机制：

  1. 监控：Sentinel持续监控主节点和从节点状态
  2. 主观下线（SDOWN） ：单个Sentinel检测到主节点在30秒内无响应
  3. 客观下线（ODOWN） ：超过quorum数量的Sentinel确认主节点不可达
  4. 领导者选举：使用Raft算法选举Leader执行故障转移
  5. 故障转移：Leader根据优先级、复制偏移量等规则从从节点中选出新主节点

配置示例：

bash
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 10000

部署建议：

  • 至少部署3个Sentinel实例（奇数个，避免脑裂）
  • 分布在独立物理节点或可用区
  • quorum通常设为N/2 + 1
  • 调整min-slaves-to-write防止脑裂

优缺点：

  • 优点：自动化容灾、高可用、客户端透明
  • 缺点：异步复制可能丢失数据、配置维护成本高、存在脑裂风险

4.3 Cluster集群 ​

定位：通过分片将数据分布在多个节点上，实现高可用和横向扩展。

核心机制：

  • 数据分片：16384个哈希槽（0-16383），不同节点管理不同槽
  • 数据路由：slot = CRC16(key) % 16384，根据槽找到对应节点
  • 主从复制：每个主节点有一个或多个从节点
  • 故障转移：主节点故障时从节点自动提升

配置示例：

bash
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000

部署要求：至少3个主节点构成最小集群。

五、性能优化 ​

5.1 连接池 ​

高并发场景下频繁创建和销毁连接会导致性能下降，使用连接池可复用连接。

python
from redis.connection import ConnectionPool
pool = ConnectionPool(host='localhost', port=6379, db=0)
r = redis.Redis(connection_pool=pool)

客户端库通常通过连接池优化连接管理。

5.2 管道（Pipeline） ​

管道技术将多个命令一次性发送给服务器，减少网络往返次数。

python
pipe = r.pipeline()
pipe.set('foo', 'bar')
pipe.get('foo')
result = pipe.execute()

5.3 批量操作 ​

使用MSET、MGET等批量命令减少网络往返。

5.4 数据结构选择 ​

选择合适的数据结构可显著减少内存使用：

数据结构适用场景
String简单键值对、计数器
Hash对象存储、结构化数据
List消息队列、有序数据
Set唯一值、标签系统
ZSet排行榜、带权重数据

5.5 避免阻塞操作 ​

避免使用KEYS等阻塞命令，使用SCAN替代：

bash
SCAN 0 MATCH user:* COUNT 100

六、高级特性 ​

6.1 事务 ​

Redis通过MULTI、EXEC、DISCARD、WATCH实现事务功能。

基本命令：

  • WATCH：监视一个或多个键，被修改则事务被打断
  • MULTI：标记事务块开始
  • EXEC：执行事务队列中的所有命令
  • DISCARD：取消事务

示例：

bash
> MULTI
OK
> INCR foo
QUEUED
> INCR bar
QUEUED
> EXEC

注意：Redis事务并非关系型数据库中的严格事务，某操作失败时不会回滚。

6.2 Lua脚本 ​

Lua脚本允许在Redis服务器端执行原子性操作，减少网络开销。

基本使用：

bash
EVAL "return 'Hello, scripting!'" 0

脚本示例：

lua
local key = KEYS[1]
local value = ARGV[1]
redis.call('SET', key, value)
return redis.call('GET', key)

最佳实践：

  • 优先使用EVALSHA缓存脚本，避免每次传输脚本内容
  • 避免在Lua中执行耗时操作（如循环大列表）
  • 使用redis.pcall增强容错性
  • 做好参数校验和错误处理

应用场景：秒杀库存扣减、分布式锁、限流等需要原子性的场景。

6.3 发布订阅（Pub/Sub） ​

Redis的发布订阅是一种消息通信模式，发布者发送消息，订阅者接收消息。

使用场景：

  • 实时通知和事件处理
  • 聊天应用
  • 缓存失效信号广播
  • UI更新推送

注意：Pub/Sub本质是广播系统，每个订阅者都会收到每条消息。如需消息只投递给一个消费者，应使用Stream。

6.4 Stream（消息队列） ​

Redis 5.0引入的Stream是一种日志型数据结构，专门用于处理消息流和事件日志。

核心特性：

  • 消息持久化
  • 消费者组（Consumer Groups）
  • ACK确认机制

基本操作：

bash
# 添加消息
XADD mystream * field1 value1 field2 value2
# 查询消息
XRANGE mystream - + COUNT 10

消费者组示例：

python
redis.xgroup_create("order_stream", "order_group", id="0", mkstream=True)
messages = redis.xreadgroup("order_group", "consumer1", {"order_stream": ">"}, count=1, block=0)

典型场景：实时日志系统、订单状态追踪、IoT设备数据。

6.5 分布式锁 ​

Redis通过SETNX等命令实现分布式锁。

基本实现：

bash
SETNX lock:resource true EX 30   # 非阻塞加锁
DEL lock:resource                 # 释放锁

Redisson框架：

  • 使用Hash数据结构存储锁信息
  • 内置锁续期机制（Watchdog），防止锁无法释放
  • 支持可重入锁、公平锁、读写锁等
  • 所有操作打包到Lua脚本中原子执行

七、缓存常见问题与解决方案 ​

7.1 缓存穿透 ​

定义：查询不存在的数据，缓存和数据库均无法命中，每次请求直达数据库。

根因：

  • 恶意攻击：构造大量不存在的ID
  • 业务Bug：参数校验不严谨
  • 缓存预热缺失

解决方案：

  1. 接口层入参校验：过滤明显非法的请求
  2. 布隆过滤器：将有效Key写入布隆过滤器，不存在则直接拦截。某电商平台实践显示穿透率下降82%
  3. 空值缓存：对查询结果为空的键设置短期缓存（如30秒-5分钟）

7.2 缓存击穿 ​

定义：热点Key过期失效的瞬间，海量并发请求直接冲击数据库。

解决方案：

  1. 永不过期策略：通过异步线程定期刷新缓存
  2. 分布式锁控制：只允许一个线程重建缓存，其他线程等待
  3. 逻辑过期方案：存储数据时附加过期时间戳，临近过期时异步更新

7.3 缓存雪崩 ​

定义：大量Key在同一时间集中过期，或Redis集群整体宕机。

解决方案：

  • 过期时间随机化，避免集中失效
  • Redis集群部署，保证高可用
  • 限流熔断组件兜底

八、Redis 7.0+新特性 ​

Redis 7.0+完成了从“内存缓存”到“一站式多模数据平台”的架构跃迁。

8.1 Redis Functions ​

替代传统Lua脚本，解决脚本集群兼容性差、无法持久化复用、权限管控弱等痛点。

核心特性：

  • 函数预编译、持久化存储
  • 全集群自动同步
  • 细粒度权限控制、函数版本管理
  • 执行性能较Lua脚本提升40%+

8.2 多线程IO ​

Redis 7.0+实现读写全链路多线程优化，突破单线程IO瓶颈：

  • 高并发场景吞吐提升100%+
  • 延迟降低50%+
  • 支持IO线程数动态配置

8.3 内存管理优化 ​

  • 用Listpack全面替代Ziplist，内存碎片率降低30%+
  • 升级jemalloc 5.3内存分配器

8.4 持久化优化 ​

  • AOF增量重写：磁盘IO降低90%+，CPU占用降低70%+
  • AOF多文件分块存储：备份恢复效率提升10倍+

8.5 其他增强 ​

  • Sharded Pub/Sub：分片发布订阅，网络带宽占用降低90%+
  • ACL增强：支持key粒度的权限控制

数据库层开发-高性能访问-缓存策略：缓存击穿处理 ​

一、缓存击穿概述 ​

1.1 什么是缓存击穿 ​

缓存击穿是指一个被高频访问的热点Key（如秒杀商品、热门新闻、明星动态）在缓存失效的瞬间，海量并发请求（成千上万）同时穿透缓存，直接涌向数据库，导致数据库在极短时间内压力骤增甚至崩溃。

可以用一个生动的比喻来理解：缓存击穿就像一堵坚固的墙上某一个点被反复捶打，当这个点恰好破裂时，墙后所有的洪水瞬间从这个破洞倾泻而出。与缓存穿透（查不存在的数据）和缓存雪崩（大量Key同时失效）不同，击穿的核心特征是**“单点热点 + 高并发 + 瞬间失效”**。

1.2 典型场景 ​

  • 电商秒杀：某款热门商品在整点开始秒杀，该商品的缓存Key恰好在此前几秒过期，成千上万的抢购请求瞬间击穿缓存直达数据库
  • 热点新闻：某明星官宣突发事件，对应的新闻详情页Key缓存失效，大量用户同时刷新阅读
  • 定时抢票：春运车票开售瞬间，热门车次缓存过期，高并发请求压垮余票查询接口
  • 大促活动：双11零点，爆款商品缓存时间计算失误，在流量洪峰到来时失效

1.3 危害 ​

  • 数据库瞬间过载：热点Key承载着远超普通Key的访问量，失效瞬间DB的QPS可能飙升几十甚至上百倍
  • 响应延迟急剧增加：数据库连接池被占满，正常请求排队等待，整体响应时间陡增
  • 连锁故障风险：数据库CPU飙升→慢查询堆积→连接池耗尽→应用服务不可用→上游服务超时→引发更广泛的系统雪崩
  • 业务直接损失：秒杀场景下，缓存击穿可能导致下单接口超时，用户无法成功下单，造成直接经济损失

1.4 与缓存穿透、缓存雪崩的对比 ​

对比维度缓存穿透缓存击穿缓存雪崩
问题本质查询不存在的数据热点Key过期失效大量Key同时失效
影响范围多个不同Key（恶意构造）单个热点Key大量Key（成百上千）
访问数据特征数据本身不存在于DB数据存在于DB，缓存刚好失效数据存在于DB，集体过期
核心原因恶意攻击/异常流量热点Key过期 + 超高并发TTL集中设置/缓存宕机
影响时间持续不断（攻击持续）极其短暂（毫秒~秒级）较长（数分钟以上）
数据库压力特征大量无效空查询针对单条数据的密集重复查询针对大量不同数据的并发查询

二、缓存击穿的成因深度剖析 ​

2.1 核心三要素 ​

缓存击穿的发生需要同时满足三个条件：

  1. 热点数据：该Key承载着极高的访问并发量（QPS可能过万）
  2. 缓存过期：该Key到达TTL时间，从缓存中移除
  3. 瞬间高并发：Key失效的同一毫秒，海量请求同时到达

2.2 为什么会集中在这一瞬间？ ​

在高并发系统中，大量请求几乎在同一时间点到达。如果热点Key在T0时刻失效，那么所有在T0之后到达的请求都会发现缓存为空，进而同时发起数据库查询。这种“同时性”使得数据库瞬间承受的并发量从缓存命中时的近似0，陡增至全部请求量。

2.3 与缓存雪崩的关键区别 ​

特性缓存击穿缓存雪崩
Key的数量单个Key大量Key
失效时间点集中在同一毫秒分散在同一时间段（如凌晨0点）
修复难度相对容易，针对单点处理较复杂，需要系统性方案
数据特征极热数据（如爆款商品）普通或热门数据（批量）

三、缓存击穿的核心解决方案 ​

缓存击穿的应对核心思路是：在热点Key失效的高并发瞬间，只允许一个请求去数据库加载数据，其他请求等待或直接返回旧数据。 具体可分为两大类策略：互斥锁（强一致性） 和 逻辑过期（高可用性）。

3.1 方案一：互斥锁（分布式锁） ​

3.1.1 原理 ​

当缓存失效时，多个线程同时尝试获取分布式锁，只有成功获取锁的一个线程被允许去数据库查询并回填缓存，其他线程则自旋等待或短暂休眠后重试，重试时缓存已被重建，直接命中缓存返回。

这是解决缓存击穿的经典方案，也是保证数据一致性的最强手段。

3.1.2 实现方式一：SETNX + 自旋等待 ​

java
public Product getProductWithMutex(String productId) {
    String cacheKey = "product:" + productId;
    String lockKey = "lock:" + cacheKey;
    
    // 1. 先查缓存
    Product product = redisTemplate.opsForValue().get(cacheKey);
    if (product != null) {
        return product;
    }
    
    // 2. 缓存失效，尝试获取分布式锁
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
    
    if (Boolean.TRUE.equals(locked)) {
        try {
            // 3. Double-Check：再次检查缓存（防止上一个持有锁的线程已重建缓存）
            Product doubleCheck = redisTemplate.opsForValue().get(cacheKey);
            if (doubleCheck != null) {
                return doubleCheck;
            }
            
            // 4. 查询数据库
            Product dbProduct = productMapper.selectById(productId);
            if (dbProduct != null) {
                // 设置过期时间，加入少量随机偏移防止雪崩
                int ttl = 3600 + ThreadLocalRandom.current().nextInt(300);
                redisTemplate.opsForValue().set(cacheKey, dbProduct, ttl, TimeUnit.SECONDS);
            }
            return dbProduct;
            
        } finally {
            // 5. 释放锁
            redisTemplate.delete(lockKey);
        }
    } else {
        // 6. 未获取到锁：休眠后递归重试
        try {
            Thread.sleep(50); // 等待50ms
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return getProductWithMutex(productId); // 递归重试
    }
}

注意事项：

  • 锁必须设置过期时间，防止线程异常崩溃导致死锁
  • 释放锁时建议校验持有者（使用UUID或线程ID），防止误删他人的锁
  • 休眠时间不宜过长（建议10-100ms），避免请求堆积

3.1.3 实现方式二：Redisson 看门狗（自动续期） ​

使用Redisson的看门狗（Watchdog）机制，锁默认过期时间30秒，若业务逻辑执行时间超过30秒，看门狗会自动续期，保证锁不会提前释放：

java
public Product getProductWithRedisson(String productId) {
    String cacheKey = "product:" + productId;
    RLock lock = redissonClient.getLock("lock:" + cacheKey);
    
    // 1. 先查缓存
    Product cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return cached;
    }
    
    try {
        // 尝试加锁，等待3秒，锁自动续期（默认30秒，看门狗自动续期）
        if (lock.tryLock(3, TimeUnit.SECONDS)) {
            try {
                // Double-Check
                Product doubleCheck = redisTemplate.opsForValue().get(cacheKey);
                if (doubleCheck != null) {
                    return doubleCheck;
                }
                
                Product dbProduct = productMapper.selectById(productId);
                if (dbProduct != null) {
                    int ttl = 3600 + ThreadLocalRandom.current().nextInt(300);
                    redisTemplate.opsForValue().set(cacheKey, dbProduct, ttl, TimeUnit.SECONDS);
                }
                return dbProduct;
                
            } finally {
                lock.unlock(); // 释放锁
            }
        } else {
            // 获取锁失败，短暂等待后重试
            Thread.sleep(50);
            return getProductWithRedisson(productId);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return null;
    }
}

3.1.4 优化建议 ​

  • 超时时间设置：锁超时时间应 > 数据库查询 + 缓存写入的总耗时，一般建议3-10秒
  • 锁粒度：每个Key独立加锁，避免全局锁阻塞不同数据的请求
  • 加锁失败策略：
    • 自旋重试：适用于高一致性要求场景
    • 快速失败（Fast Fail） ：返回友好提示“系统繁忙，请稍后重试”，适用于对响应时间敏感的秒杀场景

3.1.5 优缺点 ​

优点缺点
强一致性：保证数据库和缓存数据一致性能损耗：每次缓存失效都有加锁解锁开销
实现相对简单潜在死锁风险：需妥善处理锁释放
防止缓存重建期间的脏数据等待延迟：未获取锁的线程需要等待，增加响应时间
通用性强，适用于绝大多数场景锁竞争激烈时，大量线程排队等待

3.2 方案二：逻辑过期（永不过期 + 异步重建） ​

3.2.1 原理 ​

缓存Key不设置物理过期时间（即Redis中永不过期），而是在缓存Value中额外存储一个逻辑过期时间戳。当读取缓存时，判断逻辑时间是否过期：

  • 若未过期：直接返回数据
  • 若已过期：立即返回旧数据（保证用户响应极快），同时异步发起一个后台线程去数据库加载最新数据并更新缓存

这种策略的核心思想是 “牺牲短暂的一致性，换取绝对的可用性” ，尤其适用于对响应时间极度敏感的场景。

3.2.2 数据结构定义 ​

java
@Data
public class CacheWrapper<T> {
    // 逻辑过期时间戳（毫秒）
    private Long expireTime;
    
    // 实际业务数据
    private T data;
}

3.2.3 完整实现示例 ​

java
@Component
public class ProductService {
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    @Autowired
    private ProductMapper productMapper;
    
    // 缓存Key永不过期（不设置TTL）
    private static final int LOGIC_EXPIRE_SECONDS = 3600; // 逻辑有效期1小时
    
    // 获取商品（逻辑过期方案）
    public Product getProduct(String productId) {
        String cacheKey = "product:" + productId;
        
        // 1. 从缓存获取
        CacheWrapper<Product> wrapper = (CacheWrapper<Product>) 
            redisTemplate.opsForValue().get(cacheKey);
        
        if (wrapper == null) {
            // 2. 缓存完全不存在（首次查询），直接查DB并写入
            return loadFromDBAndCache(productId);
        }
        
        // 3. 检查逻辑是否过期
        if (wrapper.getExpireTime() > System.currentTimeMillis()) {
            // 未过期，直接返回
            return wrapper.getData();
        }
        
        // 4. 逻辑已过期：先返回旧数据，异步刷新
        asyncRefresh(productId, wrapper);
        return wrapper.getData(); // 立即返回旧数据
    }
    
    // 异步刷新缓存
    private void asyncRefresh(String productId, CacheWrapper<Product> oldWrapper) {
        String lockKey = "lock:refresh:" + productId;
        
        // 尝试获取刷新锁（防止并发情况下多个线程重复刷新）
        Boolean gotLock = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", 5, TimeUnit.SECONDS);
        
        if (Boolean.TRUE.equals(gotLock)) {
            // 提交到线程池异步执行
            refreshExecutor.submit(() -> {
                try {
                    // Double-Check：再次检查逻辑过期时间，避免重复刷新
                    CacheWrapper<Product> latest = (CacheWrapper<Product>) 
                        redisTemplate.opsForValue().get("product:" + productId);
                    if (latest != null && 
                        latest.getExpireTime() > System.currentTimeMillis()) {
                        return; // 已被其他线程刷新
                    }
                    
                    // 查询数据库最新数据
                    Product newProduct = productMapper.selectById(productId);
                    if (newProduct != null) {
                        CacheWrapper<Product> newWrapper = new CacheWrapper<>();
                        newWrapper.setData(newProduct);
                        newWrapper.setExpireTime(
                            System.currentTimeMillis() + LOGIC_EXPIRE_SECONDS * 1000
                        );
                        // 写入缓存（Key物理永不过期）
                        redisTemplate.opsForValue().set(cacheKey, newWrapper);
                    }
                } finally {
                    redisTemplate.delete(lockKey);
                }
            });
        }
    }
    
    // 首次加载（同步）
    private Product loadFromDBAndCache(String productId) {
        Product product = productMapper.selectById(productId);
        if (product != null) {
            CacheWrapper<Product> wrapper = new CacheWrapper<>();
            wrapper.setData(product);
            wrapper.setExpireTime(
                System.currentTimeMillis() + LOGIC_EXPIRE_SECONDS * 1000
            );
            // 物理永不过期
            redisTemplate.opsForValue().set("product:" + productId, wrapper);
        }
        return product;
    }
}

3.2.4 线程池配置建议 ​

java
@Configuration
public class RefreshThreadPoolConfig {
    
    @Bean("refreshExecutor")
    public ExecutorService refreshExecutor() {
        // 核心线程数 = CPU核数 * 2，最大线程数 = 核心数 * 4
        int coreSize = Runtime.getRuntime().availableProcessors() * 2;
        return new ThreadPoolExecutor(
            coreSize,
            coreSize * 2,
            60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(1000),
            new ThreadPoolExecutor.DiscardPolicy() // 队列满时丢弃，保证主线程不被阻塞
        );
    }
}

3.2.5 优缺点 ​

优点缺点
响应极快：用户请求无需等待数据库查询数据一致性差：可能存在秒级~分钟级的脏数据
系统高可用：即使数据库短暂抖动，用户仍能读到旧数据实现复杂：需维护逻辑过期时间和异步刷新机制
彻底解决击穿：缓存永不过期，不存在失效瞬间内存占用：缓存数据物理永驻，过期数据不会自动清理
DB压力可控：刷新操作异步化，DB压力平缓冷Key问题：长期不访问的Key也占用内存

3.3 方案三：热点Key提前预热 ​

3.3.1 原理 ​

在流量高峰来临之前，通过后台任务或脚本，主动将热点数据加载到缓存中，并设置合理的过期时间，避免在流量洪峰时刻缓存恰好失效。

3.3.2 实现方式 ​

方式一：定时任务预热

java
@Component
public class CachePreheatScheduler {
    
    // 每天9:55执行预热（假设10:00为流量高峰）
    @Scheduled(cron = "0 55 9 * * ?")
    public void preheatHotProducts() {
        // 1. 从大数据平台或统计日志获取预测的热点商品ID
        List<Long> hotIds = getHotProductIdsFromPredict();
        
        for (Long id : hotIds) {
            Product product = productMapper.selectById(id);
            if (product != null) {
                // 设置随机过期时间，范围10:00~12:00之间随机
                int baseTtl = 7200; // 2小时
                int randomOffset = ThreadLocalRandom.current().nextInt(3600);
                redisTemplate.opsForValue().set(
                    "product:" + id, 
                    product, 
                    baseTtl + randomOffset, 
                    TimeUnit.SECONDS
                );
            }
        }
        log.info("热点缓存预热完成，预热数量: {}", hotIds.size());
    }
}

方式二：手动触发热点标记

java
// 运营后台或管理接口主动标记热点
public void markHotProduct(Long productId) {
    String hotKey = "hot:product:" + productId;
    // 设置标记，有效期2小时
    redisTemplate.opsForValue().set(hotKey, "1", 2, TimeUnit.HOURS);
    // 同时刷新该商品缓存
    refreshProductCache(productId);
}

3.3.3 适用场景 ​

  • 电商大促（双11、618）前预热预估爆款
  • 定时秒杀活动开始前预热
  • 系统上线或重启后的冷启动

3.4 方案四：互斥锁的优化 —— Single Flight ​

3.4.1 原理 ​

Single Flight是Go语言标准库提供的一种机制，在Java中可用LoadingCache或自研实现。它将同一个Key的并发请求合并为一次数据库查询，所有等待的请求共享同一次查询结果。

与分布式锁的区别在于：Single Flight不需要显式加锁，而是通过请求合并（Coalescing） 的方式，将同一时刻针对同一个Key的多个请求折叠为一个。

3.4.2 Java实现示例（使用Guava LoadingCache + 超时） ​

java
import com.google.common.cache.CacheBuilder;
import com.google.common.cache.CacheLoader;
import com.google.common.cache.LoadingCache;

@Service
public class ProductServiceWithSingleFlight {
    
    // 使用LoadingCache实现Single Flight效果
    private final LoadingCache<String, Product> productCache = 
        CacheBuilder.newBuilder()
            .expireAfterWrite(1, TimeUnit.SECONDS) // 同一Key的请求1秒内合并
            .maximumSize(10000)
            .build(new CacheLoader<String, Product>() {
                @Override
                public Product load(String productId) throws Exception {
                    // 只有第一个请求会执行DB查询
                    return productMapper.selectById(productId);
                }
            });
    
    public Product getProduct(String productId) {
        try {
            // 并发请求会被合并为一次load调用
            return productCache.get(productId);
        } catch (ExecutionException e) {
            return null;
        }
    }
}

3.4.3 优缺点 ​

优点缺点
无需分布式锁，减少网络开销仅在单机内有效（JVM级别），分布式环境需结合Redis
代码简洁，实现优雅缓存过期需额外处理（本地缓存 + Redis双写）
对应用透明，无锁竞争数据一致性依赖本地缓存刷新策略

四、方案对比与选型建议 ​

方案一致性响应时间实现复杂度适用场景
互斥锁（分布式锁）强一致中等（有等待延迟）中绝大多数场景（首选）
逻辑过期+异步刷新最终一致极快高超高并发、容忍短暂不一致（秒杀、大促）
热点Key预热强一致（预热期间）快低大促活动、定时秒杀（辅助方案）
Single Flight强一致快中单机内部请求合并

选型决策树 ​

是否需要绝对的数据一致性？
├── 是（金融交易、库存扣减） → 互斥锁（分布式锁）
└── 否（内容展示、新闻详情）
    └── 是否应对极端高并发（QPS > 10万）？
        ├── 是 → 逻辑过期 + 异步刷新（牺牲一致性换可用性）
        └── 否 → 互斥锁（简单可靠）

推荐组合策略（生产级最佳实践） ​

大多数生产系统建议采用 “互斥锁为主 + 预热为辅” 的组合方案：

  1. 日常场景：使用互斥锁方案，保证数据一致性
  2. 大促场景：提前预热热点Key，将Key的过期时间调整到流量高峰之后
  3. 兜底方案：配置限流降级，当数据库压力超过阈值时，返回降级数据或友好提示
  4. 监控告警：针对特定热点Key设置缓存命中率监控，命中率突降立即告警
java
// 组合方案示例：预热 + 互斥锁
public Product getProductWithPreheatAndLock(String productId) {
    // 1. 检查是否预热标记
    if (isHotProduct(productId)) {
        // 热点商品：缓存永不过期 + 异步刷新（或延长过期时间）
        return getProductWithLogicExpire(productId);
    } else {
        // 普通商品：互斥锁
        return getProductWithMutex(productId);
    }
}

五、监控告警与最佳实践 ​

5.1 关键监控指标 ​

监控维度关键指标告警阈值
缓存层热点Key的缓存命中率突降超过20%触发告警
数据库层针对单条数据的QPS突增较基线突增5倍触发告警
应用层获取锁的等待时间超过100ms告警
应用层锁获取失败率超过10%告警

5.2 代码层面最佳实践 ​

  1. Double-Check机制：获取锁后、查询DB前，必须再次检查缓存，防止重复重建
  2. 锁超时设置：锁过期时间 > DB查询耗时，建议3-10秒；使用Redisson看门狗可自动续期
  3. Key命名规范：包含业务前缀，便于监控和问题排查，如product:{id}、order:{id}
  4. 异常处理：DB查询失败时，不写入空值（与穿透不同），重试或抛出异常
  5. 日志记录：记录缓存失效事件和锁竞争情况，便于事后分析

六、总结 ​

缓存击穿是缓存三大经典问题中最突发、最具冲击力的一类，虽然只涉及单个Key，但由于其承载的并发量巨大，破坏力往往不亚于缓存雪崩。

解决缓存击穿的核心思路是：

在热点Key失效的瞬间，通过“请求合并”或“异步重建”的方式，将海量并发请求收敛为一次或零次数据库访问，从而保护数据库不被冲垮。

对比总结缓存穿透缓存击穿缓存雪崩
解决思路前置拦截不存在Key单点请求合并分散失效时间 + 多级兜底
首推方案布隆过滤器互斥锁TTL随机化 + 高可用
备选方案空值缓存逻辑过期多级缓存 + 限流降级

在实际工程中，应根据业务对一致性的要求和并发量级选择合适的方案：

  • 对一致性要求高的场景（如库存、支付），互斥锁是唯一选择
  • 对一致性要求低、可用性要求极高的场景（如内容展示），逻辑过期是最优解
  • 组合方案（预热 + 互斥锁 + 限流）是生产环境的最佳实践

核心原则：永远要为热点Key的失效做好预案，永远不要低估高并发下单个Key失效带来的连锁反应。通过合理的策略选择和监控告警，将缓存击穿的风险降至最低。

数据库层开发-高性能访问-缓存策略：缓存一致性策略 ​

一、缓存一致性问题概述 ​

1.1 什么是缓存一致性问题 ​

在同时使用缓存（如Redis）和数据库（如MySQL）的系统中，缓存一致性是指当数据发生变更时，缓存中的数据与数据库中的数据需要保持同步。由于缓存和数据库是两个独立的存储系统，不具备原生的分布式原子性保证，在并发读写场景下，因操作时序错位、执行失败、网络波动等因素，两份存储的数据可能出现差异，最终引发业务脏读、数据错误。

缓存的核心价值是用空间换时间——加速读请求、降低数据库压力。而一致性方案的核心矛盾，正是在 「读写性能」与「数据准确性」 之间做权衡——不存在兼顾极致性能与绝对强一致的银弹。

1.2 不一致的典型场景 ​

在一个包含MySQL（作为可靠数据源）和Redis（作为缓存）的系统中，所有的写操作都必须同时处理这两个地方，任何一步失败或延迟都会导致不一致：

场景描述
写MySQL成功，写Redis失败Redis中留存旧数据
写Redis成功，写MySQL失败Redis中存在数据库中不存在的“脏数据”
并发读写线程A更新数据库但尚未更新缓存时，线程B读取到旧缓存数据
主从延迟数据库读写分离架构下，从库同步滞后，读请求拿到旧值回写缓存

根本原因只有一句话：缓存和数据库是两个独立存储，无法原子更新。只要是“先操作A，再操作B”的两步动作，就一定可能出现第一步成功、第二步失败或超时的情况。

1.3 一致性等级划分 ​

一致性等级核心定义缓存场景适配性业务适用场景
强一致性任意时刻缓存与数据库数据完全一致极差，需牺牲可用性与性能金融核心交易、支付对账等零容错场景（极少用缓存承载）
最终一致性允许短暂不一致，经有限时间后必然对齐极佳，工业界主流方案电商商品、内容资讯、用户画像等绝大多数互联网业务
弱一致性不一致时间窗口不可控，无明确兜底机制差访问统计、非实时排行榜等辅助数据

在实践中，我们通常追求最终一致性——允许在短暂的时间内数据不一致，但通过一些手段保证数据最终会保持一致。

二、三种经典的缓存读写策略 ​

缓存更新的策略主要分为三种：Cache-Aside Pattern（旁路缓存） 、Read/Write Through Pattern（读写穿透） 和 Write Behind Caching（异步写入） 。

2.1 Cache-Aside Pattern（旁路缓存模式） ​

这是最常用、最经典的缓存模式。核心原则是：应用程序直接与数据库和缓存交互，缓存不作为写入的必经之路。

读流程 ​

  1. 先查询缓存，若命中则直接返回
  2. 若缓存未命中，则查询数据库
  3. 将查询结果写入缓存后返回

写流程 ​

  1. 先更新数据库
  2. 再删除缓存（注意：是删除，不是更新）
java
// 写操作示例
public void updateUser(User user) {
    // 1. 更新数据库
    userDao.update(user);
    // 2. 删除缓存
    redisTemplate.delete("user:" + user.getId());
}

// 读操作示例
public User getUser(Long userId) {
    // 1. 尝试从缓存获取
    User user = redisTemplate.opsForValue().get("user:" + userId);
    if (user != null) {
        return user;
    }
    // 2. 缓存未命中，查询数据库
    user = userDao.selectById(userId);
    if (user != null) {
        // 3. 写入缓存
        redisTemplate.opsForValue().set("user:" + userId, user, 3600, TimeUnit.SECONDS);
    }
    return user;
}

为什么是删除缓存，而不是更新缓存？ ​

这是关键设计点：

  • 性能考虑：如果更新缓存，每次数据库写操作都要伴随一次缓存写操作。如果该数据并不经常被读取，这次缓存写入就是资源浪费
  • 并发安全：在并发写场景下，更新缓存的顺序可能与更新数据库的顺序不一致，导致缓存中是旧数据。而删除操作是幂等的，更为安全
  • 延迟加载更自然：删除缓存后，下一次读取时会触发缓存未命中，从数据库加载最新数据并回填缓存，保证缓存中的数据总是从数据库加载的最新值

适用场景 ​

适用于读多写少、对实时性要求不高的系统。90%以上的业务系统（订单、用户、商品等）都适合。

存在的风险 ​

Cache-Aside依然存在不一致的窗口期：

  1. 线程A更新数据库
  2. 线程B读取数据，发现缓存不存在，从数据库读取旧数据（因为A的事务可能还没提交）
  3. 线程B将旧数据写入缓存
  4. 线程A删除缓存 → 缓存中已是旧数据，但删除操作删了个寂寞（旧数据已经写进去了）

这种情况发生的概率较低，因为通常数据库写操作比读操作耗时更长（涉及锁、日志等）。但在极端并发下仍有可能发生。

2.2 Read/Write Through Pattern（读写穿透模式） ​

在这种模式下，缓存层自己负责与数据库交互。对应用程序来说，它只与缓存交互，数据库的存在对应用是透明的。

  • 读穿透：缓存未命中时，缓存层自动从数据库加载数据并更新缓存
  • 写穿透：写入时缓存层先更新自身数据，再同步更新数据库

优点 ​

  • 对客户端透明，业务代码无需关心底层存储
  • 一致性比Cache-Aside更好

缺点 ​

  • 性能较差：每次写操作都必然涉及一次数据库写入
  • 缓存层需实现完整的数据同步逻辑，对缓存服务性能要求高
  • 若缓存更新成功但数据库更新失败，需实现回滚机制

2.3 Write Behind Pattern（异步写回模式） ​

Write-Through的异步版本。写入操作仅更新缓存，由后台线程定期或批量将缓存变更刷入数据库。

java
// 写入时仅更新缓存
public void asyncUpdate(User user) {
    // 1. 更新缓存（立即返回）
    redisTemplate.opsForValue().set("user:" + user.getId(), user);
    // 2. 异步写入数据库（后台批量处理）
    writeBehindQueue.offer(user);
}

优点 ​

  • 写性能极高：应用写入缓存后立即返回

缺点 ​

  • 有数据丢失风险：缓存宕机时，尚未刷入数据库的变更可能丢失
  • 一致性最弱：适用于允许少量数据丢失的场景，如计数、点赞等

2.4 三种模式对比 ​

模式一致性强度写入性能实现复杂度适用场景
Cache-Aside最终一致高低绝大多数业务（首选）
Read/Write Through较强中中高需要严格缓存控制的场景
Write Behind弱一致极高高计数、点赞等可容忍数据丢失的场景

三、写操作的核心策略对比 ​

3.1 先删缓存，再更新数据库 ❌ ​

这是错误方案，一定会产生脏数据：

时间线程A（写）线程B（读）
T1删除缓存
T2读数据库 → 获取旧数据
T3将旧数据写入缓存
T4更新数据库为新值

结果：缓存中是旧数据，数据库是新数据 → 永久不一致

3.2 先更新数据库，再删除缓存 ✅ ​

这是业界标准正确姿势。绝大多数情况下能保证最终一致性。

极端并发下的不一致窗口（概率极低）：

时间线程A（读）线程B（写）
T1缓存未命中，读数据库旧值
T2更新数据库为新值 → 删除缓存
T3将旧值写入缓存

结果：缓存中是旧数据 → 短暂不一致（不是永久脏数据）

结论：先更新数据库再删除缓存是最优选择，不一致窗口极短且概率极低，对绝大多数业务可接受。

四、进阶保障方案 ​

4.1 延迟双删（Delay Double Delete） ​

原理 ​

针对Cache-Aside中极端并发场景下旧数据被写回缓存的问题，在更新数据库并删除缓存后，延迟一段时间再次删除缓存。

执行流程 ​

  1. 先删除缓存
  2. 更新数据库
  3. 延迟一段时间（如几百毫秒）
  4. 再次删除缓存
java
public void updateWithDelayDoubleDelete(String key, Object newData) {
    // 1. 第一次删除缓存
    redisTemplate.delete(key);
    
    // 2. 更新数据库
    database.update(newData);
    
    // 3. 延迟一段时间（通常几百毫秒）
    try {
        Thread.sleep(500); // 延迟时间需根据业务评估
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    
    // 4. 第二次删除缓存
    redisTemplate.delete(key);
}

注意：这里的“先删缓存”与前面“先更新数据库再删缓存”并不矛盾。延迟双删是在先更新数据库再删缓存的基础上，额外增加了一次前置删除，以覆盖极端并发场景下的脏数据写入。

延迟时间的设定难题 ​

延迟时间如何设置是个棘手的问题：

  • 设置太短：并发场景下仍可能出现数据不一致
  • 设置太长：长时间内存在数据不一致

根本原因在于，并发线程的调度时间不能人为控制（由操作系统统一调度）。延迟时间通常需要通过压测来估算。

适用场景 ​

对数据一致性要求高、并发量大的场景。

4.2 删除缓存失败的重试机制 ​

问题 ​

先更新数据库再删除缓存时，如果删除缓存失败，就会导致脏数据。

解决方案 ​

  • 消息队列重试：将删除操作放入MQ，失败后重试
  • 定时任务重试：定时扫描失败记录，重新执行删除
  • 分布式任务重试：通过分布式任务调度平台保证最终删除成功
java
// 基于MQ的异步重试
public void updateWithRetry(String key, Object newData) {
    // 1. 更新数据库
    database.update(newData);
    
    // 2. 尝试删除缓存
    try {
        redisTemplate.delete(key);
    } catch (Exception e) {
        // 3. 删除失败，发送到MQ进行重试
        messageQueue.send(new CacheDeleteEvent(key));
    }
}

// MQ消费者
@RabbitListener(queues = "cache_delete_queue")
public void handleCacheDelete(CacheDeleteEvent event) {
    try {
        redisTemplate.delete(event.getKey());
    } catch (Exception e) {
        // 重试，进入死信队列
        retryTemplate.execute(context -> {
            redisTemplate.delete(event.getKey());
            return null;
        });
    }
}

4.3 Binlog订阅方案（Canal） ​

原理 ​

通过Canal监听MySQL的Binlog（二进制日志），将数据变更（增、删、改）信息发送至消息队列（如Kafka），程序监听到消息后更新或删除Redis缓存。

架构流程 ​

业务应用 → 只写MySQL（不操作缓存）
                ↓
        MySQL生成Binlog
                ↓
        Canal订阅Binlog
                ↓
        发送变更消息到Kafka
                ↓
        消费者监听 → 更新/删除Redis缓存

优点 ​

  • 与业务代码完全解耦：业务层只需关心数据库操作
  • 一致性有保障：基于数据库自身的变更日志，不会遗漏
  • 高并发下最稳：大厂主流方案

缺点 ​

  • 实现复杂：需引入Canal、Kafka等中间件
  • 运维成本高：需维护额外组件
  • 存在短暂不一致：从Binlog产生到缓存更新有延迟

快速配置步骤 ​

  1. 开启并配置MySQL的Binlog
  2. 重启MySQL服务
  3. 创建Canal专用MySQL用户
  4. 安装并解压Canal
  5. 配置Canal将数据同步到Kafka
  6. 指定同步的数据库和表
  7. 启动Canal服务
  8. 在代码中监听Kafka主题，更新Redis缓存

4.4 版本号控制 ​

原理 ​

在缓存数据中存储版本号，每次数据变更时更新版本号，读取时校验版本号一致性。

java
@Data
public class CacheValue<T> {
    private T data;
    private Long version;  // 版本号
}

// 更新时版本号+1
public void update(String key, Object newData) {
    Long newVersion = redisTemplate.opsForValue()
        .increment("version:" + key, 1);
    CacheValue<Object> cacheValue = new CacheValue<>();
    cacheValue.setData(newData);
    cacheValue.setVersion(newVersion);
    redisTemplate.opsForValue().set(key, cacheValue);
}

// 读取时校验版本号
public Object get(String key) {
    CacheValue<Object> cached = redisTemplate.opsForValue().get(key);
    Long dbVersion = getVersionFromDB(key);
    if (cached != null && cached.getVersion().equals(dbVersion)) {
        return cached.getData();
    }
    // 版本不一致，从DB重新加载
    return loadFromDB(key);
}

五、方案对比与选型建议 ​

5.1 方案全景对比 ​

方案一致性保障实现复杂度业务侵入性适用场景
Cache-Aside（先更新DB再删缓存）最终一致（有极短窗口）低中95%一般场景，并发量不大或一致性要求不高
延迟双删最终一致（窗口更短）中中一致性要求高、并发量大的场景
删除重试机制最终一致（高可靠）中中对缓存删除可靠性要求高的场景
Binlog订阅（Canal）最终一致（最稳）高无基础建设完善、高并发对一致性要求高的场景
版本号控制最终一致（可校验）中高需要可验证一致性的场景
分布式锁（强一致）强一致高高金融交易、库存扣减等零容错场景

5.2 选型决策树 ​

业务对一致性的要求？
├── 强一致（零容忍）
│   └── 分布式锁/事务机制
│       ⚠ 代价：性能损耗约30% RT，有可用性风险
│
└── 最终一致（可容忍短暂不一致）
    ├── 并发量不高 / 团队资源有限
    │   └── Cache-Aside（先更新DB再删缓存）
    │
    ├── 并发量高 / 对一致性要求较高
    │   └── 延迟双删 + 重试机制
    │
    └── 并发量极高 / 基础建设完善 / 希望业务无侵入
        └── Binlog订阅（Canal + Kafka）

5.3 生产级最佳实践 ​

  1. 默认方案：从 Cache-Aside（先更新数据库，再删除缓存） 开始。它简单可靠，适合绝大多数应用
  2. 增强方案：如果Cache-Aside的不一致窗口无法接受，引入延迟双删或消息队列异步删除
  3. 终极方案：对于核心业务和高并发场景，采用Canal订阅Binlog方案，实现业务无侵入的最终一致性
  4. 兜底方案：给缓存设置合理的过期时间，保证即使出现不一致，最终也会因缓存过期而自动修复

5.4 核心原则总结 ​

写数据时，一定是「更新数据库 + 淘汰缓存」，绝对不能「更新数据库 + 更新缓存」。

原因：

  • 更新缓存 = 写放大，高并发下浪费CPU
  • 并发更新会产生覆盖，导致永久脏数据

六、监控与对账 ​

6.1 监控指标 ​

监控维度关键指标说明
缓存删除成功率删除操作的成功率低于阈值需告警
缓存命中率缓存命中率的变化异常下降可能意味着一不一致
数据对账定期比对缓存与DB数据发现不一致触发修复

6.2 定期对账 ​

通过定时任务定期比对缓存和数据库中的数据，发现不一致时触发异步修复：

java
@Component
public class DataConsistencyChecker {
    
    @Scheduled(fixedRate = 60000) // 每分钟执行
    public void syncCheck() {
        List<String> allKeys = database.getAllKeys();
        allKeys.forEach(key -> {
            Data dbData = database.get(key);
            Data cacheData = redisTemplate.opsForValue().get(key);
            if (!Objects.equals(dbData, cacheData)) {
                // 触发异步修复
                asyncRepairCache(key, dbData);
            }
        });
    }
}

七、总结 ​

缓存一致性问题的本质是缓存与数据库是两个独立存储，无法原子更新。解决方案的核心是在 「读写性能」与「数据准确性」 之间做权衡。

核心结论说明
缓存一致性≠强一致性分布式环境下强一致性代价极高，工业界主流是最终一致性
写操作铁律先更新数据库，再删除缓存（不是更新）
默认方案Cache-Aside模式适合95% 的业务场景
进阶方案延迟双删、重试机制、Binlog订阅逐级加强
终极方案Canal订阅Binlog实现业务无侵入的最终一致性
兜底保障缓存设置过期时间 + 定期对账

一个设计良好的“最终一致”方案，配合监控和对账，其整体可靠性和可维护性，往往比一个复杂脆弱、无人敢动的“强一致”分布式事务系统要高。在实际工程中，应根据业务对一致性的要求选择合适的方案，而不是一味追求理论上的“强一致”。

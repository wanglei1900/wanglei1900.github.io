一、概述：什么是哈希分片 ​

哈希分片（Hash-based Sharding / Hashed Sharding）是数据库分片中最常见的策略之一。其核心思想是：通过对数据的某个字段（分片键）进行哈希计算，将哈希值映射到不同的分片（Shard）或服务器上，从而实现数据的均匀分布，最大程度减少单点瓶颈。

简单来说，哈希分片就是用哈希函数打散数据，让数据"随机"但均匀地散落到各个分片上。

MongoDB等数据库对哈希分片的定义更为具体：对分片键的值应用哈希函数（如MD5、SHA-1），将哈希结果映射到固定范围的chunk（如0~2^64-1），实现数据均匀分布。

二、工作原理 ​

2.1 基本流程 ​

哈希分片的工作流程可以概括为四个步骤：

  1. 选定分片键：确定用于分片的字段（如user_id、order_id）
  2. 哈希计算：对分片键的值应用哈希函数（如MurmurHash、CRC32，或简单的取模运算）
  3. 取模映射：将哈希值对分片总数取模，得到分片编号
  4. 数据存储：将数据写入对应的物理分片

数学表达为：

分片编号 = hash(分片键值) % 分片总数

2.2 具体示例 ​

假设有4个分片，对用户ID进行哈希分片：

user_idhash(user_id) % 4目标分片
10012shard_2
10020shard_0
10033shard_3
10041shard_1

数据被"打散"到各个分片，相邻的user_id（1001和1002）被分配到不同的物理节点上。

2.3 哈希函数的选择 ​

哈希函数特点适用场景
取模运算（%）最简单，计算快分片键本身就是整数且分布均匀
MurmurHash非加密哈希，速度快，分布好通用场景，高性能要求
CRC32校验和算法，计算快需要快速散列的场景
MD5/SHA-1加密哈希，强随机性需要强随机性，但计算开销较大

在分布式数据库中间件中，常见的实现包括华为云DDM的MOD_HASH算法（根据拆分键的键值直接按分库数/分表数取余）、UNI_HASH算法（字符串计算哈希值后再取余）等。

2.4 MongoDB的哈希分片实现 ​

MongoDB的哈希分片有独特的实现方式：先计算分片键的哈希值（64位整型），再根据哈希值的范围将文档分布到不同的chunk上。本质上是对哈希值再做了一次"范围分片"。

javascript
// MongoDB中启用哈希分片
sh.shardCollection("articledb.comment", {"nickname": "hashed"})

这种方式的特征是：拥有"相近片键"的文档不会存储在同一个数据块中，数据的分离性更好。

三、哈希分片的优缺点 ​

3.1 优点 ​

① 数据分布均匀，解决热点问题

哈希分片最大的优势在于数据分布的均匀性。良好的哈希函数可以将数据尽可能均匀地散列到各个节点，避免数据倾斜，实现负载均衡。在理想状态下，16个分片的数据偏差率可控制在±2%以内。

② 写能力可充分扩展

由于哈希值的计算是随机的，数据被随机分发到不同的分片上，可以充分扩展写能力，弥补了范围分片在写入方面的不足。对于高写入负载场景（如物联网设备数据上报、用户行为日志等），哈希分片是理想选择。

③ 点查询性能卓越

对于等值查询（如WHERE user_id = 12345），哈希取模能将请求精准定位到单个分片，响应时间可控制在极低水平。某金融交易系统的实践中，等值查询响应时间可控制在5ms以内。

④ 路由计算简单高效

哈希取模的计算非常简单（一次哈希运算+一次取模），写入吞吐量通常比范围分片更高。

3.2 缺点 ​

① 扩容成本极高（核心痛点）

这是哈希分片最严重的缺陷。当分片数量变化时（扩容或缩容），几乎所有数据的哈希映射关系都会改变。

  • 分片数从N扩展到M时，平均有(M-N)/M比例的数据需要重新路由
  • 从10个节点扩容到11个节点时，约90%的数据需要迁移
  • 从3个节点扩容到4个节点时，约66%~75%的数据需要重新分配
  • 某物流系统的真实案例：分片数从8增至16导致42%的数据迁移，耗时超过12小时

② 范围查询性能差（"全表扫描"）

哈希运算会破坏数据的顺序性。相邻的值经过哈希后分布在完全不同的分片上。因此，范围查询（如WHERE user_id BETWEEN 1000 AND 2000）需要扫描所有分片，响应时间可能比单分片查询高出两个数量级。

在哈希分片下，范围查询基本等价于全表扫描。

③ 不适合OLAP场景

由于范围查询性能的极端劣化，哈希分片限制了在OLAP（在线分析处理）场景的应用。

④ 依赖分片键的自身分布

简单取模算法要求拆分列的值自身分布均衡，才能保证哈希均衡。如果分片键本身分布不均（如性别这种低基数字段），哈希也无法解决倾斜问题。

四、哈希分片 vs 其他分片策略 ​

4.1 核心对比 ​

维度哈希分片（取模）一致性哈希范围分片
数据分布✅ 均匀✅ 较均匀❌ 可能不均匀（热点风险）
点查询✅ 精准定位✅ 精准定位一般
范围查询❌ 需扫描全部分片❌ 需扫描全部分片✅ 高效
扩容成本❌ 极高（全量迁移）✅ 低（仅部分迁移）✅ 低（无需迁移数据）
实现复杂度✅ 简单较高中等
适用场景均匀负载、点查询为主动态扩展场景时序数据、范围查询为主

4.2 哈希取模 vs 一致性哈希：关键区别 ​

哈希取模（如hash(key) % N）：

  • 实现简单、性能高、数据分布均匀
  • 痛点：节点变动引发全量重映射，灾难性的数据迁移几乎不可避免

一致性哈希：

  • 将所有节点和数据映射到一个逻辑环形哈希空间
  • 节点变化时，仅影响环上相邻的一小部分数据，数据迁移范围被控制在局部
  • 通过虚拟节点机制进一步解决数据倾斜问题
  • 广泛用于现代分布式系统（如Cassandra、Redis Cluster）

简单来说：哈希取模是"全员搬家"，一致性哈希是"局部调整" 。

4.3 哈希 vs 范围：设计哲学的差异 ​

维度哈希分片范围分片
预分区能力✅ 强（哈希值分布均匀，可等分）❌ 弱（依赖业务数据分布，难以预测）
确定性✅ 高（路由结果可精确预知）❌ 低（依赖调度器动态调整）
写入热点✅ 无（随机分散）❌ 有（自增ID/时间戳导致集中写入）
范围查询❌ 差（等价全表扫描）✅ 好（分区裁剪）

PolarDB-X、YugabyteDB默认使用哈希分区算法，而TiDB、CockroachDB默认使用范围分区算法。这一差异反映了不同数据库在设计哲学上的取舍——前者追求确定性与稳定性，后者追求范围查询的灵活性。

五、主流数据库/中间件的哈希分片实现 ​

5.1 华为云DDM的MOD_HASH算法 ​

华为云分布式数据库中间件DDM提供了多种哈希分片算法。

MOD_HASH：根据拆分键的键值直接按分库数/分表数取余。

sql
-- 分库不分表
CREATE TABLE mod_hash_tb (
    id INT,
    name VARCHAR(30),
    PRIMARY KEY(id)
) dbpartition BY MOD_HASH(ID);

-- 既分库又分表（4个分表）
CREATE TABLE mod_hash_tb (
    id INT,
    name VARCHAR(30),
    PRIMARY KEY(id)
) dbpartition BY MOD_HASH(ID) 
  tbpartition BY MOD_HASH(ID) 
  tbpartitions 4;

路由计算方式：

  • 分库路由结果 = 分库拆分键值 % 分库数
  • 分表路由结果 = 分表拆分键值 % 分表数

如果是字符串类型的拆分键，会先计算字符串的哈希值再进行取模。

5.2 ShardingSphere的哈希分片 ​

ShardingSphere通过配置分片规则实现哈希分片。典型配置中，使用取模算法将设备ID对8取模，生成8个分表。

yaml
# ShardingSphere配置示例（简化）
sharding:
  tables:
    device_data:
      actual-data-nodes: ds$->{0..1}.device_data_$->{0..7}
      table-strategy:
        standard:
          sharding-column: device_id
          precise-algorithm-class-name: 
            org.apache.shardingsphere.api.algorithm.sharding.standard.ModuloTableShardingAlgorithm

最佳实践建议：初始分片数选择2的幂次（2、4、8、16），便于后续动态拆分。

5.3 MongoDB的哈希分片 ​

MongoDB的哈希分片特点：

  1. 对分片键计算64位哈希值
  2. 基于哈希值的范围划分chunk
  3. 数据均匀分布，彻底解决热点问题
  4. 但范围查询需扫描所有分片

MongoDB只允许一个集合使用一种分片策略（哈希或范围），不可同时使用两种。

5.4 MyCat的字符串哈希分片 ​

MyCat支持字符串hash解析算法：初始化一个长度为1024的数组，前512个数为0，后512个数为1，实现字符串到分片的映射。

六、热点问题与解决方案 ​

6.1 哈希分片也有热点？ ​

虽然哈希分片以"解决热点"著称，但并非万无一失：

① 哈希冲突：当不同键的哈希值碰撞到同一分片时，可能引发局部热点。

② 低基数的分片键：如果用性别（只有男/女）作为分片键，哈希后最多只有两个分片有数据。

③ 查询热点：即使数据分布均匀，如果某些分片上的数据被频繁查询，也会形成访问热点。

6.2 解决方案 ​

问题解决方案
哈希冲突二次哈希+链表存储；或使用一致性哈希
低基数分片键选择高基数字段（如用户ID、订单ID）
查询热点增加副本节点；使用缓存层
扩容数据迁移采用一致性哈希替代简单取模

七、最佳实践与选型建议 ​

7.1 何时选择哈希分片 ​

哈希分片最适合以下场景：

场景说明
高写入负载物联网数据上报、日志收集、用户行为追踪
点查询为主80%以上的查询是等值查询（如按ID查用户、按订单号查订单）
数据无明显范围特征分片键无业务语义的顺序性（如用户ID、设备ID）
均匀负载要求需要将数据均匀分布到所有节点
预分区确定性要求高OLTP业务希望数据库性能和稳定性具有确定性

7.2 分片键选择的核心原则 ​

分片键的选择直接决定了哈希分片的成败：

① 高基数（High Cardinality）

  • 分片键的值要足够分散
  • 避免低基数字段（如gender、country），否则会导致数据分布不均
  • 推荐：用户ID、订单ID、设备ID

② 查询模式优先

  • 80%的查询应该能用到分片键作为过滤条件
  • 如果常用查询都不带分片键，每次查询都要扫描所有分片

③ 避免业务语义变化

  • 分片键一旦选定，不应频繁变化
  • MongoDB中，文档的分片键值是不可更改的

7.3 扩容策略优化 ​

哈希取模扩容代价高昂，可采取以下优化策略：

策略说明
预分片初始设置较大分片数（如128、256），即使节点较少，也预留扩展空间
2的幂次分片分片数选择2的幂次（2、4、8、16...），便于后续翻倍扩容
一致性哈希从根本上解决扩容数据迁移问题
增量迁移只迁移受影响的数据，而非一次性迁移所有数据
双写方案扩容期间新旧集群双写，逐步切流，实现无缝扩容

7.4 策略选型决策树 ​

业务查询以点查询（等值查询）为主？
  ├─ 是 → 扩容是否频繁？
  │       ├─ 是 → 一致性哈希（动态扩展友好）
  │       └─ 否 → ✅ 哈希分片（取模）（实现简单、性能高）
  └─ 否 → 范围查询占比高？
          ├─ 是 → 范围分片（范围查询高效）
          └─ 混合查询 → 
              ├─ 点查询为主 → 哈希分片
              ├─ 范围查询为主 → 范围分片
              └─ 各占一半 → 考虑复合分片策略或根据业务权衡

八、总结 ​

哈希分片是数据库分片策略中最基础也最常用的方案之一。其核心优势在于数据分布均匀和点查询高效，天然适合高写入负载、等值查询为主的业务场景。但同时面临扩容成本极高和范围查询性能差两大固有挑战。

在实际生产环境中，哈希分片的选择和优化需注意：

  1. 分片键选择是成败关键：高基数、高频查询、稳定不变
  2. 扩容需提前规划：预分片、2的幂次、或直接采用一致性哈希
  3. 查询模式决定策略：点查询为主选哈希，范围查询为主选范围
  4. 分布式数据库的默认选择各有侧重：PolarDB-X、YugabyteDB默认哈希；TiDB、CockroachDB默认范围，反映了不同设计哲学

理解哈希分片的原理、优缺点和适用场景，是进行分布式数据库架构设计的基础能力。在实际选型时，需结合业务的数据特征、查询模式和扩展需求，综合权衡后做出决策。

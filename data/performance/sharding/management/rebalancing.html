一、概述：什么是分片重平衡 ​

1.1 定义 ​

分片重平衡（Rebalancing） ，又称分区再平衡，是指将数据负载从集群中的一个节点向另一个节点移动的过程。当分布式数据库集群的节点数量发生变化（扩容或缩容）、节点发生故障需要其他节点接管、或数据分布出现严重不均时，系统需要重新调整数据在各个节点上的分布，这个过程就是分片重平衡。

1.2 为什么需要分片重平衡 ​

随着业务发展，数据库集群会面临多种变化：

  • 查询负载增加：需要更多CPU来处理负载
  • 数据规模增加：需要更多磁盘和内存来存储
  • 节点可能故障：需要其他节点接管失效节点
  • 业务扩容需求：主动增加节点以提升系统容量和吞吐能力
  • 数据倾斜：部分节点数据量远超其他节点，导致性能瓶颈

所有这些变化都要求数据、请求能够从一个节点平稳地转移到另一个节点。

一个典型的触发场景：某电商平台在618大促期间，因未做合理的分库分表和扩容规划，导致核心交易系统瘫痪2小时，直接损失超千万。分片重平衡机制正是为了应对这类场景——在业务增长时能够平滑扩容，避免系统崩溃。

二、分片重平衡的核心目标 ​

无论采用哪种分区策略，分片重平衡通常需要满足以下三个核心目标：

目标说明
均匀分布重平衡后，负载、数据存储、读写请求应在集群内更均匀地分布
持续可用重平衡执行过程中，数据库应能继续正常处理读写请求
最小迁移避免不必要的负载迁移，以加速重平衡效率，并尽量减少网络和磁盘I/O影响

三、分片重平衡的常见策略 ​

3.1 反面教材：hash mod N ​

取模分片（如 hash(key) mod N）看似简单直接，但在节点数量变化时会引发灾难性的数据迁移。

示例说明：

  • 假设 hash(key)=123456，最初有10个节点
  • 该key落在节点6（123456 mod 10 = 6）
  • 当集群扩展到11个节点，该key需要移动到节点3（123456 mod 11 = 3）
  • 当扩展到12个节点，该key需要移动到节点0（123456 mod 12 = 0）

结论：节点数量N每次变化，大多数key都需要从一个节点移动到另一个节点，迁移成本巨大。因此，单纯依赖取模分片且频繁扩容的系统是不可取的。

3.2 固定数量的分区（Fixed Number of Partitions） ​

核心思想：创建比节点数量多得多的分区，为每个节点分配多个分区。

实现方式：

  • 例如10个节点的集群，逻辑上划分为1000个分区，每个节点约分配100个分区
  • 新增节点时，新节点从现有每个节点中"窃取"一些分区，直到全局再次平衡
  • 分区的总数不变，key到分区的映射关系不变，唯一变化的是分区所在的物理节点

优点：

  • 扩容时只需迁移部分分区，而非重新分配所有数据
  • 可以按节点硬件能力差异化分配（性能强的节点分配更多分区）

缺点：

  • 分区数量在数据库初次建立时确定，之后难以改变
  • 初始分区数决定了最大节点数量，需要充分考虑未来业务需求
  • 分区太多会产生管理开销，分区太少则每个分区数据量过大
  • 若数据总量变动很大，固定分区数难以达到最佳性能

典型应用：Elasticsearch、Couchbase等系统采用此策略。

3.3 动态分区（Dynamic Partitioning） ​

对于使用范围分区（Range Partitioning）的数据库，分区边界可以动态调整。

核心思想：

  • 当分区数据量超过阈值时，自动拆分为两个分区
  • 当分区数据量低于阈值时，自动与相邻分区合并
  • 分区数量随数据量动态变化

优点：分区大小保持相对稳定，单个分区的数据量可控

缺点：分区数量动态变化增加了路由和元数据管理的复杂度

3.4 按节点比例分区（Partition per Node） ​

这种策略下，每个节点拥有固定数量的分区（如每个节点64个分区）。新增节点时，系统在全局范围内重新分配分区。

特点：兼顾了固定分区策略的稳定性和动态分区的灵活性，但实现复杂度介于两者之间。

四、主流中间件的分片重平衡实现 ​

4.1 Apache ShardingSphere 弹性伸缩 ​

ShardingSphere 提供了完整的弹性伸缩（弹性扩容/缩容）解决方案，采用 "双集群切换" 的方式实现平滑迁移。

4.1.1 设计特点 ​

优点：

  • 伸缩过程中，原始数据不受任何影响
  • 伸缩失败无风险（可回滚）
  • 不受分片策略限制

缺点：

  • 在一定时间内存在冗余服务器（双集群运行）
  • 所有数据都需要移动

4.1.2 四阶段执行流程 ​

ShardingSphere 将弹性伸缩拆解为4个主要阶段：

第一阶段：准备阶段

  • 进行数据源连通性及权限校验
  • 进行存量数据统计、日志位点记录
  • 根据数据量和用户设置的并行度，对迁移任务进行分片

第二阶段：存量数据迁移阶段

  • 执行准备阶段拆分好的存量数据迁移作业
  • 采用JDBC查询方式，直接从数据节点读取数据
  • 使用新分片规则将数据写入新集群

第三阶段：增量数据同步阶段

  • 由于存量迁移耗时较长，此阶段同步期间业务新增的数据
  • 基于CDC（Change Data Capture） 技术，通过订阅并解析数据库日志实现
    • MySQL：订阅并解析binlog
    • PostgreSQL：采用官方逻辑复制（test_decoding）
  • 捕获的增量数据同样根据新规则写入新数据节点

第四阶段：规则切换阶段

  • 存在短暂的业务只读窗口期
  • 通过设置数据库只读或ShardingSphere熔断机制，让旧数据节点静态化
  • 确保增量同步完全完成
  • 通过配置中心修改配置，将业务导向新规则集群
  • 窗口期短则数秒，长则数分钟

当前状态：ShardingSphere弹性伸缩模块当前处于alpha开发阶段。

4.2 MongoDB 分片重平衡 ​

MongoDB 通过均衡器（Balancer） 和 Chunk（数据块）迁移 实现分片重平衡。

4.2.1 核心机制 ​

  • 数据通过分片键哈希值分配
  • 集群将数据划分为多个Chunk（默认每个Chunk约64MB-128MB）
  • 均衡器在后台持续监控各分片的数据量

4.2.2 触发条件 ​

当分片间数据量差异超过阈值时触发迁移：

最大分片数据量 / 总数据量 > 1.2

目标：使每个分片数据量趋近平均值。

4.2.3 操作方式 ​

自动重平衡（默认启用）：

javascript
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { stopped: false } }
)

手动控制迁移窗口（设置在低峰期运行）：

javascript
sh.setBalancerState(true)
sh.startBalancer({ timeWindow: { start: "23:00", stop: "06:00" } })

监控进度：

javascript
sh.isBalancerRunning()  // 检查是否正在迁移
db.chunks.find({ "onCurrentShard": false })  // 查看待迁移数据块

4.2.4 关键注意事项 ​

  • 分片键选择：扩容后需确保分片键仍支持高效分布
  • 网络带宽：数据迁移占用带宽，建议在业务低峰操作
  • 磁盘空间：迁移过程中需预留临时空间（约迁移数据量的1.1倍）
  • 中止操作：紧急情况下可暂停迁移：sh.stopBalancer()

4.3 ClickHouse 分片重平衡 ​

ClickHouse 原生缺乏数据自动再平衡机制，使得分片数量调整后的数据迁移成为技术难点。

4.3.1 解决方案：clickhouse-copier ​

ClickHouse官方提供了 clickhouse-copier 工具用于集群间数据迁移。

核心特性：

  • 基于ZooKeeper的协同调度：所有worker节点通过ZooKeeper协调任务分配，避免重复迁移或遗漏
  • 分片级并行处理：每个分片的数据迁移独立进行，最大化利用集群IO和CPU资源
  • 原子性保证：采用类似两阶段提交的机制，确保数据要么完整迁移，要么完全不迁移

对比手动迁移：

维度clickhouse-copier手动迁移
并行度全自动并行需自行实现并发控制
一致性保证内置完整性校验依赖人工验证
资源占用可调节的流量控制容易引发网络拥塞
监控能力集成ZooKeeper任务状态跟踪需要额外开发监控系统

4.3.2 手动分区迁移方案 ​

如果需要对已有数据进行再平衡，且数据已经分区，可以考虑先分离分区，再重新挂载到新分片的方式。此方案更为手动，但可能更快且资源消耗更少。

4.4 MyCat 扩容方案 ​

MyCat 的扩容面临类似的挑战。实践中，MyCat集群在线扩容可通过以下方式实现：

  • 将已有的从库分片提升为物理分片，实现快速扩展（如4分片→8分片）
  • 配置数据分片的双主复制
  • 在中间件节点修改配置，从旧配置切换到新配置

最佳实践：最好事先规划好分片的数量，数据扩容时按分片组扩容，原有分片组的数据不需要迁移。

五、一致性哈希与分片重平衡 ​

5.1 基本原理 ​

一致性哈希是解决分片重平衡问题的经典算法。其核心思想是哈希环与虚拟节点的结合。

工作流程：

  1. 将节点和数据映射到一个环形哈希空间
  2. 数据通过哈希计算后在环上定位
  3. 按顺时针方向找到最近的节点
  4. 节点变化时，仅影响相邻节点的数据

5.2 核心优势 ​

传统哈希分片方法在节点增减时易引发大规模数据迁移，导致系统不可用。一致性哈希通过环状拓扑与虚拟节点机制，将数据迁移范围控制在局部。

量化效果：当集群规模变化时，仅需迁移相邻节点的部分分片，将数据迁移量控制在 O(1/n) 级别。

5.3 虚拟节点机制 ​

为缓解数据分布不均的问题，一致性哈希引入了虚拟节点（Virtual Nodes） ：

  • 每个物理节点对应多个虚拟节点
  • 通过增加虚拟节点数量来平衡数据分布
  • 物理节点承载多个虚拟分片

应用价值：在系统扩展时最小化数据迁移量，仅迁移必要的数据块，避免了全量数据迁移的高开销。系统能够平滑扩展，减少因扩展引起的性能损失。

六、分片重平衡的关键挑战与最佳实践 ​

6.1 数据倾斜问题 ​

定义：在分布式数据库中，数据分布不均导致部分节点负载过高，而其他节点闲置的现象。

严峻现实：根据对多家实施案例的复盘，超过70%的分布式数据库项目都经历过数据倾斜带来的性能波动。

解决思路：

  • 热点数据识别
  • 分片策略优化
  • 负载均衡调度

6.2 迁移过程中的资源争抢 ​

常见问题包括：

  • 迁移任务抢占IO与CPU资源，导致查询延迟升高
  • 未合理规划迁移批次，造成热点分片持续过载
  • 缺乏限流策略，使网络带宽饱和

解决方案：

  • 分批次迁移：不要试图一次性迁移所有数据，而是将数据分片打散，按优先级和负载情况分批次进行迁移
  • 设置迁移窗口：在业务低峰期执行迁移
  • 限流控制：对迁移速度进行流量控制
  • 熔断机制：当某节点连续出现超时，暂停其上的迁移任务

6.3 数据一致性与原子性 ​

重平衡过程中，保证数据一致性是最大的技术挑战。

核心要点：

  • 数据均衡的本质是在保证强一致性或最终一致性的前提下重新分配数据分片
  • 锁机制和事务日志（WAL）的生成量会呈指数级增长

ShardingSphere的解决方案：通过双集群切换+CDC增量同步，配合短暂的只读窗口期确保最终一致性。

clickhouse-copier的方案：采用类似两阶段提交的机制，确保数据要么完整迁移，要么完全不迁移。

6.4 扩容策略选择 ​

策略迁移量实现复杂度适用场景
hash mod N极高（几乎所有数据）低❌ 不推荐用于需扩容的系统
固定数量分区中等（部分分区迁移）中数据量可预估、扩容频率低
动态分区低（仅拆分/合并边界）高数据量变化大、需频繁调整
一致性哈希低（仅相邻节点）中需频繁扩容、追求平滑扩展
分片组扩容极低（组内无需迁移）中有充分前期规划能力

6.5 最佳实践总结 ​

  1. 提前规划：在设计阶段就应考虑未来的扩容需求，选择合适的分片策略
  2. 分区数要远大于节点数：为未来扩容留足空间
  3. 选择合适的分片键：高区分度、数值型、核心查询携带
  4. 在低峰期执行重平衡：设置迁移时间窗口
  5. 监控与可观测性：实时监控数据分布标准差、查询延迟等指标
  6. 分批迁移：避免一次性大规模迁移导致系统抖动
  7. 准备回滚方案：确保迁移失败时能快速回退
  8. 扩容后观察：每次扩容后观察24小时业务指标，确认无异常后再继续操作

七、总结 ​

分片重平衡是分布式数据库运维中最复杂、风险最高的操作之一，它直接关系到系统的扩展性、可用性和数据一致性。

理解分片重平衡需要把握以下要点：

  1. 触发原因：节点增减、故障接管、数据倾斜、业务增长
  2. 三大目标：均匀分布、持续可用、最小迁移
  3. 策略演进：从简单的 hash mod N（反面教材）→ 固定数量分区 → 动态分区 → 一致性哈希
  4. 主流实现：ShardingSphere（四阶段双集群切换）、MongoDB（Chunk迁移+均衡器）、ClickHouse（clickhouse-copier工具）
  5. 核心技术：一致性哈希+虚拟节点、CDC增量同步、双集群切换
  6. 关键挑战：数据倾斜、资源争抢、一致性保证、原子性
  7. 最佳实践：提前规划、分批迁移、低峰执行、监控回滚

核心启示：没有"零代价"的重平衡方案。架构师需要在数据均匀性、迁移成本、系统可用性三者之间做出权衡。一致性哈希通过将全局迁移转化为局部操作，显著降低了节点变动时的系统重构成本，是目前应对频繁扩缩容场景的主流选择。而像ShardingSphere这样的中间件，则通过"双集群切换"的思路，将重平衡对在线业务的影响降到最低。

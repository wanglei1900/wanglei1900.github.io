一、Redis概述与核心设计 ​

1.1 Redis简介与定位 ​

Redis（Remote Dictionary Server）是一个开源的、基于内存的键值存储系统，支持多种数据结构。它不仅仅是简单的key-value存储，更是一个数据结构服务器。

核心特性：

  • 内存存储为主，提供持久化选项
  • 支持多种数据结构：字符串、列表、集合、有序集合、哈希表等
  • 单线程事件循环模型（Redis 6.0+引入多线程I/O）
  • 支持事务、Lua脚本、发布/订阅
  • 内置复制、哨兵、集群模式

1.2 Redis的整体架构 ​

二、Redis对象系统：redisObject ​

2.1 redisObject结构定义 ​

所有Redis键值对中的值都是通过redisObject结构表示的：

c
typedef struct redisObject {
    unsigned type:4;        // 对象类型：STRING, LIST, SET, ZSET, HASH
    unsigned encoding:4;    // 底层编码方式
    unsigned lru:LRU_BITS;  // LRU时间戳或LFU访问频率
    int refcount;           // 引用计数，用于内存回收
    void *ptr;              // 指向实际数据结构的指针
} robj;

2.2 对象类型与编码映射 ​

Redis为每种数据类型提供了多种底层编码实现，根据数据特征自动选择最优编码：

数据类型可能编码选择条件
STRINGint, embstr, raw根据字符串长度和内容
LISTziplist, linkedlist, quicklist元素数量和大小
SETintset, hashtable元素类型和数量
HASHziplist, hashtable字段数量和值大小
ZSETziplist, skiplist+dict元素数量和值大小

三、字符串（String）的实现 ​

3.1 字符串的三种编码 ​

3.1.1 INT编码 ​

  • 条件：字符串表示64位有符号整数范围内的数字
  • 存储：直接将整数值存储在redisObject.ptr中（实际上ptr不再是指针，而是直接存储值）
  • 内存布局：
c
redisObject.type = REDIS_STRING
redisObject.encoding = REDIS_ENCODING_INT
redisObject.ptr = 12345  // 直接存储整数值

3.1.2 EMBSTR编码 ​

  • 条件：字符串长度 ≤ 44字节（Redis 5.0+）
  • 特点：redisObject和SDS结构在连续内存中分配
  • 内存布局：
┌─────────────┬─────────────────┐
│ redisObject │ SDS头部 + 数据   │
└─────────────┴─────────────────┘
（连续内存块，一次分配）

3.1.3 RAW编码 ​

  • 条件：字符串长度 > 44字节
  • 特点：redisObject和SDS分开分配内存

3.2 简单动态字符串（SDS） ​

3.2.1 SDS结构定义 ​

c
struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;        // 已使用长度
    uint8_t alloc;      // 分配的总容量
    unsigned char flags;// SDS类型：sdshdr5/8/16/32/64
    char buf[];         // 柔性数组，存储实际字符串
};

3.2.2 SDS的优势 ​

  1. O(1)时间复杂度获取长度：直接读取len字段
  2. 二进制安全：不依赖\0终止符，可以存储任意二进制数据
  3. 缓冲区保护：
    • 空间预分配：增长时，len < 1MB则alloc = len * 2；len ≥ 1MB则每次增加1MB
    • 惰性空间释放：缩短时不立即释放内存，减少内存重分配
  4. 兼容C字符串：buf末尾自动添加\0，可以直接使用C字符串函数

四、列表（List）的实现 ​

4.1 编码演进 ​

  • Redis 3.2之前：小列表用ziplist，大列表用linkedlist
  • Redis 3.2+：统一使用quicklist

4.2 快速列表（Quicklist） ​

4.2.1 Quicklist结构 ​

c
typedef struct quicklist {
    quicklistNode *head;    // 头节点
    quicklistNode *tail;    // 尾节点
    unsigned long count;    // 所有ziplist中entry总数
    unsigned long len;      // quicklistNode节点数
    int fill : QL_FILL_BITS;// ziplist大小限制
    unsigned int compress : QL_COMP_BITS; // LZF压缩深度
} quicklist;

typedef struct quicklistNode {
    struct quicklistNode *prev;
    struct quicklistNode *next;
    unsigned char *zl;           // 指向ziplist的指针
    unsigned int sz;             // ziplist字节大小
    unsigned int count : 16;     // ziplist中entry数量
    unsigned int encoding : 2;   // RAW=1, LZF=2
    unsigned int container : 2;  // NONE=1, ZIPLIST=2
    unsigned int recompress : 1; // 临时解压标记
    unsigned int attempted_compress : 1;
    unsigned int extra : 10;     // 预留字段
} quicklistNode;

4.2.2 Quicklist设计原理 ​

┌────────────┬────────────┬────────────┐
│ quicklist  │ quicklist  │ quicklist  │
│   Node     │   Node     │   Node     │
│  (ziplist) │  (ziplist) │  (ziplist) │
└────────────┴────────────┴────────────┘
       ↑           ↑           ↑
   双向链表连接，每个节点包含一个ziplist

优势：

  • 结合了双向链表（便于修改）和ziplist（内存紧凑）的优点
  • 可配置的压缩：可以压缩中间节点以节省内存
  • 可配置的节点大小：通过list-max-ziplist-size控制

4.3 Ziplist（压缩列表） ​

4.3.1 Ziplist内存布局 ​

┌──────────┬────────┬────────┬────────┬────────┬────────┐
│ zlbytes  │ zltail │ zllen  │ entry1 │ entry2 │ ...    │ zlend │
└──────────┴────────┴────────┴────────┴────────┴────────┘
  • zlbytes：整个ziplist占用的内存字节数
  • zltail：最后一个entry的偏移量，便于快速定位尾部
  • zllen：entry数量（当小于65535时准确）
  • zlend：特殊值0xFF，标识ziplist结尾

4.3.2 Entry结构 ​

┌─────────────────────────────┐
│ prevlen │ encoding │ content │
└─────────────────────────────┘
  • prevlen：前一个entry的长度，1或5字节
  • encoding：内容编码，表示类型（整数/字符串）和长度
  • content：实际存储的数据

4.3.3 连锁更新问题 ​

当插入或删除元素导致相邻entry的prevlen字段需要扩展时，可能引发连锁更新，最坏情况O(N²)复杂度。但在实际中很少发生。

五、哈希表（Hash）的实现 ​

5.1 两种编码方式 ​

5.1.1 Ziplist编码（小哈希） ​

  • 条件：
    • 所有field和value长度都小于hash-max-ziplist-value（默认64字节）
    • field数量小于hash-max-ziplist-entries（默认512）
  • 存储格式：
┌────────┬────────┬────────┬────────┐
│ field1 │ value1 │ field2 │ value2 │ ...
└────────┴────────┴────────┴────────┘
（交替存储field和value）

5.1.2 Hashtable编码（字典） ​

5.1.2.1 字典结构 ​
c
typedef struct dict {
    dictType *type;     // 类型特定函数
    void *privdata;     // 私有数据
    dictht ht[2];       // 两个哈希表，用于渐进式rehash
    long rehashidx;     // rehash进度，-1表示未进行
    unsigned long iterators; // 正在运行的迭代器数量
} dict;

typedef struct dictht {
    dictEntry **table;      // 哈希表数组
    unsigned long size;     // 表大小
    unsigned long sizemask; // 大小掩码，用于计算索引值
    unsigned long used;     // 已有节点数量
} dictht;

typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    struct dictEntry *next; // 链表下一个节点
} dictEntry;
5.1.2.2 哈希算法 ​
c
// 使用MurmurHash2或SipHash（防止HashDoS）
hash = dict->type->hashFunction(key);
index = hash & dict->ht[0].sizemask;
5.1.2.3 渐进式Rehash ​

触发条件：负载因子(used/size) ≥ 1时，如果正在执行BGSAVE/BGREWRITEAOF，则≥5时才触发。

过程：

  1. 为ht[1]分配空间：ht[1].size = 第一个大于等于ht[0].used * 2的2ⁿ
  2. 设置rehashidx = 0，开始rehash
  3. 每次对字典的CRUD操作时，顺带迁移ht[0].table[rehashidx]的整个桶
  4. rehashidx++，直到所有桶迁移完成
  5. 释放ht[0]，将ht[1]设置为ht[0]，创建新的ht[1]，rehashidx = -1

特点：

  • 避免一次性rehash导致的长时间阻塞
  • 在rehash期间，查找先在ht[0]进行，找不到再到ht[1]
  • 新增元素直接添加到ht[1]

六、集合（Set）的实现 ​

6.1 两种编码方式 ​

6.1.1 Intset编码（整数集合） ​

  • 条件：所有元素都是整数，且元素数量小于set-max-intset-entries（默认512）
  • 特点：有序、紧凑的整数数组
c
typedef struct intset {
    uint32_t encoding;  // 编码方式：INTSET_ENC_INT16/32/64
    uint32_t length;    // 元素数量
    int8_t contents[];  // 柔性数组，按encoding存储整数
} intset;

升级机制： 当新添加的元素无法用当前编码表示时，intset会升级：

  1. 计算新编码所需空间
  2. 重新分配内存
  3. 将原有元素转换为新编码，并保持有序性
  4. 添加新元素 注意：只升级不降级

6.1.2 Hashtable编码 ​

  • 条件：包含非整数元素，或元素数量超过阈值
  • 实现：与Hash类型相同，但value设为NULL，只使用key

七、有序集合（ZSet）的实现 ​

7.1 两种编码方式 ​

7.1.1 Ziplist编码（小有序集合） ​

  • 条件：
    • 元素数量 < zset-max-ziplist-entries（默认128）
    • 所有成员长度 < zset-max-ziplist-value（默认64字节）
  • 存储格式：
┌────────┬────────┬────────┬────────┐
│ member1│ score1 │ member2│ score2 │ ...
└────────┴────────┴────────┴────────┘
（成员和分值交替存储，按score排序）

7.1.2 SkipList + Dict编码 ​

7.1.2.1 组合结构 ​
c
typedef struct zset {
    dict *dict;         // 字典：member -> score，O(1)查找
    zskiplist *zsl;     // 跳表：按score排序，支持范围操作
} zset;

双索引设计优势：

  • 字典：支持O(1)的成员查找和更新
  • 跳表：支持O(logN)的范围查询和排序操作
7.1.2.2 跳表（SkipList）实现 ​
c
#define ZSKIPLIST_MAXLEVEL 32  // 最大层数
#define ZSKIPLIST_P 0.25       // 层数增加概率

typedef struct zskiplistNode {
    sds ele;                    // 成员字符串
    double score;               // 分值
    struct zskiplistNode *backward; // 后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针
        unsigned long span;     // 跨度，用于排名
    } level[];
} zskiplistNode;

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;
    unsigned long length;       // 节点数量
    int level;                  // 最大层数
} zskiplist;

跳表层级示例：

Level 3: 头 → 节点3 → NULL
Level 2: 头 → 节点1 → 节点3 → 节点5 → NULL
Level 1: 头 → 节点1 → 节点2 → 节点3 → 节点4 → 节点5 → NULL

节点创建时的随机层数算法：

c
int zslRandomLevel(void) {
    int level = 1;
    // 每增加一层的概率为P
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}

跳表与平衡树的对比：

特性跳表平衡树（AVL/红黑树）
实现复杂度简单复杂
范围查询简单（双向链表）需要中序遍历
并发控制相对简单复杂
内存占用平均1.33指针/节点2指针/节点（左右子树）

八、Redis内存管理与优化 ​

8.1 内存分配器 ​

Redis使用zmalloc封装了系统内存分配，提供：

  • 内存使用统计
  • 内存碎片控制
  • 支持多种底层分配器（jemalloc/tcmalloc/libc）

8.2 内存回收策略 ​

8.2.1 引用计数 ​

  • 每个redisObject.refcount记录被引用次数
  • 为0时立即回收内存

8.2.2 淘汰策略 ​

当内存达到maxmemory时，根据maxmemory-policy：

  1. noeviction：不淘汰，返回错误（默认）
  2. allkeys-lru：从所有key中淘汰最近最少使用的
  3. volatile-lru：从设过期时间的key中淘汰LRU
  4. allkeys-random：随机淘汰所有key
  5. volatile-random：随机淘汰设过期时间的key
  6. volatile-ttl：淘汰剩余时间最短的key
  7. allkeys-lfu / volatile-lfu：淘汰使用频率最低的

8.3 内存碎片整理 ​

Redis 4.0+引入主动内存碎片整理：

  • 通过activedefrag配置开启
  • 复制数据到新位置，释放旧内存块
  • 受active-defrag-ignore-bytes和active-defrag-threshold-lower控制

九、高级数据结构内部实现 ​

9.1 HyperLogLog ​

  • 用途：基数统计，误差率0.81%
  • 内存：固定12KB（16384个6-bit寄存器）
  • 原理：基于调和平均数估计基数

9.2 Bitmap ​

  • 实现：基于String的位操作
  • 存储：SDS + 位操作函数
  • 应用：用户签到、活跃统计

9.3 GeoHash ​

  • 实现：基于ZSet，score存储GeoHash值
  • 编码：将经纬度编码为52位整数（26位分别表示经度和纬度）

9.4 Stream ​

  • 实现：基数树（Rax） + 列表
  • 结构：
c
typedef struct stream {
    rax *rax;               // 消息ID -> 消息内容的映射
    uint64_t length;        // 消息数量
    streamID last_id;       // 最后一条消息ID
    rax *cgroups;           // 消费者组
} stream;

十、性能特征与最佳实践 ​

10.1 时间复杂度总结 ​

操作类型平均复杂度最坏情况
GET/SETStringO(1)O(1)
LPUSH/RPUSHListO(1)O(N)（内存重分配）
HGET/HSETHashO(1)O(N)（rehash时）
SADD/SISMEMBERSetO(1)O(N)（rehash时）
ZADD/ZRANGEZSetO(logN)O(N)（编码转换时）

10.2 内存优化建议 ​

  1. 小数据使用压缩编码：
bash
# 配置参数
hash-max-ziplist-entries 512
hash-max-ziplist-value 64
list-max-ziplist-size -2  # -2表示8KB，-1表示4KB

  1. 使用合理的数据类型：

    • 频繁修改的列表用List，不频繁的用String + JSON
    • 需要范围查询的用ZSet，不需要的用Hash

  2. 控制key长度：过长的key会占用大量内存

  3. 使用共享对象：Redis会共享0~9999的整数对象

10.3 持久化与数据结构 ​

RDB持久化：

  • 保存时使用写时复制（COW）
  • 大内存页可能导致阻塞

AOF持久化：

  • 记录所有写命令
  • 重写时创建新AOF文件，避免阻塞

十一、Redis 6.0+新特性 ​

11.1 多线程I/O ​

  • 主线程：命令执行（仍单线程）
  • I/O线程：网络读写（可配置1-16个）
  • 配置：io-threads 4，io-threads-do-reads yes

11.2 客户端缓存 ​

  • 服务端协助的客户端缓存（Tracking）
  • 减少重复查询，降低服务端压力

十二、总结 ​

Redis的数据结构设计体现了空间与时间的精妙平衡：

  1. 编码自适应：根据数据特征自动选择最优编码
  2. 渐进式优化：rehash、持久化等避免长时间阻塞
  3. 混合结构：如ZSet的字典+跳表组合，兼顾不同操作
  4. 内存友好：多种压缩编码减少内存占用

理解Redis内部实现有助于：

  • 合理选择数据结构
  • 优化内存使用
  • 诊断性能问题
  • 设计高效应用

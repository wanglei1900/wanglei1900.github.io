Redis 实战案例分析 ​

📋 一、Redis 海量车辆实时速度排行榜 ​

🔰 P1 层级：基础数据结构选型（考察基本功） ​

Q1：为什么存储“车辆当前速度”不用 Hash，而用 String？

考察点：是否了解 Redis 底层编码差异，是否关注过期时间。

  • ① Hash 无法对单个 Field 设置独立 TTL，如果车辆离线，无法自动清理，会产生内存泄漏。
  • ② String 的 SETEX 支持原子设置过期时间，契合“当前速度”的实时属性。
  • ③ 如果速度是整数/小数，String 底层有 embstr 和整数编码优化，读取性能极高。

Q2：你在 String 中存储速度时，为什么建议乘以 10 转成整数？不转可以吗？

考察点：是否关注内存占用和序列化开销。

  • 可以存浮点数字符串（如 "85.5"），但 Redis 处理字符串比处理整数更耗 CPU 和内存。转成整数 855 后，Redis 会启用整数编码（OBJ_ENCODING_INT），节省 30%~50% 内存。如果业务需要更高精度（如 85.53），可以乘以 100。

Q3：如果要存的“速度”不仅是一个数值，还附带经纬度、方向，你选什么类型？

考察点：数据结构组合能力。

  • ① 速度用独立的 String（TTL=30s，高频变更）。
  • ② 经纬度/基础信息用独立的 String 或 Hash（TTL=3600s，低频变更）。
  • ③ 这样设计能让高频的“速度”快速消亡，而不会因为速度过期把宝贵的车辆基础信息也连带删除。

🧠 P2 层级：过期时间与内存控制（考察细节经验） ​

Q4：如果所有车辆的过期时间都设置为 30 秒，会发生什么？

考察点：是否了解缓存雪崩与 Redis 过期策略。

  • 会导致大量 Key 在同一秒同时过期，瞬间拉高 Redis CPU（后台删除扫描），可能引发性能抖动。
  • 解决方案：给过期时间增加随机扰动（如 30 + random(0~5) 秒），将过期时间打散。

Q5：Redis 的过期 Key 是到了时间就立刻从内存删除吗？

考察点：是否了解 Redis 惰性删除 + 定期删除机制。

  • 不是。Redis 采用被动删除（读时检查）+ 后台定期抽样删除。如果 Key 过期了但没人读取，它可能依然躺在内存里。因此必须设置 maxmemory-policy（如 allkeys-lru）作为兜底，防止内存写满。

Q6：你提到了 maxmemory-policy，在 String + ZSET 混合存储的场景下，推荐配什么策略？

考察点：淘汰策略的选型能力。

  • 推荐配置 volatile-ttl（优先淘汰 TTL 最短的 Key）。因为我们给 String 设置了过期时间，且 String 是数据量最大的部分。这样内存紧张时，Redis 会优先剔除即将过期的速度数据，而 ZSET（排行榜数据）因为是永不过期的，不会轻易被误淘汰。

⚔️ P3 层级：排行榜排序与同步问题（考察实战攻坚） ​

Q7：为什么要用 ZSET 做排行榜？直接用 List 按速度排序不行吗？

考察点：数据结构时间复杂度认知。

  • List 只支持 LPUSH/RPUSH，无法按分数排序。如果每次全量排序，时间复杂度 O(NlogN)，千万级数据不可行。ZSET 底层是跳表（SkipList），ZADD 和 ZREVRANGE 都是 O(logN)，且支持按分数范围裁剪（ZREMRANGEBYRANK），天生适合排行榜。

Q8：ZSET 的 Member（车辆 ID）不支持过期时间，如果车辆离线了，怎么把它从 ZSET 里删掉？

考察点：是否理解 ZSET 的痛点。

  • 无法自动删除。采用 “读时修复（Lazy Deletion）” 策略：每次展示 Top100 时，用 Pipeline 批量 EXISTS 检查这 100 辆车的 String 是否存活，死掉的立即 ZREM 剔除，并递归补位。这样清理操作只发生在 TopN 范围内，复杂度极低。

Q9：如果 Top100 全是僵尸车（都过期了），你的“读时修复”会怎么处理？会不会无限循环或超时？

考察点：异常边界控制能力（区分普通人和高手的核心点）。

  • 必须设置 最大迭代次数（如 3 次） 和 最大扫描范围（如最多取 500 辆）。如果 3 次迭代后有效车仍不足 N 辆，直接返回当前有效数据，并触发业务告警，绝不无限扩大 fetchSize 去扫描跳表尾部，防止拖垮 Redis。

Q10：如果速度值相同（比如都是 0），ZREVRANGE 返回的顺序是固定的吗？

考察点：是否关注排序稳定性。

  • 不固定。分数相同时，Redis 按 Member 字符串的字典序（Lexicographical Order）排序，这会导致榜单抖动。
  • 解决方案：采用 复合分数，例如 Score = 速度 * 10^10 + (Long.MAX_VALUE - 当前秒级时间戳)。这样速度相同时，最新上报的车辆因为时间戳更大而排在前面，解决了平局问题（注意时间戳取秒级（10位），防止超过 2^53 的整数精度上限）。

🚀 P4 层级：高并发与分片策略（考察架构能力） ​

Q11：如果按车辆 ID 做哈希分片，把 ZSET 拆成 10 个，能解决性能问题吗？

考察点：是否理解分片对全局排序的破坏性（这是一个大坑，看你跳不跳）。

  • 不能。 哈希分片会破坏全局有序性。要拿全局 Top100，必须从 10 个分片各取前 100 名（共 1000 条），在应用层做归并排序。数据量上亿时，归并计算耗时巨大，无法满足 30s 延迟要求。因此，全国总榜不能做哈希分片。

Q12：既然不能哈希分片，那你的“按省份/城市分片”思路是出于什么考量？

考察点：业务降维思维。

  • 这是业务维度隔离，而不是技术哈希分片。用户通常只关心自己所在省份/城市的榜单，因此 Key 设计为 speed:ranking:province:{ID}。每个分片的数据量从千万级降到几十万级，且不需要跨分片归并，业务查询天然隔离，性能大幅提升。

Q13：如果业务方强制要求做“全国总榜”，且不分片，你的方案还成立吗？

考察点：技术取舍与兜底能力（必须给出确定答案）。

  • 完全成立。 我采用 写入时裁剪（ZREMRANGEBYRANK 保留 Top 10万），将 ZSET 物理大小永久锁死在 10万条（内存仅几 MB）。此时单机 ZSET 的 ZREVRANGE 操作是微秒级的，完全不需要分片。
  • 结论：全国总榜用单机 + 裁剪；地区分榜用业务分片，两者并不冲突。

Q14：你说“写入时裁剪保留 Top 10 万”，如果高并发下，线程 A 刚 ZADD 完新车，线程 B 的 ZREMRANGEBYRANK 会不会把新车误删？

考察点：原子性与并发安全（极其重要的细节）。

  • 会！这是经典的并发竞态条件。
  • 解决方案：使用 Lua 脚本，先执行 ZREMRANGEBYRANK（删低分），再执行 ZADD（加高分）。或者用 Redis 的 ZADD 选项 GT（仅当分数大于当前时才更新）配合判断。总之必须保证“删除低分”和“添加高分”的原子性，且顺序不能反。

🧩 P5 层级：极端异常与运维保底（考察全局视野） ​

Q15：如果瞬间涌入 1 亿辆车（流量突刺），你的写入裁剪还没来得及触发，Redis 内存爆了怎么办？

考察点：是否具备运维保底意识（最终防线）。

  • 配置 maxmemory-policy volatile-ttl 作为兜底策略。当内存超过上限时，Redis 会主动驱逐 TTL 最短的 Key（即将过期的速度数据），确保写入不会因 OOM 中断。同时，在应用层对写入流做本地聚合（1秒窗口去重），将写入 QPS 降低 90% 以上。

Q16：如果 Redis 主节点挂了，排行榜不可用，业务怎么降级？

考察点：高可用与降级方案。

  • ① 主从 + 哨兵 自动故障转移，这是基本盘。
  • ② 如果全挂，应用层 本地缓存（Caffeine） 会保留上一次拉取的 Top100 快照（TTL 30s），前端大屏依然能展示旧数据，只是不实时，但不至于白屏。
  • ③ 极端情况下，放弃 ZSET 排序，直接降级为从数据库（MySQL）按速度字段 ORDER BY 查 Top100（加索引，扛低并发兜底）。

Q17：你反复提到用 Pipeline 批量操作，但如果批量的 1000 辆车里，某一条指令失败了怎么办？需要全部回滚吗？

考察点：对 Redis 事务与 Pipeline 机制的深刻理解。

  • Pipeline 不是事务，不保证原子性，某条失败不影响其他指令执行，且不支持回滚。在我们的场景中（速度上报），允许部分失败（最终一致性），不需要回滚。如果必须保证绝对一致，需改用 Lua 脚本（Redis 单线程执行，天然原子）。但考虑到性能，99.9% 场景用 Pipeline 即可，失败的上报由三方接口重试补偿。

Q18：为什么你裁剪 ZSET 时保留的是 Top 10 万，而不是 Top 1000 或 Top 100 万？这个阈值怎么定的？

考察点：数据量级的工程直觉。、

  • ① Top 100：内存极小，但万一 Top100 全是僵尸车，读时修复递归次数会变多（需要往后扫描更多才能凑齐有效数据）。
  • ② Top 100 万：内存约 50~80 MB，虽然单机也能扛，但 ZREMRANGEBYRANK 遍历 100万 条的时间开销比 10万 条大几倍。
  • ③ Top 10 万（约 5~8 MB）：是性价比最佳平衡点，既保证了读时修复只需递归 1~2 次就能凑齐 Top100，又保证了 ZSET 操作极快。这个阈值可通过压测动态调整。

Q19：如果我将 ZSET 裁剪到 Top 10 万，第 100001 名的车辆突然加速到第一名，它进得了榜单吗？

考察点：对裁剪逻辑的理解（这是一个灵魂拷问）。

  • 进得了！ 因为每次写入都执行 ZADD + ZREMRANGEBYRANK。当这辆车加速上报时，ZADD 会将其分数更新为最高分，它立即进入 Top 10 万；紧接着执行裁剪，Redis 会删除当前排名第 100001 名的最低分车辆。所以新车永远能进来，裁剪删的是“当前分数最低的那辆车”，而不是“排名固定的车”。

Q20：最后一问，如果让你用一句话总结这个设计的核心思想，是什么？

考察点：技术抽象与总结能力（决定定级）。

  • “用 O(1) 的写入裁剪替代 O(N) 的全量遍历，将海量数据压力转化为可控的少量常驻内存，并结合业务视角（TopN 展示）做局部精准修复。”

📋 二、Redis 高并发抢红包系统 ​

🔰 P1 层级：数据结构选型与业务拆解（考察基本功） ​

Q1：为什么抢红包要用 Redis 的 List 结构？用 DECR 扣库存 + String 存金额不行吗？

考察点：是否理解 List 的“原子弹出”特性。

  • ① DECR 只能扣减库存数量（个数），无法绑定具体金额。如果只用 DECR，还需要额外查询金额，这破坏了原子性。
  • ② List 的 LPOP/RPOP 是原子的 O(1) 操作，它将“库存扣减”和“金额获取”合二为一。弹出即占有，不存在中间状态，天然杜绝超发。

Q2：发红包时，金额拆分具体怎么操作？为什么不在抢的时候实时计算？

考察点：算法理解与预计算思维。

  • ① 采用二倍均值法或线段切割法，在发红包时一次性将总金额拆分成 N 个随机小额（如单位换算为分，避免浮点数）。
  • ② 用 LPUSH 将拆分好的所有金额一次性写入 Redis List。
  • ③ 不在抢时实时计算的原因是：实时计算涉及随机数和浮点运算，会消耗 CPU，且高并发下难以保证金额总和等于总金额；预拆分则完全规避了这些风险，抢红包只是简单的弹栈操作。

Q3：存储金额时，用 String（字符）存还是用整数存？

考察点：内存优化意识。

  • 必须用**整数（分为单位）**存。例如 1.23 元存为 123。Redis 对整数有特殊编码优化（OBJ_ENCODING_INT），比存浮点数字符串节省 50% 以上的内存。一个 100 人红包，List 中存整数仅占用几百字节。

🧠 P2 层级：并发安全与防刷（考察细节经验） ​

Q4：LPOP 确实原子，但如果有 10 万并发，Redis 单线程扛得住吗？会不会出现“弹出为 nil”但实际还有钱的情况？

考察点：Redis 单线程性能认知。

  • ① Redis 单线程 QPS 可达 10万+，纯内存 LPOP 操作耗时极微（微秒级），完全扛得住。
  • ② 不会出现逻辑错误。Redis 是单线程串行处理命令，所有 LPOP 请求在服务端严格排队。如果 List 里只剩 1 个元素，只有一个请求能弹出该元素，其余请求返回 nil。不存在“看见有但弹出无”的并发幻读问题。

Q5（必问！灵魂拷问）：如果同一个用户疯狂点击“开红包”按钮 100 次，你的方案会让他抢到 100 个红包吗？你怎么防？

考察点：是否考虑幂等性与去重（这是区分新手和高手的核心分水岭）。

  • 会！ 如果不做拦截，用户连续 LPOP 100 次，就会弹走 100 个红包，这是严重的业务漏洞。
  • 解决方案（Lua 脚本原子拦截）：在抢红包的 Lua 脚本中，先执行 SISMEMBER envelope:{id}:users {userId} 检查该用户是否已领取过，若已存在直接返回“已抢过”；若不存在，再执行 LPOP 弹出一个金额，成功后执行 SADD 将用户 ID 加入集合。
  • 关键：SISMEMBER + LPOP + SADD 这三步必须用 Lua 脚本封装，保证原子性，防止“检查通过后还没来得及 SADD，被另一个线程穿插”的超抢情况。

Q6：如果一个红包有 1000 人份，List 弹出的金额怎么和用户绑定？异步记录明细时，万一明细表插入了但 List 已弹出，怎么保证最终一致性？

考察点：最终一致性落地方案。

  • ① 抢到后立即返回金额给用户，同时将 (红包ID, 用户ID, 金额) 封装成消息扔进 RocketMQ / RabbitMQ 或本地内存阻塞队列。
  • ② 消费者异步批量写入 MySQL。写入失败时，采用重试 + 死信队列机制。由于资金相关，必须保证最终落库，重试 3 次仍失败则记录日志并触发人工告警。
  • ③ 绝对不能在抢红包的同步链路中直接插入 MySQL，否则高并发下数据库会直接被打死。

⚔️ P3 层级：数据一致性与异常恢复（考察实战攻坚） ​

Q7：如果 Redis 突然宕机重启，List 里的红包数据还在吗？如果丢了，钱不就飞了？

考察点：是否关注 Redis 持久化与资金安全（极其敏感）。

  • ① 红包属于资金数据，不能只靠纯内存。必须开启 AOF（Append Only File），并配置 appendfsync everysec（每秒刷盘），最多丢失 1 秒的数据。
  • ② 发红包时，LPUSH 成功后，必须先写一条 MySQL 红包流水日志（状态为：待领取），再返回成功。如果 Redis 宕机丢失了 List 数据，可以通过后台任务扫描 MySQL 中“待领取”但 Redis 里无数据的红包，进行手动补发或退款。
  • ③ 每天凌晨运行对账脚本：对比 MySQL 已领取金额 + Redis List 剩余金额是否等于红包总金额，若有差值则触发报警。

Q8：抢红包接口的 LPOP 返回 nil（已抢完），但异步明细还没落库，前端显示“已抢完”，用户后来发现明细里没自己，怎么解释？

考察点：对异步延迟的容忍度设计。

  • ① 前端展示“手慢了，红包抢完了”是即时响应，基于 Redis 状态，无需等待 MySQL。
  • ② 明细异步落库存在秒级延迟。用户可以通过“钱包明细”页面查看，该页面查询 MySQL，最终数据一定一致。
  • ③ 如果用户刚抢完就查明细查不到，前端应设计为“处理中”或“稍后查看”的文案缓冲，避免用户困惑。

Q9：如果单个红包非常大（比如 1 万元拆成 10000 个 1 元），LPUSH 一个超长 List 会有什么问题？

考察点：大 Key（Big Key）治理意识。

  • ① 单个 List 过大（超过 1 万个元素）会导致 LPUSH 时网络传输耗时增加，且 LLEN 等操作变慢，甚至阻塞 Redis。
  • ② 解决方案（分段存储）：发红包时，将 10000 个金额拆分成多个子 List，如 red:batch:1、red:batch:2 各存 2000 个。应用层维护一个游标，当当前批次 LLEN 为 0 时，自动切换到下一批次。
  • ③ 或者在业务上限制单个红包最大拆分份数（如 2000 份），大额红包引导用户分多次发放。

🚀 P4 层级：高可用与分片拓展（考察架构能力） ​

Q10：你的红包 Key 是 envelope:{id}，如果使用 Redis Cluster，这个 Key 会落在哪个节点？如果抢同一个红包的 QPS 超过 10万，单节点扛不住怎么扩容？

考察点：集群环境下热点 Key 的处理能力。

  • ① Redis Cluster 根据 Key 的 Hash 槽（CRC16）分配节点。同一个红包 ID 只能落在一个节点上，无法通过增加节点来分摊单个红包的写压力。
  • ② 解决思路（本地聚合）：在抢红包的网关层或业务层，引入 Lua + 令牌桶 或 本地内存限流，针对同一红包 ID 在应用层做请求合并。例如，1000 个请求打到网关时，网关只透传 1 个请求到 Redis，其余 999 个在网关层直接返回“已抢完”或等待重试。
  • ③ 此外，单个 LPOP 微秒级响应，其实 10万 QPS 单节点 Redis 完全能扛住（官方基准 10万+），通常不会成为瓶颈，瓶颈反而在应用服务器和数据库。

Q11：如果我要分库分表（按红包 ID 做分片），Redis Key 怎么设计才能配合 MySQL 分片，避免跨库查询？

考察点：存储与缓存的联动设计。

  • Redis Key 设计为 red:envelope:{shardKey}，其中 shardKey 与 MySQL 分库分表键保持一致（如红包创建者 ID 或红包 ID 取模）。
  • 查询明细时，前端带上红包 ID，网关通过 ID 取模直接路由到对应的 MySQL 库，而 Redis 作为该库上的一级缓存，完美配合，避免了跨库 JOIN。

🧩 P5 层级：极端异常与终极保底（考察全局视野） ​

Q12：如果 LPOP 弹出金额后，应用服务器在写入 MQ 之前突然宕机（进程被杀），导致这个金额“弹出即丢失”，既没有发出去也没有记录，这笔钱怎么追回？

考察点：WAL（预写日志）思想（P5 级高难度问题）。

  • 这属于发奖中断的极端灾难。解决方案是采用 “先记日志，再弹红包” 的反向操作（或使用 Redis 的 RPOPLPUSH 原子转移）：
  • ① 抢红包时，执行 RPOPLPUSH source destination，将弹出的金额原子性地从 envelope:{id} 转移到 envelope:{id}:processing（处理中的临时 List）。
  • ② 业务成功写入 MQ/DB 后，再从 processing 中 LREM 删除该元素。
  • ③ 如果应用宕机，重启时扫描 processing 临时队列，发现里面有残留数据，说明上次处理未完成，可以重新发起异步落库流程（或退款重试）。
  • 这样即使服务器宕机，资金也绝对不丢失，因为金额只是转移了位置，没有被丢弃。

Q13：如果大量恶意用户使用脚本狂刷抢红包接口，导致 Redis CPU 飙高，你如何做熔断和降级？

考察点：安全防护与系统韧性。

  • ① 限流：对单个用户 ID 抢红包接口做令牌桶限流（如 1 秒最多请求 5 次），超过直接返回“请求频繁”。
  • ② 验证码兜底：当某个红包 ID 的 QPS 瞬间飙升 10 倍时，触发风控规则，强制要求后续请求输入验证码，拦截机器流量。
  • ③ Redis 熔断：监控 Redis 错误率或响应延迟，当延迟超过阈值（如 100ms）时，开启 Hystrix 熔断，直接返回“系统繁忙，请稍后再试”，保护 Redis 不被拖垮。

Q14：灵魂总结题——如果让你用一句话概括这个红包系统的核心设计思想，是什么？

考察点：技术抽象能力。

  • “利用 Redis List 的原子弹出特性（LPOP）将‘库存扣减’与‘金额获取’合并为一次内存操作，实现近乎无锁的超高并发；同时剥离耗时的数据库写入为异步任务，并配合 WAL（预写转移）和 Lua 去重脚本，在极端宕机场景下保证资金安全和数据最终一致性。”

📋 三、Redis 可靠延迟队列（ZSET vs Streams） ​

🔰 P1 层级：数据结构选型与基本原理（考察基本功） ​

Q1：为什么延迟队列要用 ZSET？用 List 加定时任务轮询不行吗？

考察点：数据结构特性认知。

  • ① List 是先进先出（FIFO），无法按时间优先级弹出。如果要实现延迟，必须全量遍历 List 并判断时间戳，时间复杂度 O(N)，数据量一大就不可行。
  • ② ZSET 的 Score 天然适合存时间戳，ZRANGEBYSCORE 可以 O(logN) 地按时间范围快速捞取到期任务，效率极高。

Q2：Stream 方案比 ZSET 方案先进在哪里？为什么说它“可靠性更高”？

考察点：是否理解 Redis Streams 的设计哲学（这是 5.0+ 的新特性）。

  • ① 消费确认机制（ACK）：ZSET 方案中，任务弹出后若消费者宕机，任务就丢失了；而 Streams 的消费者组（Consumer Group）要求消费者显式发送 XACK，未 ACK 的消息会一直留在 PEL（Pending Entries List）中，不会丢失。
  • ② 消息持久化：Stream 是追加日志（Append-Only Log） 结构，消息持久化在内存中，支持回溯。
  • ③ 故障转移：消费者宕机后，其他消费者可通过 XPENDING 和 XCLAIM 认领未处理的消息，实现高可用。
  • ④ 一句话总结：ZSET 是实现延迟队列的 “轮询+删除” 模式；Streams 是实现消息队列的 “发布-订阅+确认” 模式，后者是原生 MQ 的设计范式。

Q3：ZSET 方案中，Score 存什么？为什么要用时间戳而不是延迟秒数？

考察点：对有序集合排序逻辑的理解。

  • Score 存储 “任务应执行的绝对时间戳（毫秒级）”，即 System.currentTimeMillis() + delayMillis。定时任务每次执行时，取 ZRANGEBYSCORE key 0 当前时间戳，捞出的就是所有已到期的任务。如果存延迟秒数（如 30s），系统重启后基准时间丢失，无法准确计算剩余延迟。

🧠 P2 层级：并发安全与原子性（考察细节经验） ​

Q4（必问！灵魂拷问）：ZSET 方案中，如果多个消费者实例同时轮询，同一个到期任务会不会被多个实例取走，导致重复执行？

考察点：并发竞态条件处理（Redis 分布式锁 vs Lua 脚本）。

  • 会！ 如果先 ZRANGEBYSCORE 再 ZREM，中间存在时间窗口，多个消费者会读到同一条数据。
  • 正确解法（Lua 脚本原子操作）：使用 ZPOPMIN（Redis 5.0+）或 Lua 脚本原子性地弹出一个到期任务，并直接将其移入“处理中”队列。代码如下：
lua
-- 原子弹出到期任务
local task = redis.call('ZPOPMIN', 'delay:queue', 1)
if task and task[1] then
    redis.call('ZADD', 'delay:processing', task[1], task[2])
    return task
end
return nil

这样，“取出”和“删除/转移”在一个原子操作中完成，彻底杜绝重复消费。

Q5：如果不用 ZPOPMIN，用 ZRANGEBYSCORE ... LIMIT 0 1 配合 ZREM，有什么风险？

考察点：对 Redis 命令特性的深入理解。

  • 存在ABA 问题的可能。虽然单条命令是原子的，但两步之间如果有其他线程插入了同 Score 的任务，ZREM 可能删错对象。
  • 强烈推荐使用 Redis 5.0 提供的原生 ZPOPMIN 或 BZPOPMIN（阻塞弹出），它们是官方保证的原子组合命令，无需自己写 Lua。

Q6：Streams 的消费者组是如何保证同一消息不被多个消费者重复消费的？

考察点：Streams 消费者组机制。

  • ① Streams 消费者组维护一个 Last Delivered ID（最后投递 ID），组内的每个消费者拿到的是不同的消息（轮询分配或按 Key Hash 分配）。
  • ② 消费者调用 XREADGROUP 读取消息后，Redis 会将消息 ID 放入该消费者的 PEL（Pending Entries List，待处理列表），并标记为“未确认”。
  • ③ 只有消费者显式发送 XACK 后，该消息才会从 PEL 中移除。在 XACK 之前，同组的其他消费者绝不会再拿到这条消息，天然杜绝重复投递。

⚔️ P3 层级：数据一致性与异常恢复（考察实战攻坚） ​

Q7（ZSET 方案深水区）：消费者从 ZSET 弹出任务后，处理过程中服务器宕机了，这条任务既没确认成功也没回到队列，怎么恢复？

考察点：WAL（预写日志）与超时重入机制。

  • 这正是 ZSET 方案的最大软肋。解决方案是引入 “超时兜底扫描 + 处理中队列（Processing Set）”：
  • ① 弹出任务时，原子地将任务转移至 delay:processing（ZSET），Score 存 “处理开始时间戳”。
  • ② 同时将任务体存入 delay:data:{taskId}（String，带 TTL）。
  • ③ 启动一个独立的监控守护线程，每隔 5秒 扫描 delay:processing，检查 Score（开始时间）是否超过设定的最大处理时长（如 60秒）。若超时，说明消费者宕机或处理超时，将其从 delay:processing 移除，重新放回 delay:queue，并将重试计数 +1。
  • ④ 重试次数 > 3 时，移入 死信队列（Dead Letter Queue），触发人工告警。

Q8（Streams 方案深水区）：Streams 方案中，消费者不发送 XACK，消息会一直留在 PEL，会不会导致内存爆炸？

考察点：Streams 内存水位控制。

  • 会。解决方案是多层次的：
  • ① 业务兜底：设置 maxlen 参数（如 XADD ... MAXLEN ~ 100000）截断 Stream 长度，但要注意 MAXLEN 会删除 PEL 中的消息，需谨慎使用。
  • ② 应用层强制 ACK：消息处理逻辑必须放在 try-finally 块中，确保无论成功还是失败（业务异常），最终都调用 XACK，避免消息堆积在 PEL。
  • ③ 失败分流（非 ACK 方式）：如果业务处理失败需要重试，不要不 ACK，而是先 ACK，再将消息体重新发送到 Stream 末尾，并附带 retryCount+1 和 nextDelay，这样 PEL 始终干净，重试逻辑由业务显式控制。

Q9：为什么 Streams 方案中，失败后建议“先 ACK 再重发”，而不是“留着不 ACK 等超时认领”？

考察点：对两种重试模式的优劣判断（面试高分点）。

  • ① 不 ACK（利用 PEL 挂起）：看起来省事，但如果有大量消息处理慢，PEL 会无限膨胀，XPENDING 查询变慢，且 XCLAIM（认领）涉及网络 IO 和判断逻辑，重试延迟较高。
  • ② 先 ACK 再重发（显式重试）：PEL 始终保持短小精悍，内存稳定；同时重试延迟精准可控（写入时直接指定新的延迟时间戳，配合延迟队列的 Score 精确到毫秒），且重试次数字段自带在消息体里，便于监控。
  • 结论：在重试场景下，“ACK + 重发” 是 Streams 更优雅、更可控的实践，而非依赖 PEL 超时。

🚀 P4 层级：高可用与性能优化（考察架构能力） ​

Q10：ZSET 方案中，如果延迟队列里积压了 1000 万条任务（如双十一预售），ZRANGEBYSCORE 每次取 100 条，会不会导致 Redis 阻塞？

考察点：Big Key 治理与分页查询优化。

  • 不会阻塞，ZRANGEBYSCORE 按 Score 范围遍历跳表，取前 100 条的时间复杂度是 O(logN + 100)，微秒级完成。但注意 ZREMRANGEBYSCORE 批量删除大量消息时会阻塞，因此消费时建议用 ZPOPMIN 每次弹出一条或少量（如 10条）。
  • 优化策略：业务可接受的前提下，使用 BZPOPMIN 阻塞弹出，让 Redis 服务端主动推送，替代客户端空轮询，减少网络 IO。

Q11：既然 Streams 这么好，是不是可以直接取代 ZSET 做所有延迟队列？什么场景下 ZSET 反而更合适？

考察点：技术选型的权衡能力（必须给出明确标准）。

  • ① 选择 ZSET：适合轻量级、低频、简单延迟场景（如 30分钟 订单超时取消，日请求量 < 10万）。ZSET 部署简单，依赖 Redis 现有组件，无需学习 Streams 消费者组复杂概念。
  • ② 选择 Streams：适合高可靠、高吞吐、多消费者的“任务调度”场景（如 消息推送、账单日切、分布式定时 Job）。Streams 原生支持多消费者负载均衡、故障转移（XCLAIM）、消息回溯，是 Redis 官方的 MQ 解决方案。
  • ③ 一句话决策：需要 ACK 确认 和 消费者组容灾 就必须选 Streams；只想快速实现一个“定时触发”功能，ZSET 足以。

Q12：ZSET 方案如何做到“延时消息”和“即时消息”的优先级混合处理？

考察点：复合 Score 设计。

  • 将 Score 设计为 (优先级 * 10^13 + 时间戳)。例如优先级分为 0（高）、1（中）、2（低）。ZRANGEBYSCORE 默认按 Score 从小到大取，高优先级的 Score 更小，会被优先弹出。这样实现了“高优先级的延迟任务插队执行”。

🧩 P5 层级：极端异常与终极保底（考察全局视野） ​

Q13：Redis Stream 的 XACK 如果因为网络原因发送失败，消费者以为自己 ACK 了，但 Redis 没收到，消息会重复消费吗？怎么处理？

考察点：分布式系统中的幂等性设计（面试官最后的杀手锏）。

  • 会！ 网络抖动可能导致 ACK 丢失，Redis 认为消息还在 PEL 中，超时后会被 XCLAIM 再次投递给其他消费者，导致消息重复消费。
  • 解决方案（生产级必做）：
  • ① 业务幂等性兜底：消费端必须实现幂等接口，以 (订单号/任务唯一ID) 为唯一键（Unique Key）去重。处理前先检查 Redis 或 DB 中是否已处理过该 taskId，已处理则直接返回成功（并主动补发 XACK 避免阻塞）。
  • ② 消费者侧去重：在消费者本地维护一个小容量 LRU 缓存（如 Caffeine），记录最近 5分钟 内处理过的 taskId，快速过滤重复投递。
  • ③ 结论：MQ 领域只能保证“至少消费一次（At-least-once）”，无法保证“恰好一次（Exactly-once）”，幂等性是业务系统最后的防线。

Q14：如果 Redis 内存满了，ZSET 或 Streams 里的延迟任务被淘汰策略（allkeys-lru）误删了，业务数据丢了怎么办？

考察点：Redis 定位认知与兜底配置。

  • ① 延迟任务属于业务关键数据，绝不能依赖 Redis 的 LRU 淘汰。必须配置 maxmemory-policy noeviction（不淘汰），确保 Redis 内存满时拒绝写入（报错），而不是静默丢失数据。
  • ② 同时，发消息前必须同步写 DB（任务日志表），状态为 待执行。Redis 作为热数据索引。如果 Redis 数据丢失，后台补偿任务会扫描 DB 中“待执行且执行时间 < 当前时间”的任务，重新灌入 Redis。
  • ③ 对流量的敬畏：提前预估积压量，为 Redis 分配足够内存（如 16GB 可存数亿条轻量任务 ID），并配置内存告警。

Q15：灵魂总结题——如果让你用一句话分别总结 ZSET 方案和 Streams 方案，你会怎么说？

考察点：技术抽象与定位能力。

  • ① ZSET 方案：“利用 Score 作为时间索引的轻量级调度器，通过原子弹出和超时扫描实现准可靠的任务分发，适合简单场景。”
  • ② Streams 方案：“Redis 原生实现的持久化消息队列，通过消费者组、ACK 确认和 PEL 待处理列表，在内存级提供了媲美专业 MQ 的可靠性保障，是分布式任务调度的首选基础组件。”

📋 四、Redis 附近的人（LBS）地理位置服务 ​

🔰 P1 层级：数据结构选型与基本原理（考察基本功） ​

Q1：Redis 的 GEO 底层是什么数据结构？为什么它能高效地做“附近的人”查询？

考察点：是否了解 GeoHash 算法与 ZSET 底层。

  • ① Redis GEO 底层就是 ZSET（有序集合）。它利用 GeoHash 算法 将二维经纬度编码为一维的 52 位整数值，作为 ZSET 的 Score。
  • ② GeoHash 编码的特点是：坐标越近，编码值的前缀越接近。因此 GEORADIUS / GEOSEARCH 会先通过 Score 范围快速定位附近区域，再对候选集进行球面距离计算（Haversine 公式），时间复杂度近似 O(logN + M)，M 为返回数量，效率极高。

Q2：GEOADD 添加经纬度时，如果同一个用户（Member）多次添加，Redis 会怎么处理？

考察点：对 ZADD 行为的理解迁移。

  • GEOADD 底层调用 ZADD。同 Member 再次执行 GEOADD 时会覆盖更新其经纬度（Score 更新）。这正符合“实时位置更新”的业务需求，无需先删除再插入。

Q3：GEOSEARCH 和 GEORADIUS 有什么区别？现在推荐用哪个？

考察点：对 Redis 版本演进的关注度。

  • ① GEORADIUS 是 Redis 3.2+ 引入的旧命令，功能相对单一，且默认返回未排序的结果。
  • ② GEOSEARCH 是 Redis 6.2+ 引入的新命令，更加灵活：支持 FROMLONLAT（从点搜索） 和 FROMMEMBER（从成员搜索），支持 BYRADIUS（圆形） 和 BYBOX（矩形） 两种搜索方式，且默认按距离排序。
  • ③ 生产环境优先使用 GEOSEARCH，它替代了 GEORADIUS 和 GEORADIUSBYMEMBER，设计更规范。

🧠 P2 层级：在线状态与过期清理（考察细节经验） ​

Q4（必问！灵魂拷问）：你的 GEO 里存了 1000 万用户，但其中 800 万已经卸载 App 或离线了，搜“附近的人”搜出一堆僵尸用户，怎么办？

考察点：在线状态与位置存储的解耦能力（直击痛点）。

  • 绝对不能只靠 GEO 存位置。必须将“位置”和“在线/活跃状态”解耦：
  • ① GEO 只存“位置坐标”：所有用户（包括离线）可能都存，但这不是直接展示的最终数据。
  • ② 另设一个 ZSET（online:users）或 String（带 TTL）：每次用户心跳（如每 5秒 上报位置）时，除了 GEOADD，还执行 SETEX user:online:{uid} 15 1（15秒过期）。
  • ③ 搜索时进行二次过滤：GEOSEARCH 拿到附近的 200 个 Member 后，用 Pipeline 批量 EXISTS 检查这些用户的 String 在线 Key 是否存活。只返回在线用户，离线的直接丢弃，并可选异步 ZREM 清理 GEO（或依赖惰性删除）。
  • ④ 极端优化：如果在线率极低（如 < 5%），可改为维护一个 “在线用户专用 GEO”：用户上线时 GEOADD 加入，心跳更新位置，用户主动下线或心跳超时时 ZREM 移出。这样 GEO 里全是活人，搜索无需过滤。

Q5：如果用户频繁移动（如网约车司机），每秒上报一次位置，频繁 GEOADD 会有什么性能问题？

考察点：写入放大（Write Amplification）优化意识。

  • ① GEOADD 本质是 ZADD，O(logN) 的写入性能极佳（微秒级），单节点 Redis 每秒可承受 10万+ 次写入，单纯看写入压力不大。
  • ② 真正的风险是网络 IO 和应用层压力。如果每辆车每秒都上报，网关和 Redis 的带宽/连接数会吃紧。
  • ③ 优化方案（本地聚合）：在应用服务端引入本地缓存（如 Caffeine），将 1秒 内同一用户的多次位置更新聚合成最后一次，再通过 Pipeline 批量 GEOADD，可将写入 QPS 降低 90% 以上。

⚔️ P3 层级：数据一致性与业务过滤（考察实战攻坚） ​

Q6（高阶过滤场景）：搜“附近的人”时，需要屏蔽黑名单用户、拉黑列表、或者只搜“异性”，你的 GEOSEARCH 怎么处理这些过滤条件？

考察点：纯内存数据结构的局限性认知（面试官挖坑点）。

  • GEOSEARCH 不支持在搜索条件中带属性过滤（如性别、年龄、黑名单）。解决方案是 “查询后过滤（Post-Filtering）”：
  • ① 多取数据：GEOSEARCH 不要只取 N 条，而是取 N * 3 或 N * 5 条候选数据（如业务要 20 人，实际查 100 人）。
  • ② 应用层过滤：在应用内存中，根据用户属性的本地缓存（或批量查 Redis Hash/MySQL）剔除黑名单、匹配性别/年龄。
  • ③ 递归补位：如果过滤后不足 N 人，携带排除列表，扩大搜索半径再次递归查询（最多递归 2~3 次），直到凑齐 N 人或达到最大半径。绝对不能一次性把半径拉到 10km 去查询，那会导致候选集过大，拖垮 Redis。
  • ④ 终极兜底：如果实在凑不齐，直接返回当前过滤后的所有结果。

Q7：如果 GEO 的 Key 设计为 geo:city:{cityId}（按城市分片），用户在两个城市交界处（如北京和河北边界）搜索，会搜不到另一边的用户吗？

考察点：分片边界的业务感知能力。

  • 会！ 这是“按城市分片”的经典边界漏网问题。解决方案：搜索时同时查询周边相邻城市的分片：
  • ① 根据用户的经纬度，调用地图 API（如高德/谷歌）获取其所在的行政区域编码（Adcode）。
  • ② 计算周边 8 个相邻城市（或行政区）的 Adcode 列表。
  • ③ 应用层并行（异步） 向这 9 个 Geo 分片发起 GEOSEARCH，然后将 9 个结果集在内存中按距离归并排序，取 Top N。
  • ④ 或者更简单的业务降级：如果用户严格按城市列表选择城市（如北京），就只搜本市，把“跨省漏网”视为可接受的业务边界（用户感知不到）。

🚀 P4 层级：高可用与分片策略（考察架构能力） ​

Q8：如果北京城区的 GEO Key（geo:beijing）里存了 500 万用户，单 Key 过大，GEOSEARCH 查询速度会变慢吗？怎么解决？

考察点：Big Key 治理与网格化分片。

  • ① 500 万用户的 ZSET 跳表高度约为 20~30 层，GEOSEARCH 的 O(logN) 查询依然在 1~2 毫秒 内，通常不会变慢。
  • ② 真正的瓶颈在于返回的候选集（M）非常大。如果半径 1km 内有 10 万人，返回 10 万条数据做距离计算和网络传输，会严重拖垮性能。
  • ③ 终极解法（网格化分片 - Geohash 前缀）：
    • 将地图按 Geohash 精度划分为 Level 6（约 1.2km x 0.6km） 或 Level 7（约 152m x 152m） 的网格。
    • Key 设计为 geo:grid:{geohash_prefix}，例如 geo:grid:wx4g0。
    • 写入时，根据用户经纬度计算出所在网格前缀，写入对应的 Key。
    • 搜索时，计算目标点所在的网格，并同时查询周围 8 个相邻网格的分片，并行归并。
    • 效果：每个网格内用户数骤降到几千人，GEOSEARCH 极快，且天然支撑水平扩展。

Q9：如果使用 Redis Cluster，GEOSEARCH 涉及到跨多个网格分片（Key）查询，怎么做到高性能？

考察点：集群模式下的并行查询能力。

  • ① 由于网格分片 Key 不同，Hash 槽位不同，无法使用单条命令跨 Key 查询。
  • ② 在应用层使用 异步并发框架（如 CompletableFuture），同时向 9 个网格 Key 发起异步 GEOSEARCH 请求，然后等待所有结果返回，在内存中做归并排序。
  • ③ 设置超时熔断：如果某个分片 50ms 未返回，直接降级忽略该分片，避免整体响应超时。

🧩 P5 层级：极端异常与终极保底（考察全局视野） ​

Q10：GEOSEARCH 默认按距离排序返回，但 Redis 计算球面距离（Haversine）是浮点运算，比较消耗 CPU。如果 QPS 高达 10万，Redis CPU 飙到 100% 怎么办？

考察点：计算密集型操作的降级与缓存。

  • ① 本地缓存热门坐标：如果用户在同一个地方（如公司、商场）反复搜索，服务端可以缓存该坐标点的搜索结果（如 Caffeine，TTL=30秒），直接返回，完全不经过 Redis。
  • ② 降低精度：业务上如果允许，可将距离排序精度从米级降为百米的粗略排序，或者提前将经纬度四舍五入到小数点后 3 位（约 100米 精度），减少 GeoHash 计算量。
  • ③ 读写分离：将 GEOSEARCH（读操作）指向 Redis 从节点（Replica），主节点只负责 GEOADD（写操作），分散 CPU 压力。

Q11：如果一个恶意用户在高并发下用脚本反复查询“附近的人”，导致你的 GEO 热点分片（如北京核心区）被打爆，你怎么防御？

考察点：安全防护与热点治理。

  • ① 用户级别限流：对单用户 ID 或 IP 的 GEOSEARCH 接口做令牌桶限流（如 1秒 最多 2 次），超过直接返回 429。
  • ② 结果缓存：对相同坐标点（经纬度四舍五入到一定精度）的查询结果，设置短期缓存（如 5秒），同一网格内的所有用户共享该缓存，有效降低 95% 的透传请求。
  • ③ 熔断降级：监控 Redis 的 latency，如果 GEOSEARCH 延迟超过 100ms，自动熔断，返回空列表或“当前区域繁忙，请稍后重试”的文案。
  • ④ 随机偏移（隐私处理）：给返回的附近用户经纬度增加微小随机偏移（如 10~50米），既能防止恶意定位，又能强制缓存失效分散，避免集中过期。

Q12：灵魂总结题——如果让你用一句话概括“附近的人”这个场景的核心设计哲学，是什么？

考察点：技术抽象与业务权衡能力。

  • “利用 GeoHash 的空间填充曲线将二维降维为一维索引，实现高效的距离检索；同时通过‘在线状态解耦’、‘网格化分片’和‘查询后业务过滤’三层架构，将海量地理数据和复杂的人肉过滤压力转化为可控的局部计算与缓存策略。”

“用户开启虚拟定位，位置飘到别处怎么防？”考察风控常识（非 Redis 问题）前置反作弊风控，通过 GPS 与 IP 归属地比对、WiFi 指纹辅助校验，Redis 只管存储和查询
“如果我要存用户的经纬度历史轨迹，GEO 行吗？”考察数据结构边界不行。GEO 只存最新位置。轨迹需用 Redis Streams + 时间窗口 或转存 时序数据库（InfluxDB/TDengine）
“网格化分片后，网格边界上的用户搜索，会不会漏掉正隔壁网格的人？”考察 Geohash 边界感知必须同时查询目标网格 + 周围 8 个相邻网格（共 9 个分片），应用层归并排序，弥补 Geohash 边界不连续性

📋 五、Redis 实时排行榜（积分榜/多维度榜单） ​

🔰 P1 层级：数据结构选型与基本原理（考察基本功） ​

Q1：为什么排行榜要用 ZSET？用 MySQL 的 ORDER BY score DESC LIMIT 10 不行吗？

考察点：数据库与缓存的性能差异认知。

  • ① MySQL 的 ORDER BY 需要全表扫描或走索引扫描，数据量达到千万级时，即使有 (score) 索引，查询 Top 100 也需要扫描大量索引页，耗时通常在 几十毫秒到几百毫秒，且随着并发升高，磁盘 IO 和 CPU 飙升，数据库会被打垮。
  • ② Redis ZSET 是纯内存结构，底层是跳表（SkipList），ZREVRANGE 取 Top N 的时间复杂度为 O(logN + M)（M 为返回条数），微秒级返回，且单节点可抗 10万+ QPS。结论：MySQL 做持久化存储和复杂分析，Redis 做实时热榜。

Q2：ZADD 更新积分时，如果 Member 已存在，Redis 是覆盖还是追加？

考察点：对 ZADD 语义的理解。

  • 覆盖更新。ZSET 按 Member 唯一标识，相同的 Member 再次 ZADD 会直接更新其 Score。这正是实时排行榜所需的“积分变更即更新”行为，无需先删除再插入。

Q3：ZREVRANK 和 ZRANK 有什么区别？查“我的排名”用哪个？

考察点：命令语义清晰度。

  • ① ZRANK key member 返回按 Score 从小到大（升序） 的排名（第 1 名索引为 0）。
  • ② ZREVRANK key member 返回按 Score 从大到小（降序） 的排名，即积分最高者排名最靠前。
  • ③ 业务上排行榜通常是积分高者排前面，因此查询“我的排名”用 ZREVRANK，返回 0 表示第 1 名。

🧠 P2 层级：平局处理与榜单设计（考察细节经验） ​

Q4（必问！灵魂拷问）：如果成千上万用户积分相同（比如都是 100 分），ZREVRANGE 取 Top 10 时，谁能排前面？会不会每次刷新顺序都不一样？

考察点：Score 平局（Tie-breaking）的处理能力（区分普通与优秀的核心分水岭）。

  • ① 默认情况下，Score 相同时，Redis 按 Member 字符串的字典序（Lexicographical Order） 排序。这会导致：① 排名顺序随机且不可控；② 如果 Member 是纯数字字符串（如 "10001"），其字典序可能不符合预期。
  • ② 生产级解决方案（复合分数设计）：将 Score 设计为 积分 * 10^13 + (Long.MAX_VALUE - 当前秒级时间戳)。
    • 积分权重最高，决定主排序。
    • 尾数部分用“最大时间戳 - 当前时间戳”，使得积分相同时，越早达到该积分的用户排名越靠前（先到先得），完全符合竞赛公平性。
    • 注意：必须用秒级时间戳（10位） 或 13位取低10位，防止整数溢出 2^53 的精度上限。

Q5：如果业务需要同时支持“小时榜”、“日榜”、“周榜”，你怎么设计 Key 和存储策略？

考察点：多维度榜单的架构设计（考察分层存储思维）。

  • 方案一（多 Key 独立写入，推荐）：Key 设计为 rank:hour:{yyyyMMddHH}、rank:day:{yyyyMMdd}、rank:week:{yyyyWeek}。每当用户产生积分变动时，同时 ZADD 写入这三个 Key。这样每个榜单独立、查询最快，且读取时互不影响。代价是写入量放大 3 倍，但 ZADD 是微秒级，完全可接受。
  • 方案二（ZUNIONSTORE 合并，谨慎使用）：只维护“小时榜”，日榜/周榜通过 ZUNIONSTORE 合并最近 24 小时/7 天的所有小时榜 Key 生成。但要注意：ZUNIONSTORE 在千万级数据下会阻塞 Redis 主线程数秒甚至数十秒，只能在凌晨低峰期执行，且必须设置 maxmemory 和超时熔断。

Q6：你说用多个 Key 独立写入，那“小时榜”到期后旧 Key 怎么清理？会不会内存爆炸？

考察点：数据生命周期管理（TTL 意识）。

  • ① 创建 Key 时立即设置过期时间：EXPIRE rank:hour:{时间} 7200（保留 2小时，给容错留余量）；EXPIRE rank:day:{日期} 2592000（保留 30天）。
  • ② 对周榜，建议将数据转存到 离线数仓（Hive/ClickHouse） 或 MySQL 归档表后，立即 DEL 释放 Redis 内存。
  • ③ 绝对禁止“全量保留历史 Key”的行为，Redis 是内存数据库，不是廉价存储。

⚔️ P3 层级：多榜合并与原子性（考察实战攻坚） ​

Q7：如果使用 ZUNIONSTORE 合并 7 天的小时榜生成周榜，但执行过程中 Redis 发生故障中断了，脏数据怎么处理？

考察点：对耗时长命令的异常处理意识。

  • ZUNIONSTORE 不是原子性的“事务”概念，它是同步阻塞命令。如果执行中断，不会产生脏数据，因为目标 Key 要么还没创建，要么创建了一部分（Redis 单线程不会被中断，只有宕机才会）。解决方案：
  • ① 执行前用 RENAME 将旧的周榜 Key 备份（如 rank:week:old），再执行 ZUNIONSTORE 生成新 Key。
  • ② 生成成功后 DEL rank:week:old；如果失败，直接 RENAME 回滚恢复旧榜，业务完全无感知。
  • ③ 核心建议：如果数据量极大（单 Key 超 1000 万），放弃 ZUNIONSTORE，改用在应用层通过离线 MapReduce/Spark 计算好周榜积分，再批量 ZADD 灌入 Redis。

Q8：如果“小时榜”在整点切换时（如 12:00:00），旧的排行榜 Key 刚过期被删除，新的 Key 还没来得及写入足够数据，榜单为空或数据不全，怎么处理？

考察点：榜单切换的空窗期防御（经典痛点）。

  • 采用 “双 Key 预创建 + 惰性切换” 策略：
  • ① 预创建：在 11:59:50 时，后台提前创建好 12:00 的新 Key（rank:hour:2026011412），此时它还是空的，无妨。
  • ② 写入双写：11:59:50 到 12:00:10 这 20秒 内，应用层同时写入旧 Key 和新 Key（双写）。
  • ③ 读隔离：前端查询时，根据当前时间动态计算 Key 名称，12:00:00 准时切换到新 Key。由于新 Key 已经提前接收了 10秒 的写入数据，榜单不会为空。
  • ④ 兜底：如果新 Key 数据确实极少，前端可显示“榜单更新中”的文案，或在切换初期短暂降级，让用户继续查看旧榜数据（旧榜额外保留 5分钟）。

🚀 P4 层级：高并发写入与热点治理（考察架构能力） ​

Q9：如果某个大V（明星）突然涨粉百万，积分频繁变动，导致 ZSET 中该 Member 的 Score 更新极其频繁，会造成 ZSET 的跳表频繁重建吗？有什么影响？

考察点：ZSET 跳表更新机制与热点写入影响。

  • ① ZSET 底层是跳表（SkipList）+ 哈希表（Dict）。更新一个 Member 的 Score，Redis 会先删除旧节点，再插入新节点，对应跳表的 O(logN) 删除 + O(logN) 插入，不会因为单节点频繁更新而触发“全量重建”。
  • ② 真正的风险是网络带宽和 CPU：如果该大V的每秒积分变动上千次（如直播打赏滚动），每次变动都执行 ZADD，Redis 的 CPU 和时间片会被高频小请求占满。
  • ③ 优化方案（本地聚合）：在应用层对大V用户的积分变更做本地聚合缓冲（如 1秒 窗口内累计变更量，只取最终结果），1秒 只 ZADD 一次到 Redis，可降低 90% 以上的写入压力。

Q10：如果同时有几十万用户请求“查我的排名”（ZREVRANK），这几十万请求都打向同一个 ZSET，Redis 单线程会扛不住吗？

考察点：纯读场景的高并发优化。

  • ① ZREVRANK 是 O(logN) 的纯内存操作，单节点 Redis 可轻松支撑 10万+ QPS，通常不会成为瓶颈。
  • ② 如果业务量级极大（如 百万QPS），引入 Redis 从节点（Replica） 做读写分离，ZREVRANK 和 ZREVRANGE 全部走从节点，主节点只负责 ZADD 写入。
  • ③ 如果对排名的实时性要求不是秒级（可容忍 2~3秒 延迟），应用层可直接每 2秒 定时拉取 Top 100 + 当前用户排名，缓存在本地内存（Caffeine），前端请求直接读本地内存，彻底释放 Redis 的读压力。

Q11：ZREVRANGE key 0 -1 取全量榜单有什么风险？

考察点：大 Key 访问禁区意识。

  • 极其危险！ 0 -1 会返回 ZSET 中所有 Member，如果 ZSET 有 1000 万用户，这条命令会将几十 MB 甚至几百 MB 的数据一次性通过网络传输到应用层，严重阻塞 Redis 主线程（序列化耗时），且应用层内存瞬间飙升。
  • 正确做法：只取 0 99（Top 100），或使用 游标（Cursor） 配合 ZSCAN 分批遍历，绝对禁止全量导出。

🧩 P5 层级：极端异常与终极保底（考察全局视野） ​

Q12：如果 Redis 实例宕机重启，ZSET 中的排行数据没了，怎么恢复？业务能接受积分归零吗？

考察点：持久化与数据闭环（资金/荣誉相关，极其敏感）。

  • 积分/排行属于业务核心数据，不能依赖纯内存。采用 “WAL + 定期快照” 双保险：
  • ① AOF 持久化：开启 appendfsync everysec，最多丢失 1秒 的积分变动。
  • ② DB 落库备份：每次积分变动时，异步（MQ） 将 (userId, score, timestamp) 写入 MySQL 积分流水表。每天凌晨运行对账任务，计算每个用户的积分总和，生成 MySQL 全量快照。
  • ③ Redis 重建：如果 Redis 数据全丢，从 MySQL 快照表批量加载积分数据，通过 ZADD ... 灌入 Redis（千万级数据灌入约需几分钟，可接受）。
  • ④ 业务降级：在数据重建期间，排行榜接口返回“榜单维护中”，但“查个人积分”可以直接查 MySQL 兜底返回。

Q13：如果运营需要“手动置顶”或“人工加权”某个用户（比如官方号），不允许按照纯积分排序，怎么实现？

考察点：业务规则与技术实现的解耦能力。

  • ① 不改动 ZSET 的原始 Score。另设一个 Hash 或 String 存储权重因子：weight:user:{uid}（如默认 1.0，官方号设为 1.5）。
  • ② 查询时，从 ZSET 取出 Top 100 的 (Member, Score)，在应用层读取每个用户的权重因子，计算 最终展示分 = Score * weight，再在内存中重排序后返回给前端。
  • ③ 这种“查询后计算”的方式对 Redis 零侵入，且权重变更实时生效。若 Top 100 经过加权重排后有人跌出榜单，但原本的第 101 名可能加权后应进入榜单——这种情况业务通常可接受（仅展示前 100，加权后重排只在这 100 人中生效），若严格要求全局加权，需一次性取出更多候选（如 Top 500）再做计算。

Q14：如果某个用户的积分突然被扣成负数（如作弊扣除），ZINCRBY key -999999 执行后，ZSET 怎么处理负分？

考察点：ZSET Score 边界认知。

  • ZSET 的 Score 是 双精度浮点数（double），完全支持负数。ZINCRBY key -99999 member 会将 Score 减为负数，排名会掉到最后（ZREVRANK 返回较大值）。业务上只需保证前端展示时不显示负数分（显示为 0），但 Redis 保留真实负分用于后续积分补回。

Q15：灵魂总结题——如果让你用一句话概括“实时排行榜”的核心设计哲学，是什么？

考察点：技术抽象与降级思维。

  • “利用 ZSET 跳表的高效范围查询能力实现微秒级排名，通过复合分数（积分+时间戳）解决平局公平性，并用‘多 Key 独立写入 + 预创建双写切换’规避多维度榜单的阻塞与空窗风险，最终以异步 DB 落库作为资金级数据的终极防线。”

📋 六、Redis 千万级用户签到系统（Bitmap） ​

🔰 P1 层级：数据结构选型与基本原理（考察基本功） ​

Q1：为什么用户签到要用 Bitmap？用 String 存 {userId: timestamp} 的 Set 不行吗？

考察点：对 Bitmap 空间压缩能力的认知。

  • ① Set/Hash 存储每个用户的签到记录，一条记录至少需要几十字节。1 亿用户签到一次，内存占用高达 几 GB。
  • ② Bitmap 按位存储，每个用户只占 1 bit（0/1）。1 亿用户每日签到仅占用 约 12 MB（1亿 bits ÷ 8 = 12.5 MB），内存节省 2~3 个数量级。
  • ③ Bitmap 天然支持位运算（BITCOUNT、BITOP），做日活统计、连续签到分析极为高效。

Q2：Redis 的 Bitmap 底层是什么数据结构？最大能存多少位？

考察点：Redis String 与 Bitmap 的关系。

  • ① Bitmap 底层就是 Redis String（SDS），按位存储。最大长度受 Redis String 限制，512 MB，即最多可寻址 2^32 - 1 = 约 42.9 亿 个 bit 位。
  • ② 对于千万级用户（如 5000 万），偏移量远小于这个上限，完全够用。

Q3：SETBIT key offset 1 和 SETBIT key offset 0 分别代表什么？

考察点：命令语义清晰度。

  • ① SETBIT key offset 1：将偏移量 offset 对应的位设为 1，表示该用户当天已签到。
  • ② SETBIT key offset 0：将位设为 0，表示未签到（初始状态就是 0，通常无需显式设置）。
  • ③ offset 通常用用户 ID 或 用户 ID 取模后的数值。

🧠 P2 层级：存储设计与内存计算（考察细节经验） ​

Q4（必问！灵魂拷问）：你提到用“用户 ID 作为 offset”，但如果用户 ID 是自增的，注册 1000 万用户后 ID 最大到了 1000 万，Bitmap 确实只有 1000 万位（1.19 MB）。但如果用户 ID 是 UUID 或雪花算法生成的 19 位数字，怎么办？

考察点：稀疏 Bitmap（Sparse Bitmap）的处理能力——这是区分“背过八股”和“真做过”的核心分水岭。

  • 直接使用 UUID/19位长ID做 offset 会瞬间撑爆内存（最大 offset 可达 10^19，远超 512 MB 限制）。解决方案（三种选其一）：
  • ① 维护映射表（推荐）：将用户的长 ID 映射为自增的连续数字 ID（如维护一个 Redis Hash user:id:mapping 或直接使用 MySQL 的自增主键作为位图偏移量）。这样 Bitmap 的 offset 从 1 开始连续，内存最优。
  • ② 取模分片（折中方案）：将长 ID 对某个大数（如 1亿）取模作为 offset。但取模会产生哈希冲突（两个用户落到同一个 bit 位），需要结合布隆过滤器或二次校验，业务复杂度大增，不推荐。
  • ③ 分桶存储（终极方案）：按用户 ID 范围拆分成多个 Bitmap Key，如 sign:2026-01-14:0 存 ID 1~1000万，sign:2026-01-14:1 存 ID 1000万~2000万。这样每个 Key 的 offset 仍然连续可控。

Q5：每日签到用 sign:{date} 作为 Key，一年 365 个 Key，每个 Key 占用 1.19 MB（千万用户），一年总共多少内存？

考察点：数据生命周期管理与容量规划。

  • ① 千万用户每日 Bitmap 约 1.19 MB（1000万 bits ÷ 8 ÷ 1024 ÷ 1024）。一年 365 天约 435 MB，加上 Redis 内部 overhead（每个 Key 约 100 字节），总内存不到 500 MB，完全可接受。
  • ② 但需设置过期时间：历史签到数据可保留近 30 天（热点数据），超过 30 天的 Bitmap 导出到 离线存储（HDFS/OSS） 或 MySQL 归档后删除，控制 Redis 内存水位。如果业务需要保留全年数据，500 MB 仍在单机可承受范围。
  • ③ 内存优化补充：如果用户量达到 1 亿，每日 Bitmap 约 12 MB，一年约 4.3 GB，建议使用 Redis Cluster 分散存储，或只保留近 7 天热数据，历史数据转冷存储。

Q6：如果用 Bitmap 存签到，想统计“本月签到天数”，怎么用 BITCOUNT？

考察点：对 BITCOUNT 命令的理解。

  • ① BITCOUNT sign:2026-01 会统计整个 Bitmap 中所有为 1 的位的数量，即本月所有用户签到总次数（不是日活）。
  • ② 如果要统计某个用户的当月签到天数，需要对用户 ID 对应的位在 31 天的 Bitmap 中分别 GETBIT 再累加（31 次 GETBIT）。或者可以在设计时将 31 天的位拼接成一个 按月 Bitmap（如 sign:user:{uid}:2026-01，offset 为日期），这样对一个用户 BITCOUNT 一次即可统计当月签到天数。

⚔️ P3 层级：复杂业务场景（考察实战攻坚） ​

Q7：如何用 Bitmap 计算“连续签到天数”（如连续签到 7 天有奖励）？请给出具体实现。

考察点：位运算与业务逻辑的结合能力。

  • 方案一（每天独立 Bitmap，查 7 个 Key）：对用户 ID，依次 GETBIT sign:2026-01-14 {uid}、GETBIT sign:2026-01-13 {uid}……检查最近 7 天是否全为 1。从今天开始往前遍历，直到遇到 0 或超过 7 天。时间复杂度 O(7)，微秒级，完全可接受。
  • 方案二（按月 Bitmap + 位运算）：为每个用户维护一个按月的 Bitmap（sign:user:{uid}:2026-01），第 N 天签到就把第 N 位设为 1。要计算连续签到，将该用户的月 Bitmap 右移 N 位后与自身做 BITOP AND 运算，可以一次算出连续天数，但需要 Lua 脚本支持。优点是只需操作一个 Key，缺点是每个用户多存一个 Bitmap（空间换时间）。
  • 方案三（扩展 ZSET 辅助）：维护一个 ZSET continuous:{date}，Score 存连续签到天数，每天定时任务更新。但维护复杂度高，且可能不一致。推荐方案一，简单可靠。

Q8：如果用户昨天忘记签到了，今天想“补签”，怎么设计？补签后连续签到如何计算？

考察点：业务异常流程的存储设计。

  • ① 补签记录单独存储：不能直接修改历史日期的 Bitmap（因为那天的数据已经是最终态），而是另存一个补签记录 Key：repair:{date}:{uid} 或使用 Hash repair:2026-01-14 {uid} 1。
  • ② 查询连续签到时：先检查原始签到 Bitmap，若为 0 则检查补签记录是否存在，若存在视为已签到。
  • ③ 统计日活/月活时：BITCOUNT + 补签记录去重合并（在应用层计算），或每天凌晨将前一天的补签记录回填到当天的 Bitmap 中（SETBIT sign:2026-01-14 {uid} 1），然后删除补签记录。回填操作可用 Pipeline 批量处理。

Q9：如何用 BITOP 统计“本月连续签到超过 7 天的用户数”？

考察点：BITOP 的高级应用。

  • ① 假设月签到 Bitmap 是按用户 ID 为 offset 设计的（sign:2026-01-01 到 sign:2026-01-31）。
  • ② 使用 BITOP AND 将最近 7 天的 Bitmap 进行与运算，结果中为 1 的位表示该用户在最近 7 天每天都签到。
  • ③ 对结果执行 BITCOUNT，即可得到连续签到 7 天的用户数。
  • ④ 注意：BITOP 对大 Key 是 O(N) 操作，如果 Bitmap 很大（如 1 亿位），会阻塞 Redis 主线程几秒。优化：将 BITOP 放到 从节点（Replica） 或低峰期执行，不要放在用户请求的同步链路中。

🚀 P4 层级：高可用与分片策略（考察架构能力） ​

Q10：如果用户量超过 1 亿，单个 Bitmap 的 SETBIT 和 BITCOUNT 性能会下降吗？怎么解决？

考察点：大 Key 治理与分片扩展。

  • ① 单个 1 亿位的 Bitmap 占用 12.5 MB，Redis 读写都是 O(1) 的直接内存寻址（SETBIT 是 O(1)），性能不会下降，依然是微秒级。
  • ② 真正的风险是网络传输：BITCOUNT 需要遍历整个 String 的所有字节，1 亿位（12.5 MB）的 BITCOUNT 耗时约 几十毫秒，且阻塞 Redis 主线程。
  • ③ 优化方案（分段分片）：
    • 将用户 ID 按范围分片，如 sign:2026-01-14:0（ID 1~5000万）、sign:2026-01-14:1（ID 5000万~1亿）。
    • 统计日活时，并行对多个分片执行 BITCOUNT，应用层累加。
    • 这样每个分片只有 6 MB，BITCOUNT 耗时降到 10ms 以内，且可以分散到不同 Redis 节点（Cluster）并行执行。

Q11：BITOP AND 对多个大 Bitmap 做运算时，会不会导致 Redis 内存瞬间翻倍（结果 Key 和原 Key 同时存在）？

考察点：对 Redis 内存峰值的敏感度。

  • 会！ BITOP 的结果会生成一个新的 Key，内存会临时翻倍。如果原 Bitmap 是 12 MB，结果也是 12 MB，内存峰值增加 12 MB，风险不大；但如果原 Key 是 500 MB（5 亿用户），峰值会增加 500 MB，可能导致内存溢出。
  • 解决方案：
  • ① 使用 BITOP 的 STORE 参数时，提前评估目标 Key 的大小，确保 Redis 有空闲内存（info memory 监控）。
  • ② 考虑将 BITOP 移到从节点执行，不影响主节点的写入服务。
  • ③ 或改用 应用层逐块计算：按分段分片（每片 1000 万位），逐片执行 BITOP 并累加，峰值内存可控。

🧩 P5 层级：极端异常与终极保底（考察全局视野） ​

Q12：如果 Redis 的 Bitmap Key 因为过期时间设置不当，导致某天凌晨 0 点大量 Key 同时过期（雪崩），SETBIT 写入失败怎么办？

考察点：缓存雪崩防御与降级。

  • ① 给 Key 的过期时间增加随机扰动：如 EXPIRE sign:2026-01-14 86400 + random(0, 3600)，让 365 个 Key 分散过期，避免同一秒集中淘汰。
  • ② 使用 PEXPIREAT 精确设置：统一设置为当月的最后一秒过期，而不是 TTL 86400 秒。
  • ③ 兜底方案（双 Key 策略）：签到写入时同时写当天和前一天的备份 Key（如 sign:2026-01-14:bak），如果主 Key 因过期被删除，备份 Key 仍可提供服务，直到定时任务重建主 Key。

Q13：如果某天凌晨 0 点，千万级用户同时签到（如春节打卡活动），SETBIT 的 QPS 瞬间飙到 50 万，Redis 扛不住怎么办？

考察点：流量突刺的削峰填谷能力。

  • ① 本地聚合缓冲（写优化）：在应用层（如网关或业务服务器）将 1秒 内同一用户的多次签到请求去重合并（一个用户一天只需签到一次），只保留第一次有效请求，丢弃后续重复请求，可将写入 QPS 降低 90%。
  • ② 异步批量写入：应用层将签到请求放入本地阻塞队列（如 Disruptor），消费者以 Pipeline 批量（如每批 1000 条）写入 Redis，大幅减少网络 IO 和 Redis 连接数。
  • ③ 限流 + 降级：在网关层对单个用户 ID 限流（1 秒最多 2 次签到请求），超过直接返回“已签到”。如果 Redis 延迟超过阈值（如 50ms），熔断降级，签到请求直接写入 MySQL（或本地日志），待 Redis 恢复后异步补录。
  • ④ 终极杀招（本地缓存优先）：在活动期间，签到状态优先查本地内存缓存（Caffeine，TTL=5秒），用户再次请求时直接返回“已签到”，完全不透传到 Redis，极大降低 Redis 的热点压力。

Q14：如果 Bitmap 的一个字节因为 Redis 内存损坏或 AOF 重写异常，导致某一位翻转（0 变 1 或 1 变 0），怎么发现和修复？

考察点：数据校验与修复机制。

  • ① 前置对账：每天凌晨运行对账任务，将 Redis 当天的签到 Bitmap 与 MySQL 签到流水表做抽样比对（抽取 1% 的用户），如果差异率超过阈值（如 0.1%），触发告警。
  • ② 定期全量重建：每周从 MySQL 全量签到数据重新生成 Bitmap，用 SETBIT 批量灌入 Redis，覆盖可能存在的脏数据。
  • ③ 技术层面：开启 Redis AOF 持久化 + RDB 快照（save 900 1），即使内存数据损坏，重启时可以从 RDB/AOF 恢复最近状态。

Q15：灵魂总结题——如果让你用一句话概括“Bitmap 签到系统”的核心设计哲学，是什么？

考察点：技术抽象与极端压缩思维。

  • “利用 Bitmap 的按位存储将每个用户的签到状态压缩为 1 bit，以极致的空间效率（千万用户仅 1.19 MB/天）支撑海量用户的日活统计、连续签到分析；并通过分段分片、本地聚合缓冲和异步落库，将峰值写入压力和存储成本降到最低。”

📋 七、拓展按理 ​

一、分布式锁与并发控制类 ​

  1. 分布式锁（Redisson / SET NX EX）

    • SET key value NX EX 30 加锁，Lua 脚本原子解锁（校验 value 防止误删）。
    • Redisson 的 Watchdog（看门狗）自动续期机制。
    • 主从切换导致锁丢失的 RedLock 算法争议与取舍。

  2. 接口幂等性防重复提交

    • 利用 SETNX 或 SET NX EX 生成请求唯一 Token，保证同一请求在 TTL 内不被重复处理。

  3. 秒杀系统库存扣减（非红包场景）

    • 用 DECR / DECRBY 原子扣减库存，配合 Lua 脚本判断库存是否充足。
    • 与红包 LPOP 方案的适用场景对比。

二、限流与防刷类 ​

  1. 滑动窗口限流（ZSET 实现）

    • 将请求时间戳作为 Score 存入 ZSET，ZREMRANGEBYSCORE 清除窗口外的旧数据，ZCARD 统计窗口内请求数。

  2. 令牌桶限流（Lua 脚本实现）

    • 存储上次补充时间、当前令牌数，Lua 脚本原子计算令牌补充逻辑，支持突发流量。

  3. 分布式全局计数器（日活/UV/PV）

    • INCR / INCRBY 实现实时计数，配合 EXPIRE 实现日维度自动重置。

三、统计与去重类 ​

  1. 亿级 UV 统计（HyperLogLog）

    • PFADD 添加用户 ID，PFCOUNT 统计近似 UV，误差率约 0.81%，每个 Key 仅占 12KB，与 Bitmap 签到形成“精确 vs 近似”的对比方案。

  2. 布隆过滤器（Redisson / RedisBloom）

    • 解决缓存穿透问题（查询不存在的数据直接穿透 DB）。
    • 推荐系统去重、爬虫 URL 去重。

四、业务场景实战类 ​

  1. 购物车存储（Hash）

    • HINCRBY cart:{userId} {skuId} 1 增减商品数量，HGETALL 拉取全量购物车。
    • 大 Key 治理：购物车商品过多时的分段存储方案。

  2. 分布式 Session 共享 / 用户登录态

    • SETEX session:{token} 1800 {userJson} 存储用户信息，多服务间共享登录态。

  3. Feed 流 / 关注动态时间线（推拉结合）

    • 为每个用户维护一个 ZSET（feed:{userId}），Score 存动态发布时间戳，ZREVRANGE 拉取最新动态。
    • 大 V 写扩散（推） vs 普通用户读扩散（拉）的权衡。

五、数据一致性与稳定性类 ​

  1. 缓存穿透 / 击穿 / 雪崩的防御组合拳

    • 穿透：布隆过滤器 + 缓存空对象（SETEX null 60）。
    • 击穿：互斥锁（SET NX EX）重建缓存 + 逻辑过期（永不过期 + 异步刷新）。
    • 雪崩：过期时间随机打散 + 多级缓存（本地 Caffeine + Redis）。

  2. 缓存与数据库双写一致性

    • 先更新 DB，再删缓存（Cache-Aside）的延迟双删策略。
    • 结合 Canal 监听 MySQL Binlog 异步更新 Redis，保证最终一致性。

六、底层原理与运维类（附加实战视角） ​

  1. Big Key 扫描与治理

    • SCAN + MEMORY USAGE 定位大 Key，拆分为 Hash 分片或 ZSET 分页。

  2. 热 Key 发现与解决

    • 本地缓存（Caffeine）扛热 Key 读流量，或对热 Key 做“副本随机后缀”分散到多个节点。

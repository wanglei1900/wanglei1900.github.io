MySQL 日志系统完整学习笔记 ​

日志是 MySQL 体系中极其重要的组成部分。无论是故障诊断、性能调优、数据恢复还是主从复制，都离不开对各种日志的理解和运用。MySQL 的日志系统可以看作一系列分工明确的“黑匣子”，它们从不同维度记录着数据库的运行细节。

目录 ​

  1. 概述
  2. 错误日志 (Error Log)
  3. 通用查询日志 (General Query Log)
  4. 慢查询日志 (Slow Query Log)
  5. 二进制日志 (Binary Log)
  6. 中继日志 (Relay Log)
  7. InnoDB 重做日志 (Redo Log)
  8. InnoDB 撤销日志 (Undo Log)
  9. 其他日志简介
  10. 日志综合管理与最佳实践
  11. 总结

1. 概述 ​

MySQL 内置了多种日志，按层次可以划分为 Server 层日志 和 存储引擎层日志：

  • Server 层：错误日志、通用查询日志、慢查询日志、二进制日志、中继日志。
  • InnoDB 层：重做日志 (Redo Log)、撤销日志 (Undo Log)。

这些日志在故障恢复、数据复制、问题排查、性能分析、审计等场景中发挥着不可替代的作用。

2. 错误日志 (Error Log) ​

作用 ​

记录 MySQL Server 启动、运行、关闭过程中的重要信息，尤其包含错误、警告和注解。当数据库出现故障时，错误日志是第一手诊断资料。

日志内容 ​

  • 服务器启动/关闭时间
  • 版本信息
  • 严重错误（如表损坏、无法分配内存）
  • InnoDB 引擎的相关错误
  • 复制过程中的 I/O 线程、SQL 线程错误
  • 警告信息（例如，某些不推荐使用的语法）

配置参数 ​

参数说明
log_error错误日志文件路径。若不配置，默认写到数据目录下的 host_name.err
log_error_services (8.0+)日志服务组件链，如 log_filter_internal; log_sink_internal
log_error_verbosity (5.7+)日志详细程度(1=仅错误,2=错误和警告,3=错误、警告和注释)

查看与管理 ​

sql
-- 查看错误日志位置
SHOW VARIABLES LIKE 'log_error';

-- 查看日志内容 (MySQL 8.0)
SHOW VARIABLES LIKE 'log_error_services';

-- 刷新错误日志（在操作系统层面重命名后，执行此命令新建日志文件）
FLUSH ERROR LOGS;

实用技巧 ​

  • 当磁盘写满或表损坏时，错误日志通常会给出明确提示。
  • 配合 log_error_verbosity=3 在开发环境可获取更多信息。
  • 建议使用日志轮转工具（如 logrotate）定期归档，防止文件过大。

3. 通用查询日志 (General Query Log) ​

作用 ​

记录所有客户端连接、断连和每一条执行的 SQL 语句。它是一个完整的“语句流水账”，在调试、审计时可能用到，但开启后会严重影响性能并迅速消耗磁盘空间，生产环境极少长期开启。

配置参数 ​

参数说明
general_log是否开启 (ON/OFF)
general_log_file日志文件路径，默认 host_name.log
log_output输出目标：FILE(文件)、TABLE(mysql.general_log 表)、FILE,TABLE(两者)

动态启用 ​

sql
SET GLOBAL general_log = 'ON';
SET GLOBAL log_output = 'FILE';   -- 或 'TABLE'

查看日志 ​

sql
-- 文件类直接查看文件
-- 表类查询
SELECT * FROM mysql.general_log ORDER BY event_time DESC LIMIT 20;

注意事项 ​

  • 输出到表比文件开销更大，谨慎使用。
  • 用完及时关闭：SET GLOBAL general_log = 'OFF';。
  • 调试复杂问题时作为临时手段，不要作为持久审计方案。

4. 慢查询日志 (Slow Query Log) ​

作用 ​

记录执行时间超过指定阈值的 SQL 语句，是性能优化中最重要的日志。

配置参数 ​

参数说明
slow_query_log是否开启
slow_query_log_file日志文件路径
long_query_time阈值（秒），可精确到微秒
min_examined_row_limit扫描行数少于该值的语句不记录
log_queries_not_using_indexes是否记录未使用索引的查询
log_slow_admin_statements是否记录慢管理语句（如 ALTER, OPTIMIZE）
log_throttle_queries_not_using_indexes每分钟最多记录多少条无索引查询

示例配置 ​

ini
[mysqld]
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 2
log_queries_not_using_indexes = 1
min_examined_row_limit = 1000

分析工具 ​

  • mysqldumpslow (官方)
    bash
    mysqldumpslow -s c -t 10 /var/log/mysql/slow.log   # 按次数排序前10
  • pt-query-digest (Percona Toolkit) – 功能强大，生成汇总报表。
  • Explain 分析：找到具体语句后，使用 EXPLAIN 进一步优化。

使用建议 ​

  • 将 long_query_time 设得稍低（如 0.5 秒），先收集所有潜在慢查询，优化后再提升阈值。
  • 记录未使用索引的查询有助于发现索引缺失，但可能产生大量日志，配合 log_throttle_queries_not_using_indexes 限流。

5. 二进制日志 (Binary Log) ​

作用 ​

二进制日志记录所有修改数据库数据的 逻辑操作（如 INSERT、UPDATE、DELETE 及可能产生数据变化的 DDL）。核心用途：

  • 复制：主库上的二进制日志传递到从库，从库重放实现数据同步。
  • 基于时间点的恢复 (PITR)：恢复全量备份后，重放二进制日志到指定时刻。

日志格式 ​

格式特点
STATEMENT记录 SQL 语句本身，体积小，但某些函数（如 NOW()）可能导致主从不一致
ROW (推荐)记录每一行数据的变化，最安全，但体积大
MIXED默认使用 STATEMENT，特定情况自动切换为 ROW

配置参数 ​

参数说明
log_bin指定二进制日志文件基础名（不指定路径则放数据目录）
server_id必须显式指定，每个服务器唯一，否则二进制日志无法启用
binlog_format格式：ROW / STATEMENT / MIXED
sync_binlog控制二进制日志同步到磁盘的频率。1=每次事务提交都同步，最安全
max_binlog_size单个二进制日志文件大小上限（默认为1G）
binlog_expire_logs_seconds (8.0+)二进制日志自动清除的时间（秒），替代旧版 expire_logs_days
binlog_row_image行格式下的记录细节：full / minimal / noblob

常用操作 ​

sql
-- 查看二进制日志列表
SHOW BINARY LOGS;

-- 查看当前正在写入的二进制日志
SHOW MASTER STATUS;

-- 查看日志事件
SHOW BINLOG EVENTS IN 'binlog.000003' LIMIT 10;

-- 清除指定日志之前的所有文件
PURGE BINARY LOGS TO 'binlog.000010';
-- 根据时间清除
PURGE BINARY LOGS BEFORE '2026-06-01 00:00:00';

-- 自动清除策略（8.0）
SET GLOBAL binlog_expire_logs_seconds = 604800;  -- 7天

-- 重置（删除所有二进制日志并重新开始）
RESET MASTER;  -- 操作极其危险，仅测试环境

mysqlbinlog 工具 ​

bash
# 解码 ROW 格式日志需要加 -v
mysqlbinlog -v --base64-output=DECODE-ROWS binlog.000003

# 按时间范围导出
mysqlbinlog --start-datetime="2026-07-01 10:00:00" \
            --stop-datetime="2026-07-01 11:00:00" binlog.000003 > restore.sql

Binlog 与 Redo Log 的对比 (详见后续章节) ​

  • 层次：Binlog 是 Server 层逻辑日志；Redo Log 是 InnoDB 层物理日志。
  • 内容：Binlog 记录“怎么修改的”；Redo Log 记录“在哪个表空间、哪个页的偏移量处修改了什么”。
  • 用途：Binlog 负责复制和 PITR；Redo Log 负责崩溃恢复，保证已提交事务的持久性。

两阶段提交 (2PC) ​

为了保证 Binlog 和 Redo Log 的一致性，InnoDB 采用内部 XA 事务：

  1. Prepare 阶段：写入 Redo Log 并标记为 prepare 状态。
  2. 写 Binlog：提交事务时写入 Binlog。
  3. Commit 阶段：将 Redo Log 中的对应事务标记为 commit 状态。
    如果在第二步之后、第三步之前崩溃，恢复时若发现 Binlog 中有该事务，则自动将 Redo Log 提交，从而保证主从一致。

6. 中继日志 (Relay Log) ​

作用 ​

中继日志是从库（Replica/Slave） 上的日志。从库 I/O 线程接收主库的二进制日志事件并写入中继日志，SQL 线程再读取中继日志执行，实现复制。

配置参数 ​

参数说明
relay_log中继日志文件基础名
relay_log_index中继日志索引文件名
relay_log_purgeSQL 线程执行完成后是否自动删除中继日志（默认 ON）
max_relay_log_size单个中继日志文件大小上限
relay_log_recovery (8.0 默认开启)从库崩溃后，根据存储的信息丢弃未完成的事务，保证数据一致
relay_log_info_repository存放复制信息的方式：TABLE（推荐，默认）或 FILE
sync_relay_log中继日志同步频率，默认 10000 表示每 10000 个事务同步一次

查看与管理 ​

sql
-- 显示从库状态，包含中继日志信息
SHOW SLAVE STATUS\G
-- 或（8.0.22+ 新语法）
SHOW REPLICA STATUS\G

-- 查看中继日志事件
SHOW RELAYLOG EVENTS IN 'relay-log.000010' LIMIT 5;

自动清理 ​

relay_log_purge=ON 时，SQL 线程执行完一个中继日志文件的所有事件后会自动将其删除，一般无需人工干预。如果遇到磁盘空间问题，可检查是否有未处理完成的日志积压。

7. InnoDB 重做日志 (Redo Log) ​

作用 ​

Redo Log 是 InnoDB 存储引擎特有的物理日志，记录了对数据页的修改。核心目标是保证事务的持久性（Durability），实现崩溃恢复（Crash Recovery）。

工作原理 (WAL) ​

采用 Write-Ahead Logging（预写式日志） 策略：修改数据页前先将 Redo Log 写入磁盘。即使数据页本身还未刷新到磁盘，事务提交后数据仍不会丢失。崩溃恢复时，从上次检查点 (Checkpoint) 开始重放 Redo Log，将数据页恢复到崩溃前的状态。

配置参数 ​

参数说明
innodb_log_file_size每个 Redo Log 文件的大小（默认 48MB，建议 1GB 起）
innodb_log_files_in_groupRedo Log 文件组的文件数量（默认 2）
innodb_log_group_home_dirRedo Log 存放目录，默认数据目录
innodb_flush_log_at_trx_commit最关键的持久性与性能参数（见下表）

innodb_flush_log_at_trx_commit 详解 ​

值行为特点
1 (默认)每次事务提交时将 Redo Log 写入并刷盘完全持久化，不会丢事务，但性能开销最大
2每次事务提交时写入 OS 缓存，每秒刷盘OS 崩溃可能丢失 1 秒内事务，性能较好
0每秒钟将 Redo Log 写入 OS 缓存并刷盘性能最好，但 MySQL 崩溃会丢失 1 秒数据

⚠️ 数据安全建议：核心业务系统必须设置 innodb_flush_log_at_trx_commit=1 并配合 sync_binlog=1 以保证 ACID 中的 D（持久性）。

Redo Log 文件大小设置 ​

  • 总大小 = innodb_log_file_size × innodb_log_files_in_group。
  • 太小的日志会导致频繁检查点，影响写入性能；太大则崩溃恢复时间长。
  • 修改文件大小需要先关闭 MySQL，移动旧日志文件，再重启（8.0 支持在线调整 innodb_log_file_size，通过 innodb_log_file_size 变量需重启生效？实际上 8.0.30 之前需要重启，之后支持在线调整 innodb_redo_log_capacity 新参数，但传统参数仍需重启）。

8. InnoDB 撤销日志 (Undo Log) ​

作用 ​

Undo Log 记录事务修改前的数据版本，主要提供：

  • 事务回滚：将数据恢复到修改前的状态。
  • MVCC（多版本并发控制）：快照读时构造历史版本，实现非锁定一致性读。

存储管理 ​

  • 默认存放在共享表空间 ibdata1 中，但官方强烈建议使用独立的 Undo 表空间（5.6 引入，8.0 完全独立管理）。
  • 8.0 的 Undo 表空间可通过 DDL 管理：
    sql
    CREATE UNDO TABLESPACE undo_002 ADD DATAFILE 'undo_002.ibu';
ALTER UNDO TABLESPACE undo_002 SET INACTIVE; -- 标记为不活动后删除
DROP UNDO TABLESPACE undo_002;

相关参数 ​

参数说明
innodb_undo_directoryUndo 表空间的目录，默认数据目录
innodb_max_undo_log_sizeUndo 表空间最大大小（默认 1GB），超过会标记为可截断
innodb_undo_log_truncate是否启用 undo 表空间自动截断回收（默认 ON）
innodb_purge_threads后台清理线程数
innodb_undo_tablespaces (5.7)已弃用，8.0 由 DDL 管理

长事务与 Undo Log ​

长时间未提交的事务会导致 Undo Log 无法回收，可能引起：

  • 表空间膨胀：Undo 表空间不断增长。
  • 慢查询：历史版本链过长，MVCC 查询变慢。
  • 监控方式：
    sql
    -- 查看活跃事务和运行时间
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started;
-- 查看 undo 表空间大小
SELECT TABLESPACE_NAME, FILE_NAME, FILE_SIZE/1024/1024 AS MB
FROM information_schema.FILES WHERE FILE_TYPE = 'UNDO LOG';

9. 其他日志简介 ​

DDL 日志 (InnoDB DDL Log) ​

  • 5.7 开始，InnoDB 在 DDL 操作过程中会将进度写入 mysql.innodb_ddl_log 表，用于崩溃恢复时继续或回滚 DDL。
  • 完全由系统管理，DBA 通常无需干预。

审计日志 (Audit Log) ​

  • 不属于 MySQL 默认组件，通常使用插件（如 MySQL Enterprise Audit、Percona Audit Plugin、MariaDB Audit Plugin）。
  • 可以记录用户连接、查询类型、操作对象等，用于安全审计。
  • 相比通用查询日志，性能影响更小且可筛选。

10. 日志综合管理与最佳实践 ​

空间与性能平衡 ​

  • 二进制日志：推荐 binlog_format=ROW，sync_binlog=1，binlog_expire_logs_seconds=604800（7天），并监控磁盘使用。
  • Redo Log：总大小建议等于或略大于 innodb_log_file_size×innodb_log_files_in_group 让写入性能平稳，生产通常 2-4 GB。
  • 慢查询日志：开启，长期保留以便历史分析，配合日志分析工具。

日常监控与轮转 ​

  • 使用监控系统检查日志文件所在分区的磁盘使用率。
  • 通用查询日志和慢查询日志可启用操作系统 logrotate 轮转，并配合 FLUSH LOGS。
  • 二进制日志依赖 binlog_expire_logs_seconds 自动清理，不必使用轮转。
  • 错误日志注意定期归档。

备份策略中的日志 ​

  • 全量备份（如 mysqldump 或 XtraBackup）+ 二进制日志实现 PITR。备份后应立即记录当前的 Binlog 位置或 GTID。
  • 从库上通过 relay_log_recovery=ON 保障复制的容错性。

关键安全配置清单 ​

ini
[mysqld]
# 二进制日志
server_id = 1
log_bin = /data/binlog/mysql-bin
binlog_format = ROW
sync_binlog = 1
binlog_expire_logs_seconds = 604800

# Redo 日志（InnoDB）
innodb_flush_log_at_trx_commit = 1
innodb_log_file_size = 1G
innodb_log_files_in_group = 2

# 慢查询日志
slow_query_log = 1
long_query_time = 0.5
log_queries_not_using_indexes = 1

# 错误日志
log_error = /var/log/mysql/error.log
log_error_verbosity = 3

故障排查顺序 ​

  1. 连接失败或服务启动不了 → 错误日志
  2. 数据库响应突然变慢 → 慢查询日志 + SHOW PROCESSLIST + innodb_trx
  3. 磁盘空间报警 → 检查 binlog、relay log、undo 表空间、错误日志
  4. 主从延迟 → 中继日志积压情况、SHOW REPLICA STATUS
  5. 数据误删 → 二进制日志 + 备份进行时间点恢复

11. 总结 ​

日志类型所属层次主要作用是否默认开启生产建议
错误日志Server记录启动、运行、错误信息是必须开启
通用查询日志Server记录所有 SQL (流水账)否临时调试，用完即关
慢查询日志Server记录超出阈值的 SQL，优化利器否建议开启
二进制日志Server复制与时间点恢复否（需配置 server_id 和 log_bin）必须开启
中继日志Server (从库)暂存主库传来的 Binlog 事件复制开启时自动创建使用默认配置即可
Redo LogInnoDB保证持久性，崩溃恢复是（固定两个文件）关注大小与刷盘策略
Undo LogInnoDB回滚与 MVCC是（系统管理）监控长事务，独立表空间

深刻理解这些日志的设计与协同，是掌握 MySQL 高可用、高性能和数据安全的关键。建议结合实际环境，逐一配置并实践日志的分析与故障排查，才能将理论知识转化为真正的运维能力。
